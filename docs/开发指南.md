# 开发指南

本项目优先保证协议、队列、setup 状态机、控制策略和失败恢复可在 host 环境重复验证，再接触真实 Switch PCTL。实现改动应保持边界清晰，并同步更新[协议](协议.md)或[测试指南](测试指南.md)中对应的权威说明。

## 架构

```text
家长端 PWA / CLI
        │ 生成 v1/v2 token
        ▼
Companion NRO / Tesla Overlay
        │ pctc:u IPC 优先，SD 队列回退
        ▼
Sysmodule orchestration
        │ token / rules / policy
        ▼
Platform adapters ──> PCTL / SDMC / time / logs
        ▲
        └── Common core（纯 C、无平台依赖）
```

安全边界在 sysmodule。NRO 和 Overlay 只创建请求、等待匹配 result；它们不能决定 token 是否有效，也不能直接调用 PCTL。`pctc:u` 接受请求前先持久化，IPC 已接受后的客户端不得回退重提，只能从 SD 读取同一 request id 的晚到结果。

## 模块职责

### Common core

`common/` 保存 token v1/v2、HMAC、时间计算、规则、控制策略、request/result schema 和稳定错误映射。

它不得依赖 libnx、文件系统、SD 卡路径、UI、真实时钟或进程级可变平台状态，也不得理解原始 PCTL `u16` 布局。

### Platform adapters

`platform/` 隔离环境相关能力：

- Storage：读取、原子写、追加、rename、删除、元数据和目录遍历。
- PCTL：状态、备份、目标写入、timer 控制和能力探针。
- Time：Unix time、UTC+8 day index 和 minute of day。
- Logging：文本日志、结构化事件和 PCTL 证据。

Host 使用 `mem_storage`、`pctl_stub` 和 fake time 注入成功或失败；Switch 实现只替换 adapter，不改变 common 或策略。

### Sysmodule

`sysmodule/` 负责 boot lifecycle、首次引导前置解除、配置缓存、请求队列、stuck processing 恢复、nonce ledger、PCTL 恢复事务、result/event 写入和 `enforce` 对账。启动时必须先恢复未完成事务并创建 `disable.flag`，然后才可恢复队列请求或启动 IPC。

队列空闲扫描退避到 5 秒；配置按文件元数据刷新；`enforce` 只在 UTC+8 分钟边界、配置 reload 或显式唤醒时对账。目标未变化时不得重复写 PCTL、state 或成功日志。

### Companion 与 Overlay

`companion/` 提供共享 request builder、result 解释和 transport。NRO 提供孩子页、8 位数字码输入、触摸/手柄操作以及 PIN 保护的家长区。

`companion/overlay/` 使用 C++20 和 vendored libtesla，只负责 8 位数字码输入与请求/result 桥接。它不得读取 `grant_secret`、调用系统软键盘或访问 PCTL。Overlay 与 NRO 是相互独立、地位相同的客户端。

### Tools 与 tests

`tools/` 保持 Python 标准库实现，提供 token、fixture、协议探测、PWA、构建打包和安装工具。`tests/` 覆盖 Python、C host、UI 状态和 package 安全规则；测试必须使用固定时间和可复现 fixture，不依赖真实 Switch 服务。

## 依赖规则

允许方向：

```text
companion -> common
sysmodule -> common
sysmodule -> platform adapters
tests     -> common / host doubles
tools     -> protocol-compatible fixture logic
```

禁止方向：

```text
common         -> libnx / SDMC / UI / real clock
business logic -> raw PCTL layout
client UI      -> grant_secret / token verification / PCTL
```

除 Overlay 外默认使用 C99。Overlay 可使用 C++20，但保持 `-fno-exceptions`、`-fno-rtti`，避免复杂静态初始化和不可控动态分配。

## 上游依赖

调查顺序为当前仓库和协议文档、仓库 vendored 版本、本机上游源码，最后才是 GitHub。

- PCTL service/session、公开签名或 dispatch 行为优先查看 `../libnx`。
- 当前 libnx 没有 `StartPlayTimer (1451)`、`GetPlayTimerRemainingTime (1454)`、`GetPlayTimerSettings (145601)` 和 `SetPlayTimerSettingsForDebug (195101)` 的公开封装。不得从缺失定义推断参数单位或 0x44 layout；只能依据仓库协议与真机 A/B 证据。
- Tesla 生命周期、输入和绘制优先查看 `../libtesla`，但构建只能使用 `companion/overlay/vendor/libtesla/`。
- vendored libtesla 当前固定为 `f766e9b607a05e9756843cbd62b3bfb98be1646c`；同步时必须更新 `UPSTREAM.txt`、许可证和补丁说明。
- 只有本地证据不足或任务明确要求核对上游状态时才查询 GitHub，并记录仓库、commit/tag 或 issue/PR 链接及查询日期。

## 安全不变量

- 唯一 package 的初始 `control_mode` 为 `enforce`，并包含 `boot2.flag`；未知旧配置仍降级为 `observe`。
- `setup.json` 在 `released` 之前只允许状态和引导恢复操作；在 60 秒激活宽限结束前不得执行 Enforce。
- `flags/retry_setup_release.flag` 和 `flags/restore_install_snapshot.flag` 优先于 `disable.flag`；后者仍覆盖所有正常控制写入。
- 坏 JSON、未知 schema、未知请求和无效 token 不得触碰 PCTL。
- 首次解除不得覆盖已有 `backups/install_pctl_snapshot.json`；snapshot 必须包含完整 0x44 raw、长度、timer 状态、时间和 SHA-256。
- 所有普通 PCTL 写入必须先持久化恢复事务，包含 PCTL snapshot 和受影响 rules/state/ledger 前像；写后必须启动 timer 并确认运行时目标。
- dry-run、PCTL 失败、result 失败和 nonce ledger 失败不得提前消费 nonce。
- 普通 play-timer 写入不依赖预先 capability 探针，也不受 unlimited-to-limited 配置阻止。
- `raw_block` 和 `suspend` 必须由各自探针验证；旧 play-timer capability 字段只兼容读取，不参与判断或展示。
- 恢复无法证明时清除能力并按协议创建 `disable.flag`，保持 fail-open。
- child-visible UI、日志和示例不得泄露真实 `grant_secret`、PIN 或 token。

## 开发与验证

Python、协议和安全打包回归的统一入口：

```powershell
python .\tools\test.py
```

涉及 C、Makefile、NRO、sysmodule 或 package 的权威入口：

```powershell
python .\tools\package_remote.py
```

容器直接读取挂载工作区，未提交改动也会参与构建。不要维护旁路的手工 SSH、`docker exec` 或复制构建产物流程。

## 合并前检查

- 新逻辑能否在无 Switch 的 host 测试中覆盖成功和失败路径？
- `observe` 是否完全避免写入与 nonce 消费？
- 每个普通写路径是否创建事务前像、确认运行时目标，并只在 result/state/nonce 成功后提交？
- setup/recovery flag 是否在 `disable.flag` 之前处理，普通请求是否在 setup active 前返回 `setup_pending`？
- PCTL adapter 是否只使用显式短时 `pctl`/`pctl:s` 会话，绝不占用 `pctl:a`？
- request/result、错误码、fixture 和可选字段是否同步更新协议与兼容测试？
- 外部可见行为是否更新使用或测试指南？
- 文档是否仍以 UTF-8 保存，示例是否只使用占位 secret？
