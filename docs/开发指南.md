# 开发指南

PlayWise 先在 host 侧证明协议、队列、安全状态机和恢复事务，再接触真实 Switch PCTL。外部行为变化必须同步更新[协议](协议.md)和[测试指南](测试指南.md)。

## 架构边界

```text
家长端 PWA / CLI
        │ 生成离线加时码
        ▼
Companion NRO / Tesla Overlay
        │ pctc:u IPC 优先，SD 原子队列回退
        ▼
Release sysmodule
        │ token / rules / setup / recovery
        ▼
platform adapter ──> PCTL / SDMC / time / logs
        ▲
        └── common（纯 C、无平台依赖）
```

- `common/`：token、规则、策略、request/result、稳定错误和版本常量；不得依赖 libnx、SD 路径、UI 或真实时钟。
- `platform/`：PCTL、存储和时间适配；私有 0x44 layout 只能存在于 Switch 适配层。
- `sysmodule/`：唯一安全边界，负责预检、setup、事务、恢复、队列、nonce、Enforce 和日志。
- `companion/`：只创建请求和展示结果，不读取 secret、不验证 token、不直接调用 PCTL。
- `device_lab/`：内部危险操作入口；不得向 Release UI 反向添加 LAB 枚举或字段。
- `tools/` 与 `tests/`：保持标准库和确定性 host 测试。

IPC 接受请求前必须先持久化。IPC 已接受后客户端不得回退重提，只能按同一 request ID 等待 IPC 或读取 SD result。

## Release、Support 与 Device Lab

公开版本只有 `release` profile，版本源为受一致性校验的 `common/version.h` 与 `common/version.mk` 配对。Python manifest 生成和 package 门禁统一通过 `tools/playwise_version.py` 读取这两个文件；两者不一致时构建必须立即失败。Support 是 Release 内建能力，不是第二个用户包。

Device Lab 使用：

| 项目 | Release | Device Lab |
| --- | --- | --- |
| Title ID | `4200000000BD2300` | `4200000000BD23F0` |
| IPC | `pctc:u` | `pwtl:u` |
| SD 根目录 | `sdmc:/switch/playwise` | `sdmc:/switch/playwise-device-lab` |
| manifest profile | `release` | `device-lab` |
| 默认 boot2 | 有 | 无 |
| 默认构建 | `make packages` | 仅显式 `make device-lab-package` |

Release 二进制不得包含危险 handler、工程探针、旧控制模式或 `capabilities.json`。LAB NRO 必须持续显示水印，并要求 ZL+ZR+A 组合确认。

## 安全状态机

1. 启动先验证 build manifest、环境指纹、PCTL 只读状态、layout 和未完成事务。
2. `verified` 表示命中资格基线；`accepted_unknown` 表示结构正常但需家长确认；安全前置失败进入 `protection`。
3. PIN、secret 和 rules 均有效且家长确认后，才保存不可覆盖的安装快照并解除当前限制。
4. `released` 保留 5 秒同步宽限，随后进入 `active`。
5. Enforce 写入后先记录 `applied_pending_confirmation`；30 秒内确认成功才回到 idle，超时回滚。该窗口中的 `recovery/active` 是当前进程持有的活跃事务，周期调度不得把它当成启动遗留事务。
6. 启动时仅检查一次真正遗留的旧事务；恢复成功后创建 `disable.flag` 并停止新写入，回滚无法证明时同样熔断。

`disable.flag` 不是全局停机：status、诊断导出、重试修复和安装快照恢复必须仍然工作。`active` 或 `restored` 下解除停用都必须由家长确认并重新经过只读预检，通过后才删除 flag、释放当前限制并重新接管。恢复优先级为安装快照恢复、setup 重试、启动时未完成事务、写入熔断、普通请求、Enforce。

## 数据和秘密

- `config.json` 只保存非秘密选项；不得重新加入控制模式或 secret。
- sysmodule 首次启动用 `randomGet` 生成 32 字节 secret，写入 `credentials.json`。
- Companion vendored 的二维码编码器固定在 `third_party/qrcodegen/`，上游来源、commit、许可证和查询日期记录在 `UPSTREAM.txt`；二维码只编码 URL fragment，不发起网络请求。
- `playwise-public-demo-secret-0001` 是家长明确启用的公开低安全模式标识，不是安装 seed 或私密示例；启用必须重新验证 PIN、二次确认并持续告警。
- PIN 允许家长选择 1–64 位纯数字，salt 使用随机 16 字节；旧 6 位 PIN 无需迁移。`auth.json` 保存 HMAC-SHA256 hash/salt 以及不含 PIN 明文的失败次数和冷却期限。
- 诊断导出采用白名单，永不打包 `credentials.json`、`auth.json`、token、完整 ledger 或 recovery 原始秘密。
- 系统日期无效时日志写入 `logs/undated/<boot-id>/`，不得静默丢失。

## 上游与构建规则

调查顺序：本仓库与协议文档、vendored 固定版本、本机 `../libnx` / `../libtesla`，最后才是 GitHub。当前 libnx 不公开命令 1451、1454、1952、145601、195101；不得从缺失定义推断参数单位或 0x44 layout。

本地回归：

```powershell
python .\tools\test.py
```

C、NRO、Overlay、sysmodule 和 package 权威验证：

```powershell
python .\tools\package_remote.py
```

不要维护手工 SSH、`docker exec` 或复制产物的旁路命令。Device Lab 只用于内部显式构建，不得加入公开 package 目标。

## 合并前检查

- 成功与失败路径是否都有确定性测试？
- setup 写入前是否完成只读预检？
- 写入前是否持久化前像，写后是否有界确认并可回滚？
- nonce 是否只在 token 写入、result 和 ledger 都成功后消费？
- `disable.flag` 是否仍允许 status、support 和 recovery？
- Release Zip 是否唯一且三个组件嵌入同一 manifest？
- Release 二进制是否没有 LAB/旧契约标记和占位 secret？
- 文档是否为 UTF-8，并明确最终真机资格状态？
