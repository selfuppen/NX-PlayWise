# 开发指南

PlayWise 先在 host 侧证明协议、队列、安全状态机和恢复事务，再接触真实 Switch PCTL。环境准备与平台差异见[开发环境指南](开发环境指南.md)；外部行为变化必须同步更新[协议](协议.md)和[测试指南](测试指南.md)。

## 架构边界

```text
家长网页（PWA）/ 命令行工具（CLI）
        │ 生成离线加时码
        ▼
主机应用（Companion NRO）/ 游戏内浮窗（Tesla Overlay）
        │ pctc:u IPC 优先，SD 原子队列回退
        ▼
标准分发后台服务（sysmodule）
        │ token / rules / setup / recovery
        ▼
platform adapter ──> PCTL / SDMC / time / logs
        ▲
        └── common（纯 C、无平台依赖）
```

- `common/`：token、规则、策略、request/result、稳定错误和版本常量；不得依赖 libnx、SD 路径、UI 或真实时钟。
- `platform/`：PCTL、存储和时间适配；私有 0x44 layout 只能存在于 Switch 适配层。
- `sysmodule/`：唯一安全边界，负责预检、setup、事务、恢复、队列、nonce、Enforce 和日志。
- `companion/`：只创建请求和展示结果，不读取 secret、不验证 token、不直接调用 PCTL。
- Companion NRO 主题是独立渲染层能力：平台无关的偏好解析和语义色板位于 `companion/nro/ui_theme.*`；libnx 系统主题读取与配置持久化只在 NRO 编排层，绘制层只接收只读主题视图。计时、请求、PCTL、Token、sysmodule 和 Overlay 不得依赖 NRO 主题。
- `device_lab/`：内部危险操作入口；不得向标准分发 UI 添加 LAB 枚举或字段。
- `tools/` 与 `tests/`：保持标准库和确定性 host 测试。

IPC 接受请求前必须先持久化。IPC 已接受后客户端不得回退重提，只能按同一 request ID 等待 IPC 或读取 SD result。

## 标准分发构建、Support 与 Device Lab

标准分发构建使用 `release` profile，版本源为受一致性校验的 `common/version.h` 与 `common/version.mk` 配对。Python manifest 生成和 package 门禁统一通过 `tools/playwise_version.py` 读取这两个文件；两者不一致时构建必须立即失败。Support 是标准分发构建的内建能力，不是第二个用户包。

公开输出区分两层：`playwise-<版本>.zip` 是只含 Switch 运行时目录的标准安装包；`playwise-complete-<版本>.zip` 是普通用户首选的完整交付包，且成员严格为前述标准安装包和生成后的 `playwise-offline.html`。聚合层不得改变或解开标准安装包，也不得携带 Device Lab、安装脚本或额外说明文件。

标准安装包必须可直接合并覆盖到 SD 卡根目录。六个首次安装 JSON 位于 `switch/playwise/defaults/`，不得以 `switch/playwise/*.json` 运行路径进入 Zip；Release sysmodule 和 Companion 只在对应运行文件缺失时原子创建，绝不覆盖已有文件。普通覆盖升级仅替换 NRO、Overlay、sysmodule、`build.json` 和不可变模板；显式 `-Clean`/`-Full` 才能删除普通 PlayWise 数据。新版 `release_id` 仍走兼容指纹变化后的家长重新检测流程，并保留 PIN、密钥、规则和原安装快照。

Device Lab 使用：

| 项目 | 标准分发构建 | Device Lab |
| --- | --- | --- |
| Title ID | `4200000000BD2300` | `4200000000BD23F0` |
| IPC | `pctc:u` | `pwtl:u` |
| SD 根目录 | `sdmc:/switch/playwise` | `sdmc:/switch/playwise-device-lab` |
| manifest profile | `release` | `device-lab` |
| 默认 boot2 | 有 | 无 |
| 默认构建 | `make packages` | 仅显式 `make device-lab-package` |

标准分发二进制不得包含危险 handler、工程探针、运行时控制模式或 `capabilities.json`。LAB NRO 必须持续显示水印，并要求 ZL+ZR+A 组合确认。

## 安全状态机

1. 启动先验证 build manifest、环境指纹、PCTL 只读状态、layout 和未完成事务。
2. `verified` 表示命中资格基线；`accepted_unknown` 表示结构正常但需家长确认；安全前置失败进入 `protection`。
3. PIN、secret 和 rules 均有效且家长确认后，才保存不可覆盖的安装快照并解除当前限制。
4. `released` 保留 5 秒同步宽限，随后进入 `active`。
5. Enforce 写入后先记录 `applied_pending_confirmation`；30 秒内确认成功才回到 idle，超时回滚。该窗口中的 `recovery/active` 是当前进程持有的活跃事务，周期调度不得把它当成启动遗留事务。
6. 启动时仅检查一次启动前遗留事务；恢复成功后创建 `disable.flag` 并停止新写入，回滚无法证明时同样熔断。

`disable.flag` 不是全局停机：status、诊断导出、重试修复和安装快照恢复必须仍然工作。`active` 或 `restored` 下解除停用都必须由家长确认并重新经过只读预检，通过后才删除 flag、释放当前限制并重新接管。恢复优先级为安装快照恢复、setup 重试、启动时未完成事务、写入熔断、普通请求、Enforce。

## 数据和秘密

- `config.json` 只保存非秘密选项；不得重新加入控制模式或 secret。
- sysmodule 首次启动用 `randomGet` 生成 32 字节 secret，写入 `credentials.json`。
- Companion vendored 的二维码编码器固定在 `third_party/qrcodegen/`，上游来源、commit、许可证和查询日期记录在 `UPSTREAM.txt`；二维码只编码 URL fragment，不发起网络请求。
- `playwise-public-demo-secret-0001` 是家长明确启用的公开低安全模式标识，不是安装 seed 或私密示例；启用必须重新验证 PIN、二次确认并持续告警。
- PIN 允许家长选择 1–64 位纯数字，salt 使用随机 16 字节；所有合法长度使用相同的凭据格式。`auth.json` 保存 HMAC-SHA256 hash/salt 以及不含 PIN 明文的失败次数和冷却期限。
- 诊断导出采用白名单，永不打包 `credentials.json`、`auth.json`、token、完整 ledger 或 recovery 原始秘密。
- 系统日期无效时日志写入 `logs/undated/<boot-id>/`，不得静默丢失。

## 上游与构建规则

### Switch UI 字符兼容

Companion NRO 与 Overlay 的用户可见文案只能使用已经在项目字体和真机上验证的字形。数学正负号使用 ASCII `+`、`-`，范围优先写成“1 到 120”，状态转换和方向使用中文描述；不要直接加入排版减号、全角正负号、长横线、箭头、省略号或中点等容易缺字的 Unicode 符号。确需新增特殊符号时，必须先完成 NRO 与 Overlay 真机字体验证并更新字符门禁。Markdown 文档和家长网页的正文排版不受此限制。

调查顺序：本仓库与协议文档、vendored 固定版本、可用的本地上游 checkout，最后才是 GitHub。维护者机器在 `../libnx` 和 `../libtesla` 提供可选的只读上游 checkout；它们不是构建依赖。当前调查用 libnx 不公开命令 1451、1454、1952、145601、195101；不得从缺失定义推断参数单位或 0x44 layout。

本地回归：

```text
python tools/test.py
```

家长端单文件离线版由模块化前端确定性生成，修改 `tools/ptc_frontend` 后运行：

```text
python tools/build_ptc_standalone.py
python tools/build_ptc_standalone.py --check
```

提交必须同时包含更新后的 `tools/ptc_frontend/playwise-offline.html`；Pages 部署和完整交付包构建都会用 `--check` 拒绝过期产物。最终用户直接使用生成的 HTML，不需要 Python。

C、NRO、Overlay、sysmodule 和 package 权威验证：

```text
python tools/package_remote.py
```

准备新版本时，在干净工作区运行统一发布脚本，例如：

```text
python tools/release_version.py <新版本号>
```

脚本会先拒绝非法版本和已存在的 `v<版本>` tag，再同步更新 `common/version.h` 与
`common/version.mk`，执行上述权威 package 验证，创建正式版本提交和注解 tag。tag 创建后，脚本
自动把补丁版本递增为下一开发版本（例如 `1.0.0` 之后为 `1.0.1-alpha`），并创建独立的 alpha
版本提交；因此 tag 始终指向正式版提交，分支 HEAD 则继续开发。仅隔离测试脚本本身时可使用
`--no-verify`；正式发布不得跳过验证，也不得强制移动已有 tag。

维护者默认容器流程不得用手工 SSH、`docker exec` 或复制产物的旁路命令替代。其他环境必须复现相同的 clean、测试、构建、打包和校验门禁。Device Lab 只用于内部显式构建，不得加入标准分发 package 目标。

## 合并前检查

- 成功与失败路径是否都有确定性测试？
- setup 写入前是否完成只读预检？
- 写入前是否持久化前像，写后是否有界确认并可回滚？
- nonce 是否只在 token 写入、result 和 ledger 都成功后消费？
- `disable.flag` 是否仍允许 status、support 和 recovery？
- 标准安装包是否唯一且三个组件嵌入同一 manifest，完整交付包是否只含该安装包与字节一致的离线网页？
- 标准分发二进制是否没有 LAB handler、运行时控制模式和占位 secret？
- 文档是否为 UTF-8，并明确当前真机资格状态？
