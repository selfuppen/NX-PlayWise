# PCTL1952 候选验收与契约版本

本契约针对已经接入独立累计、加时、护眼/非电视模式基线和v2日摘要的标准候选。新manifest声明 `usage_contract:"pctl1952_v2_direct"`，表示不再安装1440计数代理；旧 `pctl1952_v1_proxy1440` 继续按原代理规则验证。源码策略**不是资格结论**，不能换字符串借用旧报告；Device Lab原始探测与Eden模拟不声明产品契约。

## v2直接累计的独立要求

v2仍包含 `usage_live`、`grant_recovery`、`reason_handover`，以 `direct_cycle` 的 `unlimited → tracking → blocked → restored → unlimited_restored` 替代旧代理循环。五阶段业务均不限时／0，PCTL依次不限时、不限时、BLOCKED、不限时、不限时，配置分钟均规范化为0；护眼enabled依次false／true／true／true／false，限制原因仅中间BLOCKED为eye_care，数据的 `automatic_recovery:true` 须有实际自动恢复依据。最初不限时至少60秒与1952同步增长，整循环1451计数不增。`rest_deadline_unix` 保存实际实例期限；BLOCKED端点在期限前，恢复端点须在期限后0至15秒内。两端累计增量仅允许期限后已恢复使用的秒数另加2秒配对容差，不能把整个受限间隔当使用，也不能把采样后缀一概当作应冻结。缺期限、过晚端点、越界消费或自动1451均拒绝。不限时不要求timer标志为true来冒充可计数，必须依真实1952与raw判断。

`reason_handover` 仍要求eye_care和dock共同受限、移除eye后dock继续受限，解除最后原因后恢复不限时／0，1451不增；延期的实体dock缺口不因替换契约消失。v2观察字段使用 `direct_cycle_observed`，不接受旧proxy字段代替，其他原观察／签署、完整包身份及恢复门禁保持。

**每个v2端点**额外具有 `raw_source:{"path":"raw/<原始流>","sha256":"<原字节哈希>","line":2}`，line从1开始且必须指向标准sample行。文件须在本case的raw_sources内，启动头commit／release匹配候选；原始流需有有效stop、无损坏尾行、失败样本、缺口或保存失败。校验器逐字段配对1952、完整0x44解码模式／分钟、boot、日、unix_after、begin_ns、跨度、timer、临时解除、1451及限时的带符号余额，禁止规范化端点脱离原行。最终原始流可由几条短链共享，各规范化文件仍独立。晋级检查名使用 `pctl1952_direct_handover`，旧代理检查名不能代替。

v2的 `restoration` 另有 `before_raw_source` 和 `after_raw_source`，格式与上述raw_source一致，必须指向本报告已审计端点。该两行的完整settings_hex及timer须等于报告的恢复字段，不能只填两个相等的自报字符串；失败停止的原始流不能充作成功恢复原件。

以下原四链表格及proxy观察说明是**v1历史契约**，继续用于旧候选；v2生成器自动选择上述新case集合，不能提交旧proxy表格冒充新实现通过。

既有 OLED/HOS 22.5.0/Atmosphère 1.11.2 原始取证只作为能力背景，见 [功能影响分析](../调研/专题分析/PCTL1952功能影响分析.md)。新标准候选要绑定自己的 commit、release ID、Zip 与三个生产组件 SHA-256；不得拿旧 tap 或不同二进制上的读数资格化它。手工时钟/时区、多日休眠、官方 PIN 临时解除、Lite 和纯游戏/PDM 统计仍是独立缺口，本短链不扩大这些范围。

## 生成草稿与验收

先提交候选源码，以统一入口生成无 tracked 修改的完整资格候选（标准、完整交付、Device Lab 和默认 Eden）：

```text
python tools/package_remote.py --release
python tools/qualification/pctl_usage_qualification.py --packages build/packages --output device-reports/<批次>/pctl-usage-qualification.json --model mariko-oled --hos 22.5.0 --atmosphere 1.11.2
```

生成器从原标准 Zip 内的 `build.json` 和生产二进制取身份与哈希。它只创建 `draft`、观察值为 `null` 的索引，不操作设备、不补写真值，也拒绝覆盖已有文件。开发 dirty 包可以生成草稿检查字段，但不能通过最终门禁；正式采集前必须绑定 clean 候选重新生成。

采集以下四个**标准后台**短链。保持原始现场附件不变；按下面的格式另外生成规范化样本文件，将路径与 SHA-256 填入草稿 `cases`。每个短链在同一 boot、同一日期完成；受控机型/系统由操作者核对。[标准只读采集](PCTL1952标准采集.md)提供原始流及离线准备/核验、一次 FTP 拉回，不部署、不写 PCTL、不自动完成四短链或人工签署，也不新增危险 Lab 命令。

| case | 样本 phase 顺序 | 机器可核对的事实 |
| --- | --- | --- |
| `usage_live` | `before → after` | 正常可用、timer 已确认、无临时 PIN；至少 60 秒累计与单调时间同步增长 |
| `grant_recovery` | `before → after → active_end` | 已用超过业务额度，带符号剩余保留负值；按真实累计向上取整加时、实际授权正确、解除后至少 60 秒继续正常消费 |
| `proxy_cycle` | `unlimited → proxy → blocked → proxy_restored → unlimited_restored` | 业务不限时保持 0 分钟的业务表达；执行不限时/1440/BLOCKED/1440/不限时依次正确、累计不因写入跳涨或归零，自动休息恢复没有新增 1451 |
| `reason_handover` | `both_blocked → eye_removed → released` | 护眼与非电视模式同时限制；移除护眼后仍被非电视限制；剩余原因解除才回到 1440，自动路径没有新增 1451 |

`grant_recovery` 的配置目标为 `min(1440,max(L,ceil(U/60e9))+face)`，实际授权为目标减基数，不能把额度修正量当授权。推荐复用小额超额恢复链，避免反复做无关的大额加时。

所有样本文件采用以下平台无关格式；纳秒值使用规范十进制字符串，避免 JSON double 丢精度。示例是格式演示，不是真机证据：

```json
{
  "schema_version": 1,
  "kind": "pctl_usage_samples",
  "subject": {"commit": "<候选40位commit>", "release_id": "<候选release-id>"},
  "release_components": {"<三个生产组件相对路径>": "<各自sha256>"},
  "raw_sources": [{"path": "raw/<不可变原始采集文件>", "sha256": "<原文件sha256>"}],
  "grant_minutes": 15,
  "effective_minutes": 15,
  "samples": [{
    "phase": "before",
    "source": "pctl_1952",
    "scope": "console_usable_time",
    "ipc_result": 0,
    "boot_id": "<采集boot-id>",
    "day_index": 2380,
    "captured_at": 1783526400,
    "monotonic_ns": "100000000000",
    "total_ns": "4191000000000",
    "pairing_span_ns": 100000000,
    "start_timer_calls": 0,
    "timer_enabled": true,
    "temporarily_unlocked": false,
    "business_mode": "limit",
    "business_minutes": 60,
    "pctl_mode": "limit",
    "configured_minutes": 60,
    "signed_remaining_ns": "-591000000000",
    "restriction_reasons": ["daily_allowance"]
  }]
}
```

`grant_minutes/effective_minutes` 只用于加时短链。`release_components` 必须含索引里的三个完整路径和哈希；`subject` 与索引一致。样本从 raw 1952、raw signed 1454、0x44 设置及标准 Result/日志规范化，`pairing_span_ns` 记录这一组端点实际采集跨度，不是任意设定的容差。跨度须 ≤2 秒，带符号余额与配置减累计的误差也须 ≤2 秒。每对相邻样本间隔须 >0 且 ≤300 秒，墙钟与单调时间误差 ≤2 秒，累计不能倒退或比间隔多增超过 2 秒；这是有界配对容差，不代表私有协议精度的新硬件结论。

`configured_minutes` 是规范化执行配置：LIMIT 1–1440，BLOCKED/不限时记 0；不要把不限时 wire sentinel 当业务分钟。执行不限时仍必须保留 raw 配置来源，不能仅因无余额而推断。`start_timer_calls` 是该 boot 采集期间从标准后台日志确认的累计调用次数，不能用 Lab 进程或重启后归零的次数拼接。`restriction_reasons` 只允许 daily_allowance/bedtime/eye_care/dock；未知读数不能编成成功 0。

操作者须保留可审查原始材料并签署 `attestation.operator/signed_at`，确认同一候选已加载、原始配对正确、主机可用时间范围、加时后真实恢复、代理循环和剩余原因仍阻止使用。`restoration` 保存相同的完整 0x44 前后 hex、timer 前后 bool 与空 `unexpected_raw_offsets`。满足这些事实后才能把索引设为 `final`，不能把机器生成的 draft/null 批量改成 true 冒充观察。

每个规范化文件的 `raw_sources` 至少绑定一个保留的原始采集附件，不能指向索引或规范化样本本身；路径须在报告目录内，晋级前也会复核其字节哈希。原始材料可以跨短链共享，例如同一连续 wire log，但每份规范化样本必须独立。

## 门禁与晋级

继续运行既有 `verify_device_qualification.py --packages ... --reports ... --expected-model ... --expected-hos ... --expected-atmosphere ...`；当前契约自动要求本报告，不能靠省略新的 CLI 开关跳过。旧 Device Lab campaign、bedtime 和可选护眼报告照常验证，本短链不替代其正式功能资格。

校验器比较目录与 Zip 内嵌 manifest，校验最终报告/环境/二进制/样本 SHA-256、严格类型/范围/重复键、短链数值和恢复证据。样本路径必须留在报告目录内，不能重复借用一个文件。验证结果保存报告与全部样本哈希；`promote_qualified_build.py` 在创建输出目录和复制之前再次核对这些材料，并将绑定保存到 detached `qualification.json`。原候选 Zip 字节不变。

机器门禁检查完整性和一致性，不能独立证明人类填入样本的真实性。没有对应证据时保留pending，不修改原始取证，不把模拟／host fixtures当真机材料。v1不支持去代理结论；v2必须完成自己的新候选、标准原始流、真实不限时生命周期和健康规则组合。源码实现或Host门禁通过不等于真机验证或正式资格通过。

三包身份校验要求标准和 Device Lab 两个 manifest 都是 clean，各自 Zip 的 manifest 与目录相同，并要求完整包内的标准 Zip 与本次标准包逐字节一致。重复 Zip 成员或重复 JSON 字段不接受；晋级会再次读取这些身份信息，验证记录的 subject 和生产组件也必须仍匹配。文件哈希正确本身不能补救打包角色或候选身份的错误。
