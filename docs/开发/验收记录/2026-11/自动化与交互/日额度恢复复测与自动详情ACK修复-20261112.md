## ACK 根因与软件修复

第二轮保存的额外 status `115085000-0003` 明确返回 daily_allowance=true、restricted_now=1、temporary_unlocked=false；没有有效 UI trace，因此不单靠 ID 形状声称已证明它的客户端来源。

源码核对发现确定的匹配矛盾：`ptc_companion_result_summary_parse` 会对每日、就寝、护眼和电视规则的正常受限状态设置 `access_recovery_required=true`，该字段表示需要提供解限入口；旧 `ptc_overlay_detail_matches` 却直接拒绝这个字段为 true 的摘要。现有测试手工构造摘要，没有经过真实解析生成此派生字段，因而漏检。此缺陷可阻止四种正常受限详情完成 ACK，不需要用动画或 I/O 推测解释。

修复仅从详情状态匹配中移除这一错误拒绝条件。实际家长／PIN／键盘等敏感页面仍由 `automatic_detail_drawn` 的 GUI 状态检查排除；停用、官方临时解除或未知、错误日／原因／实例、过期身份／请求和有效 owner 仍沿用原门禁。没有延长 ACK 的两秒期限、调整 ready 租期或改变 PCTL 控制逻辑。

新增回归通过真实 `PtcResultState → status JSON → PtcCompanionResultSummary` 路径覆盖四种正常受限成功匹配，并覆盖错误实例、停用、官方解锁未知及明确解锁拒绝。统一入口在修复前明确得到四项预期失败；修复后完整 C/Python/UI、标准三组件及 Zip、安全打包、默认 Eden NRO 构建／校验通过。
