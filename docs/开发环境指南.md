# 开发环境指南

本文区分项目通用要求、维护者默认环境、devkitPro 构建环境和 Switch 真机验证。个人机器的路径、端口和工具版本不是项目协议；所有开发者都必须满足相同的测试、打包和安全门禁。

## 环境分层

| 层级 | 必需内容 | 可替代或可选内容 |
| --- | --- | --- |
| Host 回归 | Python 3、Git、确定性 fixtures | Windows、PowerShell、Docker 和真实 Switch 均非必需 |
| Host C 测试 | C99 编译器、Make | 编译器和操作系统可替换 |
| Switch 完整构建 | devkitPro、devkitA64、libnx、FreeType、Make，以及仓库的统一打包门禁 | SSH 地址、容器名称和宿主系统可替换 |
| 依赖复现 | 仓库内 vendored libtesla 与 QR Code Generator | `../libnx`、`../libtesla` 只用于可选上游调查 |
| 模拟器快速迭代 | devkitPro，以及 `make eden-test-nro` 产出的 `build/eden-test/pctc-eden.nro` | 完全可选；只用于看 UI 和业务流程，不产出任何 PCTL 证据 |
| 真机验收 | 明确的机型、HOS、Atmosphère 和当前候选 Zip | Host、容器和模拟器测试均不能替代 |

## Host 快速开始

本地协议、Python、前端和安全打包回归使用平台中立入口：

```text
python tools/test.py
```

这些测试使用固定时间、fixture 和 host adapter，不访问真实 Switch 服务。只修改 Python、协议文档或静态页面时，可先用此入口获得快速反馈。

`make test` 还会编译 host C 测试，因此需要 C99 编译器和 Make。任何 C、C++、Makefile、NRO、Overlay、sysmodule 或 package 改动都必须继续完成统一的 devkitPro 构建验证。

## Eden 模拟器快速迭代（可选）

只想快速看 UI 和业务流程时，可在 devkitPro 环境用 `make eden-test-nro` 生成 `build/eden-test/pctc-eden.nro`，把这一个 NRO 加载进 Eden 即可。它自带隔离的 `sdmc:/switch/playwise-eden` 数据根目录和进程内模拟后台，不需要 sysmodule、不需要铺开安装包。完整步骤、固定测试参数与限制见[测试指南](测试指南.md)。这是可选的迭代手段，不属于任何门禁，也不能作为 PCTL 私有命令或计时行为的证据。

## Switch 完整构建

项目支持的权威入口是：

```text
python tools/package_remote.py
```

该入口通过一次 SSH 会话在 devkitPro 环境执行清理、host C/Python/UI 测试、三个 Switch 组件构建、标准安装包、完整交付包与 Device Lab 包构建，并在共享工作区校验 Zip、离线网页、manifest 和二进制。`build/packages/` 最终保留 `playwise-<版本>.zip` 标准安装包和首推给普通用户的 `playwise-complete-<版本>.zip` 完整交付包；后者只嵌套标准安装包与 `playwise-offline.html`。构建环境需要可用的 devkitPro/devkitA64、libnx、FreeType、Make、Git、Zip 和 Python。

脚本要求本地和构建环境看到同一份工作区：构建产物由构建环境写入挂载目录，再由 host 侧校验。它不是把源码上传到任意远程机器后再复制产物的通用远程 builder。不要用多次手工 SSH、`docker exec` 或复制产物拼接出另一套候选包构建流程。

## 维护者默认 Windows 环境

当前维护流程使用 Windows、PowerShell、Docker Desktop、Windows OpenSSH 和 Python 3。`tools/package_remote.py` 的默认连接 profile 是：

| 项目 | 默认值 |
| --- | --- |
| SSH host | `127.0.0.1` |
| SSH port | `1888` |
| SSH user | `root` |
| 容器工作区 | `/ws/playwise` |

这些值是脚本和测试覆盖的维护者默认配置，不是其他开发者必须复制的网络拓扑。可用以下参数连接等价的共享 devkitPro 环境：

```text
python tools/package_remote.py \
  --host <host> \
  --port <port> \
  --user <user> \
  --container-path <mounted-repository-path> \
  --identity <private-key-path>
```

PowerShell 可将以上参数写在同一行。容器密码只允许由 OpenSSH 交互读取；自动化连接使用 `--identity` 指定已授权私钥。

仓库的 `docker/docker-compose.yml` 是维护者本机示例。使用前必须把宿主卷路径改成自己的工作区父目录，并保证容器内仓库路径与 `--container-path` 一致。Compose 默认把宿主 `1888` 映射到容器 SSH `58791`；本机使用时将端口项限制为 `127.0.0.1:1888:58791`。

开发镜像允许 root SSH，并在 Dockerfile 中设置开发用密码，因此端口只能绑定或暴露到可信的回环开发环境，不得直接发布到局域网或互联网。优先使用私钥并限制宿主防火墙规则。镜像基于 devkitA64 的 `20260215` 标签；这是固定标签，不是固定镜像 digest。

## 依赖与上游源码

实际构建使用：

- devkitPro 环境中的 libnx；
- `companion/overlay/vendor/libtesla/` 中固定的 libtesla；
- `third_party/qrcodegen/` 中固定的 QR Code Generator。

维护者机器在仓库相邻目录提供 `../libnx` 和 `../libtesla`，用于核对 service、dispatch、Overlay 生命周期、绘制和输入行为。其他开发者不需要创建这两个 checkout；它们不参与构建。同步 vendored 依赖时必须更新对应 `UPSTREAM.txt` 中的仓库、commit/tag、许可证和查询日期。

上游调查顺序是当前仓库与协议文档、vendored 固定版本、可用的本地上游 checkout，最后才是 GitHub。远程 `main` 或 `master` 不能代替项目固定 commit 的行为证据。

## CI 与部署现状

当前 GitHub Actions 只部署家长端 PWA 静态资源。Switch C/C++、NRO、Overlay、sysmodule 和 package 尚未由 CI 构建，完整门禁由维护者 devkitPro 环境执行。因此不能把 Pages workflow 的成功视为 Switch 候选包通过验证。

## 真机验证

真机验收至少分为两类：

- UI 与交互验收：覆盖 Companion NRO、Overlay、触控、手柄输入、刷新、加时码预览/确认和中断恢复；
- 资格验证：使用当前候选 Zip，在明确记录的机型、HOS 和 Atmosphère 组合上执行[测试指南](测试指南.md)中的完整流程。

PCTL 私有命令的参数单位、0x44 layout 和计时行为只能由仓库协议、确定性向量和真机 A/B 证据确定，不能从 libnx 缺少公开封装推断。模拟器（含 Eden）用模拟 PCTL 适配器，其行为完全由仓库代码决定，因此不构成上述任何一类证据。

## 平台注意事项

- 仓库中文文档统一使用 UTF-8。PowerShell 5.1 读取时显式使用 `Get-Content <file> -Encoding utf8`。
- Windows 创建中文 Git commit message 时使用无 BOM UTF-8 文件，并在提交后用 `git log -1 --pretty=%B` 检查标题。
- Linux 和 macOS 可直接运行平台中立的 Python host 回归；完整 Switch 构建仍需连接满足上述契约的 devkitPro 环境。
- 构建产物未出现在 host 工作区时，先检查共享挂载和 `--container-path` 是否指向同一仓库，再检查 SSH host key、端口、用户和私钥权限。
