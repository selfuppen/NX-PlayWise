# 详细测试计划

本文档保留测试阶段、通过标准和风险边界。具体自动验证命令、远程 devkitPro 命令、package 生成命令和模拟器辅助流程统一见 `docs/测试指南.md`。

当前代码库目标是从 Observe MVP 进入 disabled/observe boot2 真机验证：

- Host 侧 token、request queue、result JSON 和 safe package 行为可自动验证。
- `offline_code` 和 `status` 请求可以在 observe 模式下处理。
- 生成的 SDMC 目录布局默认安全，默认 `control_mode=observe`，默认不包含 `boot2.flag`。
- Companion NRO 文件协议可先用 Ryujinx/Eden 等模拟器或 NRO-only 真机流程验证。
- Sysmodule skeleton、Switch SDMC adapter、Switch time provider 和保守 PCTL adapter 已可远程构建。
- boot2 自启、真实 SDMC 持久化、PCTL 读状态和强控制仍需分阶段真机验证。

## 1. 自动验证阶段

入口：

```powershell
python .\tools\verify_auto_tests.py
```

通过标准：

- Python token v1 回归通过。
- Python observe queue 回归通过。
- host protocol probe 可以完成 init、offline_code/status request、observe processing 和 result 写出。
- observe result 为 `status: ok`、`mode: observe`、`dry_run: true`。
- request 被归档到 `inbox/done/`。
- observe 不消费 nonce。
- safe package 目录完整，zip 顶层为 `switch/`，且不包含 `boot2.flag`。
- `--boot2` 缺少 `--sysmodule-exefs` 时会失败。

远程 devkitPro 完整构建验证见 `docs/测试指南.md`。涉及 C、Makefile、NRO、sysmodule 或 package 的变更，必须先提交并推送 `master`，再让远程仓库快进到 `origin/master` 后验证。

## 2. Host 协议 Probe

目的：

- 在无 Switch 环境下验证 SDMC 目录、request queue、result schema 和 observe dry-run 语义。
- 为模拟器或 NRO-only 真机流程准备可复制的 request/result 数据。

通过标准：

- `protocol_probe.py init` 创建 `switch/play-time-control/` 目录、配置文件和 inbox/results/logs/ledger/backups/flags 子目录。
- `config.json` 的 `control_mode` 为 `observe`。
- 有效 `offline_code` 写出 ok result，并包含 `dry_run: true`。
- `status` 写出 ok result，并包含 `mode: observe`。
- 坏 token、错日期、超上限等拒绝路径写出稳定 error result。
- `ledger/used_nonces.jsonl` 在 observe 模式下不存在或保持为空。

## 3. 模拟器辅助测试

模拟器测试只用于 Companion NRO、UI 输入和文件协议。推荐在 Windows 10 上使用 Ryujinx/Eden 降低真机前台 UI 测试风险。

可验证：

- NRO 可以启动。
- 菜单、输入、按键、软键盘和超时显示符合预期。
- 离线码输入会写出 request JSON。
- 手工或 host 工具放入匹配 result 后，NRO 能正确读取和展示。
- 家长区 UI 完成后，家长操作会写出预期 request type。

不可验证：

- Atmosphere boot2 sysmodule 自动启动。
- PCTL IPC。
- play timer 真实读写。
- raw block。
- suspend。
- 真机恢复路径。

通过标准：

- UI 生成协议兼容的 request 文件。
- UI 读取匹配的 result 文件。
- result mismatch 时有明确显示。
- 后端无响应时显示超时或后台未响应，不显示为业务失败。

## 4. 真实 Switch 测试

真实 Switch 测试必须分阶段进行，不要从 `enforce` 开始。

### 4.1 前置条件

- 真实 Nintendo Switch。
- Atmosphere CFW。
- 可写 SD 卡。
- Homebrew Menu。
- 远程 devkitPro 已成功构建所需 package。
- 有已知恢复方式：能移除 `boot2.flag`，或能创建 `sdmc:/switch/play-time-control/flags/disable.flag`。
- 在 boot2 或强控制测试前，已理解并实测 `disable.flag` 恢复路径。

### 4.2 Safe SDMC Layout

目的：

- 只验证 SD 卡根目录解压后的文件布局。
- 不安装 boot2，不触碰 PCTL。

通过标准：

- `sdmc:/switch/play-time-control/config.json` 存在。
- `inbox/pending/`、`inbox/processing/`、`inbox/done/`、`results/`、`logs/`、`ledger/`、`backups/`、`flags/` 存在。
- 没有 `sdmc:/atmosphere/contents/4200000000BD2300/flags/boot2.flag`。
- `config.json` 中 `control_mode` 为 `observe`。

### 4.3 NRO-only

目的：

- 在没有 sysmodule boot2 风险的情况下验证 Companion 文件访问。

通过标准：

- Companion 可以从 Homebrew Menu 启动。
- Companion 可以提交 `status` 或 `offline_code` request。
- request 出现在 `sdmc:/switch/play-time-control/inbox/pending/`。
- 使用 `tools/make_result.py` 或 host `process-observe` 生成匹配 result 后，Companion 可以读取并展示。
- 未安装 boot2 sysmodule。

### 4.4 Disabled Boot2

目的：

- 在不访问 PCTL 的情况下验证 sysmodule 启动和 fail-open 入口。

通过标准：

- sysmodule 能启动并写出日志。
- 提交 request 后得到结构化 result。
- result reason 为 `disabled`。
- 不读取、不写入 PCTL。
- `disable.flag` 或移除 `boot2.flag` 的恢复路径可用。

### 4.5 Observe Boot2

目的：

- 验证真实 sysmodule request 处理和 PCTL 只读路径。

通过标准：

- 有效 `offline_code` result 包含 `status: ok`。
- result 包含 `mode: observe` 和 `dry_run: true`。
- 不写入 PCTL。
- 不消费 nonce。
- 如果 PCTL 读取成功，result state 包含可用的 restriction 状态字段。
- 如果 PCTL 读取失败，result 仍是结构化且稳定的。
- `logs/events.jsonl` 记录 request 和 result 流程。

### 4.6 Observe 拒绝用例

在 observe 模式下运行：

- 错误 secret。
- 错误日期。
- 加时时长超过上限。
- 格式错误的 token。
- 未知 request type。
- 坏 JSON。

通过标准：

- Result 为 `status: error`。
- Reason 稳定。
- 不消费 nonce。
- 不尝试写入 PCTL。
- sysmodule 已处理 request 时，Companion 不显示后端超时。

### 4.7 Grant / Enforce / Raw Block / Suspend

进入本阶段前必须满足：

- 自动验证全部通过。
- 远程 C host tests 全部通过。
- disabled boot2 和 observe boot2 已在真机通过。
- `disable.flag` 恢复路径已实测。
- 写入前 backup 可读且有恢复价值。
- PCTL 写失败、backup 失败、坏 token、重复 token 都不会消费 nonce。

Grant 最小写入通过标准：

- 使用 1 分钟的有效加时代码。
- 写入前创建 backup 文件。
- 今日限制按预期变化。
- Result 为成功。
- 成功后消费 nonce。
- Event log 记录本次写入。

Grant 拒绝用例通过标准：

- 重复代码、错误日期、错误 secret、超上限、unlimited guard 和可测 backup failure 均写出稳定 error result。
- PCTL 目标保持不变。
- 除非原始成功 grant 已消费 nonce，否则不消费 nonce。

Enforce 通过标准：

- Enforce 按设计启动或刷新 play timer。
- 写入仍然要求 backup。
- Results 保持结构化。
- `disable.flag` 仍会强制 fail-open。

Raw Block 与 Suspend Probe 规则：

- 仅在 grant/enforce 基础能力全部通过后运行。
- 每次只运行一种能力。
- 保持恢复路径可用。
- 记录人工观察结果。
- Probe 前普通 raw block/suspend 请求会被拒绝，probe 成功后才允许。

## 5. 恢复与回滚

禁用 sysmodule 行为：

1. 创建 `sdmc:/switch/play-time-control/flags/disable.flag`。
2. 必要时重启。
3. 如果需要完全停止 boot 行为，移除 `boot2.flag`。

清理 request 状态：

- 将卡在 `inbox/processing/` 的文件移回 `inbox/pending/`，或归档它们。
- 保留 `results/` 和 `logs/events.jsonl` 以便调试。

在后续 grant/enforce 阶段复核 PCTL 写入行为前，不要删除备份。
