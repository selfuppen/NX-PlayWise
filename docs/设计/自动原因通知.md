# 自动原因通知契约（实验）

采用短时原因通知与手动Overlay详情。通知说明刚发生的主要限制事件，不绘制实时倒计时，不获取输入焦点，不模拟组合键。限制、解除及所有家长控制事务仍由既有后台处理。

## 偏好与兼容性

`config.json`的可选布尔字段`reason_notifications_enabled`缺失或非true时关闭；新安装明确为false。家长在“安全与偏好 → 声音与通知”切换，保存失败恢复原开关。既有音效在同页独立切换，不控制第三方通知声音。完整备份和“界面偏好”选择恢复包含此字段，恢复缺字段的旧配置后关闭。

`reason_notification_language`保存已有NRO语言解析器最近解析出的`zh-Hans`、`zh-Hant`或`en`，属于同一偏好组。显式`ui_language`优先；跟随系统时后台使用此已保存解析值，缺失降级English。后台不新增语言服务或整个UI文案库；系统语言改变后需重开NRO刷新该解析值。通知文字使用共享的稳定`PTC_UI_T_NOTIFY_*`三语键。

只读`sdmc:/config/ultrahand/config.ini`的`[ultrahand] notifications`，true／false／缺失或非法分别显示开启／关闭／未知；任何值都不证明接收者驻留。只在开启时尝试实验发布。既有真机兼容证据仅覆盖Ultrahand 2.5.3 / loader 2.0.2原批二进制，不能外推所有版本或Tesla管理器。

读取`overlays.ini`的`[playwise.ovl] key_combo`，有效的2–4个不同已知按钮转换为真实组合（例如`L+DDOWN` → `L＋↓`）。未知、重复、过长或非默认launch_args模式降级“打开任我玩查看详情”，不借用NRO家长区快捷键。绝不自动修改第三方INI、全局通知开关、loader、OVL或启动项。偏好每秒最多读取一次，外部配置启用时每2秒最多读取一次；设置页进入时只读一次。

## 可靠观察与事件

`sysmodule_reason.c`只接收原Enforce成功观察并完成持久化后的状态；快路径读取失败、效果待确认、恢复／交接、未知官方开关／临时解锁／restricted_now、原因不明、跨日或处理已耗时2秒均不生成可靠事件。不额外建立PCTL会话或读取状态，不消费旧result文件。通知确认频率沿用原调度，不能承诺限制发生瞬间已识别。

可靠快照的主要原因顺序为当前已提交就寝实例、当前护眼break、已提交电视限制、明确耗尽的每日额度；每日在就寝／护眼时被屏蔽。这是单一主要原因，不是四个底层原因完整并发枚举。每日／电视实例绑定本地日，护眼绑定break ID，就寝绑定窗口实例。事件内存同时绑定当前release和后台boot，后台重开不回放历史队列。

首次启用后的新鲜可靠受限快照可以提醒当前实例；相同日／原因／实例去重。原因交接、解除后再受限、同日新break可再次提醒。常规尝试间隔至少10秒，期间合并最新原因；发布时快照须未满2秒，不能为等待限频给旧快照续期。时钟回拨、未知和旧身份保持保守，不发“可以玩”。

去重同时考虑已可靠观察到的原因交接，不能只比较最后一次尝试发布的实例。例如每日A→就寝B→每日A，B在10秒限频内没有发布，也不能把重新确认的A误作重复。等待期间只保留“仍有交接待合并”的内存意图；旧观察老化不能触发发布，也不更新观察时间。等既有策略处理再次提供新鲜可靠快照后，才尝试一次最新原因，不补发中间原因、不额外安排PCTL读取，因而不保证限频结束瞬间就有通知。未知观察、身份／时钟异常会取消待合并意图；进入详情或禁用时即使观察已老化，也会取消意图，离开详情不补播。

有效PlayWise输入owner租约或其读取未知会抑制通知；离开详情不补播已抑制的实例。租约只表示本项目实例的输入所有权，不能证明Ultrahand接收者状态。

## 文件、过期与失败

消费者目录为`sdmc:/config/ultrahand/notifications/`。每次使用唯一`playwise-reason-<16hex backend boot>-<16hex sequence>.notify`，进程中最多一份待消费文件。UTF-8 JSON固定字段：`title`、`text`、`font_size:26`、`duration:10000`、`show_time:"false"`（字符串）、`priority:30`。`pw_owner:"reason-v1"`、`pw_file`、`pw_release`、`pw_day`、`pw_reason`和十进制字符串`pw_instance`仅供本项目所有权与离线核验，旧接收者不会验证这些元数据。

先原子保存`support/reason-notification-owned.json`（file／payload），再完整写入非.notify的`.stage`文件，最后同目录更名。启动先验证持久记录的受限文件名、owner和原字节，清理上次自有待消费文件与stage。禁用、原因变化、未知、解除、正常交接或目标期限到同样清理；字节不匹配或读数未知保留现场，停止新发布。无通用目录清扫，不删除第三方文件。所有权检查与删除之间仍存在文件系统竞态，不能宣称条件删除的原子保证。

目标待消费窗口2秒，主循环约250ms提供清理机会，通知I/O在原控制锁外同步执行。SD阻塞、控制处理、后台异常退出和真实休眠均可越过目标；清理失败每10秒最多重试，累计5次I/O失败后本boot锁存停止新发布，保留所有权记录。存储恢复后可正常重开后台处理旧记录；未知所有权需先人工检查，不能盲删。

固定接收者约300ms扫描文件，读取后在内存保留内容，通常活动槽结束时才删原文件；通知关闭分支也会删文件。删除不能撤回已经复制的活动通知。duration是入槽后的显示参数，接收者队列、动画、浮窗切换或越界处理还可延长，不是从发布起算的端到端TTL。接收者缺席时只保证发布端尽力清理，不能保证异常窗口中没有旧消息补播。严格过期需另行设计、固定和分发接收端支持，本次不安装或升级第三方。

## 诊断与安全边界

`support/reason-notification.json`版本1为有界覆盖诊断，不是业务回执。状态包括`pending_display_unknown`、`expired_display_unknown`、`suppressed`、`write_failed`与`blocked_unknown_ownership`；最后一项也用于5次失败锁存。`display_confirmed:false`和`receiver:"unknown"`始终如实保留，不设delivered。包含release_id、backend_boot_id、day_index、reason、十进制字符串instance、captured_at、十进制字符串expires_mono_ms、sequence、io_failures与上一已完成旁路调用的io_max_ms。reason枚举稳定为0无、1每日、2就寝、3护眼、4电视。诊断写失败不改变原控制结果。

通知标题和正文只包含主要原因、实际详情入口；不包含PIN、secret、release或调试字段。通知状态不进入规则、恢复前像、消费、资格、nonce或业务ledger；不添加控制请求、线程、句柄或PCTL权限。默认关闭的实验能力不构成可靠全局通知或完整候选资格声明。
