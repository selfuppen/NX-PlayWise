# 自动原因通知契约（实验）

采用已加载自有Overlay自动详情优先、短时原因通知兜底。短通知不获取输入焦点；自动详情经既有Tesla前台路径取得输入归属，不模拟组合键。限制、解除及所有家长控制事务仍由既有后台处理。新增协作链已在源码实现，真机结果须绑定新候选，不能沿用37b0fc的25图作为新链通过。

## 偏好与兼容性

`config.json`的可选布尔字段`reason_notifications_enabled`缺失或非true时关闭；新安装明确为false。家长在“安全与偏好 → 声音与通知”切换，保存失败恢复原开关。既有音效在同页独立切换，不控制第三方通知声音。完整备份和“界面偏好”选择恢复包含此字段，恢复缺字段的旧配置后关闭。

`reason_notification_language`保存已有NRO语言解析器最近解析出的`zh-Hans`、`zh-Hant`或`en`，属于同一偏好组。显式`ui_language`优先；跟随系统时后台使用此已保存解析值，缺失降级English。后台不新增语言服务或整个UI文案库；系统语言改变后需重开NRO刷新该解析值。通知文字使用共享的稳定`PTC_UI_T_NOTIFY_*`三语键。

读取`sdmc:/config/ultrahand/config.ini`的`[ultrahand] notifications`，true／false／缺失或非法分别显示开启／关闭／未知；任何值都不证明接收者驻留。该开关只约束短通知兜底，不阻止已加载的自有浮窗详情。既有真机兼容证据仅覆盖Ultrahand 2.5.3 / loader 2.0.2原批二进制，不能外推所有版本或Tesla管理器。

读取`overlays.ini`的`[playwise.ovl] key_combo`，有效的2–4个不同已知按钮转换为真实组合（例如`L+DDOWN` → `L＋↓`）。未知、重复、过长或非默认launch_args模式降级“打开任我玩查看详情”，不借用NRO家长区快捷键。后台只读第三方配置；NRO仅在用户从关闭切到开启时准备全局通知键，详见下节。loader、OVL、启动项、快捷键和其他INI内容保持。后台偏好每秒最多读取一次，外部配置启用时每2秒最多读取一次。

这里读到的是SD卡上保存的配置，**不能证明驻留管理器已加载该组合**。键或节重复导致歧义、缺失、包含不支持的按钮、按钮重复或`use_launch_args`不为缺省／false时，使用通用入口提示。短通知中的入口始终供用户手动使用；识别组合键不参与自动详情唤起。

### setup与启用准备

setup第二步提供“声音与通知”入口，打开与已安装用户相同的三语设置页，默认关闭且可跳过。缺少可选接收者不阻止核心setup。先原子保存自有偏好，失败恢复开关且不写管理器。开启操作前说明将准备Ultrahand全局开关、影响其他软件通知。

仅对已有可读、唯一`[ultrahand]`节和唯一合法true／false的`notifications`键把false改为true，保留该值外的原字节（含换行、空白、注释和其他节）。读前像、写前再读比较、原子替换、完整回读比对；任何缺失、歧义或I/O失败显示依赖未就绪。保存成功、原本已开启都只证明SD配置；无驻留重载ACK，可能仍需正常重新打开管理器。`API notifications enabled.`是管理器自身切换全局接收时的提示，无需逐条手动启用。

不自动安装、换装或重启第三方组件，不注入长按MINUS。关闭自有提示不关闭全局开关，避免影响其他软件。备份恢复仍只恢复自有偏好，不恢复或改写第三方INI；若恢复为开启而接收配置关闭，可重新切换自有提示准备。修改前像与替换间仍有文件系统竞态，不能宣称跨进程条件替换原子性。

## 已加载自有浮窗的自动详情

固定vendored libtesla增加默认无操作的UI线程隐藏轮询及帧后回调，PlayWise使用250ms轮询。没有新服务、后台线程或产品HID注入。固定loader与管理器没有已证明的外部选择／打开指定Overlay接口；其他浮窗、管理器驻留或PlayWise已退出时不会自动装载PlayWise，直接尝试短通知兜底。Host sys-botbase仅为实验室通道。

只有曾取得有效状态、无未完成请求／兑换恢复／键盘／PIN／家长操作／语言选择／结果页的隐藏PlayWise，才在输入中立且自有偏好开启时发布`support/reason-detail-ready.json`，每秒续一次、有效1500ms。HOME或POWER事件后禁用自动唤起，直到下一次手动组合键；不能用该功能唤醒真实休眠。UI内的自动唤起成功不证明底层游戏已暂停。

后台在原可靠新事件上优先读取ready，核对release、backend boot、UI实例及期限，最多尝试一次`reason-detail-request.json`。请求有效2000ms，携带当前day、主要reason和限制instance、boot内sequence。没有就绪实例即尝试一次短通知；写入失败可能已发布，仍等待原期限，不立即重发或并发兜底。10秒限频及同实例去重覆盖整条详情／兜底尝试。

隐藏UI核对同一runtime、偏好、输入、页面和UI实例后，调用原show／输入归属路径，丢弃旧状态、提交一次普通status刷新并打开详情。帧完成且动画结束后，只在新鲜status与请求同日、同主要原因／实例，输入租约有效且原请求仍匹配时写`reason-detail-ack.json`。后台再核对完全相同请求元数据和当前runtime／可见owner租约，记录`detail_drawn_confirmed`。这是本项目绘制／输入链的软件确认，`display_confirmed:false`仍表示缺少独立物理画面结论。

两秒内未完成确认时，UI隐藏并释放输入；确认前只接受B退出，不开始PIN或编辑。后台最多再留500ms等待已释放owner的轮询缓存消退，请求本身不延长期限。超时且当前原因仍可靠、新鲜、未被owner抑制时，尝试一次短通知，不再次抢焦点；已有本项目可见owner、敏感页、未知／解除、禁用、时钟回退、原因交接、正常后台交接均不补播旧实例。原因交接后的新实例仍经过限频。自动打开后B按既有层级返回，根页B隐藏并释放输入；同实例不再自动重开，后续可靠新事件可再次提示。手动打开的根页B仍返回管理器。

三个协作文件均为严格JSON对象，version为整数1，kind为ready/request/ack；release、boot、owner为字符串，ui_instance、sequence、issued_ms、expires_ms、instance、day、reason为规范十进制字符串。ready的sequence／instance／reason为0且owner空，request事件字段非0且owner空，ack保留原请求所有字段并包含32位hex owner。boot为16位hex；重复键、溢出、未来签发、期限超过2000ms、错身份或已过期均拒绝。自有请求仅匹配所有元数据才移除；就绪／ACK文件保留最后快照但过期不使用，不扫描或清理其他文件。UI写失败累计5次后停止该UI实例的自动协作；后台详情写失败累计5次后仅保留通知兜底，原短通知故障预算保持。

## 可靠观察与事件

`sysmodule_reason.c`只接收原Enforce成功观察并完成持久化后的状态；快路径读取失败、效果待确认、恢复／交接、未知官方开关／临时解锁／restricted_now、原因不明、跨日或处理已耗时2秒均不生成可靠事件。不额外建立PCTL会话或读取状态，不消费旧result文件。通知确认频率沿用原调度，不能承诺限制发生瞬间已识别。

可靠快照的主要原因顺序为当前已提交就寝实例、当前护眼break、已提交电视限制、明确耗尽的每日额度；每日在就寝／护眼时被屏蔽。这是单一主要原因，不是四个底层原因完整并发枚举。每日／电视实例绑定本地日，护眼绑定break ID，就寝绑定窗口实例。事件内存同时绑定当前release和后台boot，后台重开不回放历史队列。

首次启用后的新鲜可靠受限快照可以提醒当前实例；相同日／原因／实例去重。原因交接、解除后再受限、同日新break可再次提醒。常规尝试间隔至少10秒，期间合并最新原因；发布时快照须未满2秒，不能为等待限频给旧快照续期。时钟回拨、未知和旧身份保持保守，不发“可以玩”。

去重同时考虑已可靠观察到的原因交接，不能只比较最后一次尝试发布的实例。例如每日A→就寝B→每日A，B在10秒限频内没有发布，也不能把重新确认的A误作重复。等待期间只保留“仍有交接待合并”的内存意图；旧观察老化不能触发发布，也不更新观察时间。等既有策略处理再次提供新鲜可靠快照后，才尝试一次最新原因，不补发中间原因、不额外安排PCTL读取，因而不保证限频结束瞬间就有通知。未知观察、身份／时钟异常会取消待合并意图；进入详情或禁用时即使观察已老化，也会取消意图，离开详情不补播。

有效PlayWise输入owner租约或其读取未知会抑制通知；离开详情不补播已抑制的实例。租约只表示本项目实例的输入所有权，不能证明Ultrahand接收者状态。

## 文件、过期与失败

消费者目录为`sdmc:/config/ultrahand/notifications/`。每次使用唯一`playwise-reason-<16hex backend boot>-<16hex sequence>.notify`，进程中最多一份待消费文件。UTF-8 JSON固定字段：`title`、`text`、`font_size:26`、`duration:10000`、`show_time:"false"`（字符串）、`priority:30`。`pw_owner:"reason-v1"`、`pw_file`、`pw_release`、`pw_day`、`pw_reason`和十进制字符串`pw_instance`仅供本项目所有权与离线核验，旧接收者不会验证这些元数据。

先原子保存`support/reason-notification-owned.json`（file／payload），再完整写入非.notify的`.stage`文件，最后同目录更名。启动先验证持久记录的受限文件名、owner和原字节，清理上次自有待消费文件与stage。禁用、原因变化、未知、解除、正常交接或目标期限到同样清理；字节不匹配或读数未知保留现场，停止新发布。无通用目录清扫，不删除第三方文件。所有权检查与删除之间仍存在文件系统竞态，不能宣称条件删除的原子保证。

目标待消费窗口2秒，主循环约250ms提供清理机会，通知I/O在原控制锁外同步执行。SD阻塞、控制处理、后台异常退出和真实休眠均可越过目标；清理失败每10秒最多重试，累计5次I/O失败后本boot锁存停止新发布，保留所有权记录。存储恢复后可正常重开后台处理旧记录；未知所有权需先人工检查，不能盲删。

固定接收者约300ms扫描文件，读取后在内存保留内容，通常活动槽结束时才删原文件；通知关闭分支也会删文件。删除不能撤回已经复制的活动通知。duration是入槽后的显示参数，接收者队列、动画、浮窗切换或越界处理还可延长，不是从发布起算的端到端TTL。接收者缺席时只保证发布端尽力清理，不能保证异常窗口中没有旧消息补播。严格过期需另行设计、固定和分发接收端支持，本次不安装或升级第三方。

## 诊断与安全边界

`support/reason-notification.json`版本1为有界覆盖诊断，不是业务回执。状态包括`pending_display_unknown`、`expired_display_unknown`、`suppressed`、`write_failed`与`blocked_unknown_ownership`；最后一项也用于5次失败锁存。`display_confirmed:false`和`receiver:"unknown"`始终如实保留，不设delivered。包含release_id、backend_boot_id、day_index、reason、十进制字符串instance、captured_at、十进制字符串expires_mono_ms、sequence、io_failures与上一已完成旁路调用的io_max_ms。reason枚举稳定为0无、1每日、2就寝、3护眼、4电视。诊断写失败不改变原控制结果。

通知标题和正文只包含主要状态、同轮观察的时间快照和实际详情入口；不包含PIN、secret、release或调试字段。通知状态不进入规则、恢复前像、消费、资格、nonce或业务ledger；不添加控制请求、线程、句柄或PCTL权限。默认关闭的实验能力不构成可靠全局通知或完整候选资格声明。

## 面向孩子的状态与时间通知

本节已在源码实现；新候选实际显示与P4仍须分别验收。正文为状态、时间、入口三段，维持26字号与原生命周期。实现、构建与真机状态见[调整记录](../开发/验收记录/2026-11/自动化与交互/自动原因通知状态时间实施记录-20261111.md)；[原交接](../开发/验收记录/2026-11/自动化与交互/自动原因通知文案与状态时间调整交接-20261111.md)保留接手时快照。

目标通知依次展示品牌标题、孩子能理解的当前主要状态、对应时间信息和手动详情入口。文案使用温和、明确的动作，例如“今天的游戏时间用完啦”“该睡觉啦”“让眼睛休息一下吧”“请连接电视继续玩”；避免“额度耗尽”“限制已生效”等管理术语。状态指整个主机的主要限制，不能误称已统计某款游戏。

| 主要状态 | 时间行要求与简体文案方向 |
| --- | --- |
| 每日时间用完 | 同轮可靠观察明确耗尽时显示“今天还可玩：0分钟”；负余额不展示负分钟，也不新增“马上恢复”承诺 |
| 护眼休息 | 同轮可靠break及截止时间可用时显示“休息还剩约N分钟（提醒时）”；自然到零仍须后台确认，不承诺到点一定能玩 |
| 就寝 | 可靠当前就寝实例及结束时间可用时显示“本次就寝还剩约N小时M分钟（提醒时）”；不能把就寝结束等同所有限制解除 |
| 电视模式 | 仅在同轮明确非电视余额耗尽时显示“非电视时间剩余：0分钟”；仅电视等其它触发条件以“连接电视后查看可玩时间”说明，不把电视要求换算成未知倒计时 |
| 时间字段不可用 | 主要原因仍可靠时显示“剩余时间待确认”，保留详情入口；不能从未知、过期结果、上次通知或计划推算补0。主要原因本身不可靠时仍不发布 |

剩余时间为**提醒时的快照**，不在接收端逐秒更新；有时长的行明确带“提醒时”。正剩余秒数向上取整为分钟，低于1分钟显示“不足1分钟”，取整、长时段和跨夜边界均须确定性回归。不同计数不能混用：本次休息／就寝剩余不等于今日可玩时间；不限时不能写成0或1440分钟。时间只从既有成功策略观察携带，不为通知新增PCTL读取、status请求或计时服务。若现有观察缺字段，先扩展该纯数据投影及测试，不能复用陈旧客户端结果。

详情入口保留实际保存的快捷键提示；非法配置保留“打开任我玩查看详情”。简体目标示例（示意数据）：

```text
任我玩
让眼睛休息一下吧
休息还剩约5分钟（提醒时）
L＋↓ 详情
```

提示框应比现有两行正文更大，完整容纳新增信息。先从固定接收者的自动测量、换行、宽高上限及允许字号验证能否通过内容增长；不臆造`width`／`height`字段，不通过缩小至难读字号满足验收，不未经授权升级接收者。正文保持26字号，按字宽与三语长文本验证换行／高度；四行示例不要求固定像素位置。外部管理器决定其主题与外框，本项目不能承诺完全控制尺寸。能力不足时记录准确缺口，保留可回归实现，不能伪称界面验收完成。

新正文及时间行需同步简体、繁体、英文；本项目设置与详情继续遵循双主题、语义色和动态测量规范。验证覆盖四类原因、未知／过期／跨日、多个限制、三语长文本、实际快捷键和通用入口、不裁字、不抢焦点，以及原因变化时旧快照可能仍短暂可见的边界。限频、2秒待消费目标、10000ms显示参数、默认关闭、手动打开及第三方只读边界保持现有契约。

### 时间投影与接收端容量

`PtcReasonObservation`携带同轮`time_kind`与`remaining_seconds`，各轮先重置为未知，不能继承上一条时间。就寝结束日绑定当前窗口起始日及是否跨夜，并扣除本地日内秒；护眼取已提交break截止值。发布时扣除观察至发布的0或1秒；达到截止只显示待确认，不显示解除。每日零仅来自已知耗尽，负数显示零；电视零须同日已知非电视用量达到正数配额且同轮已记录非电视模式，未知／仅电视要求使用连接电视说明。观察跨本地午夜即失效，即使墙钟年龄不足2秒。

固定接收端源码（原批封存的libultrahand commit `856ddbddd796fc4a59ad2e0bf939c5963e6f9dd2`）中`getEffectiveHeight`／`drawSlot`的带标题布局最多4行正文，宽448px、高为`88 + (行数-1) × (字体行高+3)`；图标待决时先保留88px列，实际正文换行宽329px，无图标396px。新增时间段让框自动增高，不新增width／height字段、不缩小字号。快捷键末尾缩短为“详情”／“詳情”／“Info”，保留真实组合与手动入口。

`test-notice-layout`直接调用生产正文格式器，用固定文档Noto字体测量三语、所有原因／时间种类、分钟边界、最长4键组合及通用入口，并覆盖329／396px和1.1倍字宽压力。它是内容容量模型，非接收端渲染器或Switch字体证明；`build/host/reason-notices.html`明确标注HOST PREVIEW / SAMPLE DATA。实际框高、无裁切、焦点和可见性须绑定新候选真机核验；其它通知挤占槽位仍可能使整框暂不绘制。

## 与后台空闲调度的协作

完整策略轮次继续使用到期探测与扫描退避；空闲唤醒不为通知重新加载规则、日历或读取PCTL，也不刷新观察revision与captured_at。通知旁路在控制锁外独立于完整轮次执行，保留约250ms的详情ACK检查、过期清理及交接停发机会；交接取消仍立即补一次完整轮次。通知配置沿用1秒缓存，外部管理器配置沿用2秒缓存，不能为追求新鲜观察恢复每次唤醒的完整策略处理。新鲜度不足时等待既有策略产生新观察，不补造时间。
