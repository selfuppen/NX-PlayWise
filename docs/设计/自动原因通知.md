# 自动原因通知契约（实验）

采用已加载自有 Overlay 自动详情优先、短时原因通知兜底。短通知不获取输入焦点；自动详情经既有 Tesla 前台路径取得输入归属，不模拟组合键。限制、解除及所有家长控制事务继续由既有后台处理；新增协作链的真机验收须绑定对应新候选。

## 偏好与兼容性

`config.json` 的可选布尔字段 `reason_notifications_enabled` 缺失或非 true 时关闭；新安装明确为 false。家长在“安全与偏好 → 游玩受限提醒”切换（聚焦该卡片时也可按 X 快捷切换），保存失败恢复原开关。此页面仅管理受限原因通知。完整备份和“界面偏好”选择恢复包含此字段，恢复缺字段的旧配置后关闭。

`reason_notification_language`保存已有NRO语言解析器最近解析出的`zh-Hans`、`zh-Hant`或`en`，属于同一偏好组。显式`ui_language`优先；跟随系统时后台使用此已保存解析值，缺失降级English。后台不新增语言服务或整个UI文案库；系统语言改变后需重开NRO刷新该解析值。通知文字使用共享的稳定`PTC_UI_T_NOTIFY_*`三语键。

后台与隐藏浮窗共用通知偏好解析，重复顶层键、非法 JSON 或读失败均关闭提醒。后台每次定期或 IPC 提前刷新仍读取当前配置，只有原文和上次成功解析的字节完全一致时复用结果。控制侧的元数据缓存不作为通知偏好的读取凭据。

读取`sdmc:/config/ultrahand/config.ini`的`[ultrahand] notifications`，true／false／缺失或非法分别显示开启／关闭／未知；任何值都不证明接收者驻留。该开关只约束短通知兜底，不阻止已加载的自有浮窗详情。简要提示的真机接收兼容证据限于 **Ultrahand 2.5.3 + nx-ovlloader 2.0.2** 的原批二进制和记录中的实测场景。 [接收对照记录](../开发/验收记录/2026-11/自动化与交互/3.1.8-beta.1简要提示未显示排查与合批复测-20261114.md)

**原版 Tesla 与 Ultrahand 版本边界**：
- **原版 Tesla（Tesla-Menu + nx-ovlloader）**：`playwise.ovl` 基于仓库固定 `WerWolv/libtesla` 构建，已加载并隐藏时的自动详情协作（`ready`/`request`/`accepted`/`ack` 与可选 IPC 唤醒）不检查 `[ultrahand] notifications`，代码路径上不依赖 Ultrahand，但尚未在原版 Tesla-Menu 上执行真机验收。相反，原版 Tesla-Menu 不具备 `.notify` 接收器与 `sdmc:/config/ultrahand/config.ini`；发布端（`sysmodule/reason_notification.c`）与测试通知入口（`companion/nro/nro_preferences.c`）均要求读到 `[ultrahand] notifications = true` 才写入 `.notify`，因此在原版 Tesla 环境下所有简要提示（含兜底短通知、护眼/就寝每分钟续报、任我玩自身驻留简要提示绘制及 NRO 测试按钮）均不会触发。
- **Ultrahand 上游版本基线**（2026-11-24 核对 [ppkantorski/Ultrahand-Overlay Releases](https://github.com/ppkantorski/Ultrahand-Overlay/releases)）：`v2.1.0` 首次引入 `/config/ultrahand/notifications/*.notify`，但仅支持 `text`/`font_size`/`priority`（且 `v2.1.7` 前存在隐藏文字透明问题）；`v2.3.0` 才补齐本项目发出的 `title`、`duration`、`show_time`、`priority`、`font_size` 全套 API Notifications 字段、带标题 4 行布局与 `MINUS`/触屏关闭；`v2.5.2` 修复通知对齐与翻译问题。因此简要提示协议最低门槛为 **Ultrahand `v2.3.0`**，实际源码核对（`libultrahand` `856ddbddd796fc4a59ad2e0bf939c5963e6f9dd2`）与真机实测推荐组合为 **Ultrahand `2.5.3` + `nx-ovlloader 2.0.2`**。

读取`overlays.ini`的`[playwise.ovl] key_combo`，有效的2–4个不同已知按钮转换为真实组合（例如`L+DDOWN` → `L＋↓`）。未知、重复、过长或非默认launch_args模式降级“打开任我玩查看详情”，不借用NRO家长区快捷键。后台只读第三方配置；NRO仅在用户从关闭切到开启时准备全局通知键，详见下节。loader、OVL、启动项、快捷键和其他INI内容保持。后台偏好开启时约每秒、关闭时约每5秒重读一次；外部配置（接收者开关与快捷键）不再周期读取，只在即将发布兜底短通知时读取，缓存期2秒。

这里读到的是SD卡上保存的配置，**不能证明驻留管理器已加载该组合**。键或节重复导致歧义、缺失、包含不支持的按钮、按钮重复或`use_launch_args`不为缺省／false时，使用通用入口提示。短通知中的入口始终供用户手动使用；识别组合键不参与自动详情唤起。

### setup与启用准备

setup第二步提供“游玩受限提醒”入口，打开与已安装用户相同的三语设置页，默认关闭且可跳过。缺少可选接收者不阻止核心setup。先原子保存自有偏好，失败恢复开关且不写管理器。开启操作前说明将准备Ultrahand全局开关、影响其他软件通知。

仅对已有可读、唯一`[ultrahand]`节和唯一合法true／false的`notifications`键把false改为true，保留该值外的原字节（含换行、空白、注释和其他节）。读前像、写前再读比较、原子替换、完整回读比对；任何缺失、歧义或I/O失败显示依赖未就绪。保存成功、原本已开启都只证明SD配置；无驻留重载ACK，可能仍需正常重新打开管理器。`API notifications enabled.`是管理器自身切换全局接收时的提示，无需逐条手动启用。

不自动安装、换装或重启第三方组件，不注入长按 MINUS。关闭自有提示保留全局开关，避免影响其他软件。备份恢复只恢复自有偏好，不改写第三方 INI；若恢复为开启而接收配置关闭，可重新切换自有提示以准备配置。修改前像与替换间存在极短的文件系统竞态窗口。

### 开机依赖探测与保守前置配置（阶段 A）

标准后台启动读取 `config.json` 后执行一次有界环境探测 `ptc_overlay_env_boot_reconcile`：通过 `PtcStorageVTable.read_range` 仅读取 `sdmc:/switch/.overlays/ovlmenu.ovl` 的 NRO0/ASET/NACP 头（识别 Ultrahand 与 Tesla-Menu 及语义版本号），检查 `sdmc:/atmosphere/contents/420000000007E51A/` 的 `exefs.nsp`、`flags/boot2.flag`、`toolbox.json` 版本与 `sdmc:/switch/.overlays/playwise.ovl`，并检测 Ultrahand 按应用静音标记 `sdmc:/config/ultrahand/flags/notifications/playwise.flag`（存在时后台跳过写入必被静默删除的 `.notify` 文件，状态记为 `fallback_receiver_muted`，NRO 设置页同步显示已静音并阻止测试通知）。

在已核实 **Ultrahand `>= 2.3.0`** 且 `[ultrahand]` 节省略 `notifications` 键时，按 Ultrahand 默认开启语义识别为 `1`（`notifications_implicit_default:true`）。后台开机自动校正直至同时满足：`reason_notifications_enabled == true`、已核实 `Ultrahand >= 2.3.0`、`nx-ovlloader` 与 `boot2.flag` 均存在且 `config.ini` 中存在唯一合法的 `notifications=false` 时，才以原字节保留方式将其翻转为 `true`；对关闭状态、原版 Tesla-Menu、旧版 Ultrahand（`< 2.3.0`）或缺失/歧义 INI 绝不改写。探测与动作结果写入有界诊断 `support/overlay-env.json`。

因 Atmosphère `boot2` 并发拉起 `nx-ovlloader`（0ms 延迟）与 PlayWise（启动延迟 15 秒），且 Ultrahand 仅在自身启动时读取一次 `config.ini`，开机修正 `config.ini` 不承诺当次开机已驻留的 Ultrahand 立即重载，须待下次重新打开 Ultrahand 或下次重启生效；本阶段开机探测与校正已在真机（`Ultrahand 2.5.3` + `nx-ovlloader 2.0.3`）完成验收。

### 可选实验：开机预加载自动详情（阶段 B）

`config.json` 新增默认关闭的可选布尔偏好 `reason_overlay_preload_enabled`（包含在配置备份与界面偏好恢复中，主开关 `reason_notifications_enabled` 关闭时强制视为关闭）。家长可在“游玩受限提醒”页按 `X` 或点按“详细说明”卡片右上胶囊显式切换。

开启时，在严格核实 `Ultrahand >= 2.3.0`（上游 `v2.2.8` 起支持 `boot_package.ini` `[on-boot]` 与 `open`）、`nx-ovlloader`、`boot2.flag` 及 `playwise.ovl` 后，仅在 `sdmc:/switch/.packages/boot_package.ini` 的唯一 `[on-boot]` 节内以显式边界标记维护 3 行受管块：

```ini
; playwise-preload-begin
open /switch/.overlays/playwise.ovl --pw-preload
; playwise-preload-end
```

写入与移除均执行前像校验、保留用户其他行与 CRLF/LF 原格式、原子替换与回读比对；遇到重复 `[on-boot]` 或损坏标记时拒绝修改并保留原文件。关闭开机预加载或关闭主开关时，仅移除该受管块（若文件只含 PlayWise 受管块则删除文件），`support/overlay-env.json` 同步记录 `ultrahand_boot_preload_supported`、`preload_state` 与 `boot_preload_action`。

`playwise.ovl` 收到 `--pw-preload` 启动参数时，经 `tesla.hpp` 抑制首次自动亮屏并进入隐藏驻留，先将 Ultrahand `open` 写入的 `in_overlay`/`to_packages` 瞬态标记清回 `false`，并将自动详情就绪状态标记为 `preloaded_hidden_`（允许在未人工手动呼出前由后台自动拉起详情；真机首次手动按组合键将直接打开任我玩而非 Ultrahand 列表，这是单槽 `nx-ovlloader` 下的显式权衡）。在儿童首页按 `B` 时按来源分流：自动弹出的详情页（`s_automatic_detail == true`）按 `B` 隐藏并保持驻留，继续响应后续自动弹出；手动打开的首页按 `B` 显式调用 `tsl::setNextOverlay("sdmc:/switch/.overlays/ovlmenu.ovl", "")` 并退出，卸载 `playwise.ovl` 并将单槽 `nx-ovlloader` 切回 `ovlmenu.ovl`（原版 Tesla-Menu 会直接弹出菜单；实测 Ultrahand 2.5.3 在 `in_overlay=false` 时以隐藏态接管并回到 HOME，再按一次全局组合键即可打开完整 Ultrahand 插件列表，无需改写第三方 `in_overlay` 状态；若想继续保持任我玩驻留而不切出，按浮窗组合键隐藏即可）。隐藏态按键抑制使用有界冷却与显式手动组合键门禁：`HOME` 立即隐藏清屏并冷却 3 秒（`HOME_COOLDOWN_NS = 3s`），`POWER` 立即隐藏清屏并冷却 8 秒（`POWER_COOLDOWN_NS = 8s`），同时在隐藏等待返回时以 `sleepJumpDetected`（单调时钟超出本次有界等待期限至少 3 秒）兜底识别跨休眠时钟跳变并顺延 8 秒唤醒静默窗；冷却期间无隐藏帧时单次休眠等待冷却结束（不唤醒真休眠、不空转），手动组合键可立即解除冷却打开浮窗，唤醒静默结束后自动恢复详情就绪。

设置页标题为“游玩受限提醒”，开关为“自动显示受限原因”。左侧“切换示例图”将浮窗说明／简要提示放入同一分段选择器及 16:9 静态示例组（浮窗覆盖左侧约 35%，简要提示位于左上）。右侧“示例说明”随选择联动；“提醒环境”和“检查与测试结果”保持真实检查状态，不因切换示例改变。底部“验证提醒”用编号 1、2 和连接箭头提示“先检查、后测试”的建议顺序（两者均可独立执行），选择“测试简要提示”时自动切换至简要提示示例。按钮、选择器与只读信息区共用几何，三语说明使用独立文本区域，返回按钮置于验证组外。

## 已加载自有浮窗的自动详情

### 可选 IPC 唤醒

标准后台通过现有 `pctc:u` 的可选命令 4 为匹配 release 和 boot 的会话提供只读唤醒事件，通过可选命令 5（`PTC_IPC_CMD_UPDATE_REASON_READY`）与命令 6（`PTC_IPC_CMD_QUERY_REASON_READY`）提供**零日常 SD 写入的内存就绪租约**，并通过可选命令 7（`PTC_IPC_CMD_REQUEST_WAKE_REASON_RECHECK`）支持**锁屏／休眠唤醒后受限详情自动重弹**（内置于游玩受限提醒开关，不新增独立子开关或系统服务权限）。隐藏浮窗在后台身份已知时主动探测连接 `pctc:u` 并订阅唤醒事件；订阅有效且不在 2 秒事件扫描窗内时，UI 线程空闲等待由 250ms 降至 1000ms（收到唤醒事件或手动组合键仍即时唤醒），每秒通过命令 5 在后台内存中续期 1500ms 就绪租约（0 字节 SD 写入），仅当 IPC 不可用或旧版后台不支持命令 5 时才回退写 `support/reason-detail-ready.json`。浮窗显示、关闭偏好、退出或 IPC 会话断开时后台立即清除内存租约；NRO“检查提醒环境”通过命令 6 优先读取内存租约并在无 IPC 时回退读 SD。事件在详情请求文件完整发布后触发，简要载荷仍在准备完成且尚未更名时触发。浮窗订阅成功或收到事件后在两秒扫描窗口中查找载荷，及时读取首次检查后才完成的写入；事件合并时仍分别扫描详情与原因 journal。无事件时保留每秒一次的两个文件审计，以覆盖漏唤醒和断线未被发现的情况。后台切换后在原身份刷新时失效旧订阅。

**锁屏／休眠唤醒后受限详情自动重弹**：隐藏驻留的 `playwise.ovl` 在主循环或 50ms 输入线程检测到真实内核挂起时钟跳变（`sleepJumpDetected`，覆盖 3 秒以上的短休眠与长休眠）时，复用现有 `set:sys` 会话单次只读查询 `setsysGetLockScreenFlag`（读取失败保守按开启锁屏处理，不使用 `ASSERT_FATAL`），记录唤醒时刻并设置单次 `wake_recheck_pending_`（45 秒窗口上限，手动呼出浮窗或关闭提醒立即清除）。当系统开启锁屏时，等待检测到唤醒后用户解锁输入并松手静默 0.8 秒，且距唤醒已满 2 秒（`WAKE_EARLY_MIN_NS = 2s`、`WAKE_UNLOCK_QUIET_NS = 0.8s`，允许唤醒 `POWER` 按键事件滞后内核恢复最多 2 秒 `WAKE_POWER_COOLDOWN_SKEW_NS = 2s`）即可提前解除 8 秒 `POWER` 冷却（绝不缩短 `HOME` 3 秒冷却）；当系统关闭锁屏时，须在 8 秒冷却结束后确认存在唤醒后真人输入或唤醒后 `POWER`/`HOME` 事件才放行，以屏蔽夜间黑屏暗唤醒。条件满足且输入中立、当前无可见浮窗或简要提示时，浮窗在续期内存 `ready` 租约后发送命令 7；后台立即唤醒执行一次常规 `enforce_request()`（不调用 `1451`）取得新鲜可靠的受限快照，对仍受限的同一实例单次豁免去重（带 15 秒同实例唤醒防抖 `PTC_REASON_WAKE_DEBOUNCE_MS`），仅走已加载浮窗自动详情路径（`detail_from_wake`），不触发 `.notify` 简要提示兜底；若休眠期间限制已解除、快照陈旧、存在可见 `input_owner` 或浮窗不再就绪，则静默放弃。

事件只让浮窗检查原 SD 记录，接收仍核对期限、抑制边界、身份、已发布原字节和详情 ACK 所有权。浮窗线程优先处理手动组合键及 HOME／POWER 门禁；显示和输入沿用原路径。测试通知 journal 继续由原500ms空闲轮询检查；即将显示新测试提示时如尚未检查原因 journal，补查一次以保留真实限制提示优先。后台为每个已订阅会话持有一个事件，断线或停止时释放；浮窗退出时释放自己的事件句柄。

### 可选环境探测与测试通知

setup 及已安装设置的“游玩受限提醒”提供“检查提醒环境”和“测试简要提示”，均可按 B 返回继续 setup。打开页面及点击探测有界读取当前 Ultrahand 配置、真实快捷键、`switch/.overlays/playwise.ovl` 文件元数据，以及与本 NRO release、后台 boot 及单调期限匹配的 ready 快照，不提交控制请求，不修改偏好或第三方 INI。ready 为读取时的短期快照，缺失、读失败、重复节／键及过期均保持未知／未就绪，不阻塞 setup。

“测试简要提示”独立于自动提示开关，仅在重新读取到全局通知配置为true时由用户单次触发。标题为“任我玩 · 测试提醒”，正文“这是一条测试提醒／游玩时间规则未改变”（三语对应）；不伪造受限事件、不改变PCTL、规则、nonce或ledger，也不抢占自动详情输入。页面仅报告发布成功或失败／未知，不以文件消失、配置或ready声称接收成功。没有看到时可正常重新打开管理器后重试，仍可跳过。

独立文件名为`playwise-test-<16hex随机标识>.notify`，`pw_owner:"test-v1"`，显示参数与普通短通知相同。先写`support/notification-test-owned.json`（严格两字段file/payload），再写`.stage`并更名；不覆盖已有文件。每个NRO最多一个待清理测试，两次尝试至少间隔10秒；主循环每100ms提供清理机会，目标2秒后仅删除文件名、所有权与完整原字节匹配的自有文件，退出及下次NRO启动尝试恢复清理。失败每10秒最多重试、累计5次停止本实例自动清理与新发布，保留未知现场。测试不等待接收ACK或人工确认，也不将失败写入setup状态。SD阻塞、异常退出或休眠仍可越过清理目标；删除不撤回管理器已经缓存的通知。

固定vendored libtesla增加默认无操作的UI线程隐藏轮询及帧后回调，PlayWise在自有偏好开启时使用250ms轮询，关闭时每5秒只检查一次偏好。没有新服务、后台线程或产品HID注入。固定loader与管理器没有已证明的外部选择／打开指定Overlay接口；其他浮窗、管理器驻留或PlayWise已退出时不会自动装载PlayWise，直接尝试短通知兜底。Host sys-botbase仅为实验室通道。

只有曾取得有效状态、无未完成请求／兑换恢复／键盘／PIN／家长操作／语言选择／结果页的隐藏PlayWise，才在输入中立且自有偏好开启时发布`support/reason-detail-ready.json`，每秒续一次、有效1500ms。ready仍先写临时文件、关闭后再替换；SD适配器省去这份短期提示的单独卷提交。中断后缺失或过期的ready按既有等待和兜底处理，详情request与ACK继续走原提交路径。短租约确保后台只向刚刚还中立的界面发出请求。隐藏界面缓存后台身份10秒，身份变化即重发ready，读失败每秒重试。HOME或POWER事件后禁用自动唤起，直到下一次手动组合键；不能用该功能唤醒真实休眠。UI内的自动唤起成功不证明底层游戏已暂停。

`support/reason-brief-receiver.json` 的可选 `hidden_timing` 版本 1 保存本次及上次隐藏轮询起点、最大已观察轮询间隔、输入中立标记、非中立轮询次数，以及最近两次 ready 签发／原子写入完成时间（最近一次同时记录开始时间、原租期和写入结果）。各毫秒值按单调时钟序列化为十进制字符串，时钟倒退或写入完成早于开始时 `clock_order_valid=false`。采集仅在内存中累计，沿用接收诊断的状态变化、每秒上限、32 次更新及 5 次失败预算落盘；正常隐藏时重置本段统计。旧快照缺字段时保持未知，具体失败原因需结合同候选／boot 的后台判定与原始附件核对。

可选`hidden_timing.reads`分别记录`config`、`runtime`及`request`阶段的`started_ms`、`completed_ms`、`max_elapsed_ms`十进制字符串和`attempted`／`read_ok`布尔值。config阶段包含配置读取与解析，runtime阶段包含身份读取、解析和缓存更新，request阶段包含提议读取与严格解析，各结果沿用实际调用结果。每次隐藏轮询重置当前阶段的起止与结果，保留该隐藏统计段的最大耗时。未执行的阶段为attempted=false、当前起止为0，旧最大值仍可保留。读取失败同样保存耗时。正常隐藏清空所有阶段统计，未开始即记录结束、起止倒退及跨轮询时钟倒退标记clock_order_valid=false。分阶段统计仍随原接收诊断的状态变化写出，读取本身及其门禁沿用现有路径。

后台在原可靠新事件上优先读取ready，核对release、backend boot、UI实例及期限，最多尝试一次`reason-detail-request.json`。请求接单窗口为2000ms，携带当前day、主要reason和限制instance、boot内sequence。没有就绪实例即尝试一次短通知；写入失败可能已发布，仍等待原期限，不立即重发或并发兜底。10秒限频及同实例去重覆盖整条详情／兜底尝试。

首次读取到身份匹配、原租期合法且已过期的ready时，后台可将当前新事件保留最多500ms，沿用既有250ms通知轮询重新读取续写租约。旧ready的过期年龄不限制这次等待机会，仍须绑定当前release／boot及合法原租期；旧ready只提供等待线索，新详情请求必须使用重新读到的新鲜租约。等待截止时间在本次事件内固定，新的策略revision及后续租约不会延长它。等待期间不消费事件、不写请求或简要通知，也不增加诊断落盘。续写租约仍须通过实际读取时的1500ms新鲜度与全部输入门禁，才可提出一次详情请求。等待到期后，当前新鲜可靠的限制观察可走原简要提示兜底。观察已老化时继续等待既有策略产生新鲜观察，不能凭旧快照发布。未知／解除、禁用、可见owner、原因或日期交接、停止及单调／墙钟回退均取消本次等待。缺失、未来、格式非法或身份不匹配的初次读取沿用原兜底路径，周期简要提示沿用原限频与去重规则。

隐藏UI核对同一runtime、偏好、输入、页面和UI实例后，先写入与请求匹配的 `reason-detail-accepted.json`，再复核请求仍在接单期内且未撤回。接单时刻起最多再给2000ms用于刷新与绘制，总计不超过4000ms。随后调用原show／输入归属路径，丢弃旧状态并在儿童首页发起一次普通status刷新。帧完成且动画结束后，仅当首页实际绘制本次新鲜status的主要原因、与请求同日同因同实例、输入租约有效且原请求仍匹配时写`reason-detail-ack.json`。待确认、倒计时到零或已经离开首页的帧不确认。后台再核对完全相同请求元数据和当前runtime／可见owner租约，记录`detail_drawn_confirmed`。这是本项目绘制／输入链的软件确认，`display_confirmed:false`仍表示缺少独立物理画面结论。

status摘要的`access_recovery_required`表示每日、就寝、护眼或电视规则需要提供解限入口，正常受限的孩子详情也会带此标记，不能把它当作拒绝详情ACK的条件。家长页、PIN／键盘及其它敏感页面继续由实际GUI状态在帧确认时排除；停用、官方临时解除或未知、错误日／原因／实例仍拒绝ACK。回归须经过真实回执序列化与摘要解析，不能只手工设置受限字段而遗漏派生标记。

接单后的两秒内未完成绘制时，UI隐藏并释放输入；确认前只接受B退出，不开始PIN或编辑。后台可留最多500ms供及时绘制的ACK落盘和已释放owner的轮询缓存消退。宽限期间仍拒绝过期绘制，不延长可见窗口。待绘制阶段按250ms节奏检查请求是否被撤回。待确认期间的旧观察不能发短提示，且只有浮窗本次打开后取得的新状态才可用于确认绘制。超时且当前原因仍可靠、新鲜、未被owner抑制时，尝试一次短通知，不再次抢焦点；已有本项目可见owner、敏感页、未知／解除、禁用、时钟回退、原因交接、正常后台交接均不补播旧实例。原因交接后的新实例仍经过限频。自动打开后B按既有层级返回，根页B隐藏并释放输入；同实例不再自动重开，后续可靠新事件可再次提示。成功确认显示后，浮窗说明没有固定自动关闭时限，沿用正常页面退出；护眼／就寝倒计时基于已有快照在本地扣除经过时间，不逐秒请求后台。儿童概览与详情在同一有效实例首次归零时各沿用同一去重标记，只提交一次普通status复查；重复绘制、刷新等待／失败不重提，PIN／键盘、家长操作及确认／结果页不触发该复查。归零仍显示待确认，只有新后台回执才能更新限制状态。手动打开的根页B仍返回管理器。

手动打开浮窗时，普通孩子页也停在儿童首页，消费本次打开后发出的普通 `status` 回执。首次加载沿用注册后的刷新，同一后台再次打开时单次刷新。PIN、加时码、家长页和待恢复交易优先保留原流程，受保护页面和上次打开的迟到回执不会接管页面。从首页按 `−` 或选中状态入口可主动打开独立详情。自动打开的首页按一次 `B` 隐藏并释放输入，手动打开的首页按 `B` 返回管理器。手动打开独立于自动提醒偏好和详情协作文件。

四个协作文件均为严格JSON对象，version为整数1，kind为ready/request/accepted/ack；release、boot、owner为字符串，ui_instance、sequence、issued_ms、expires_ms、instance、day、reason为规范十进制字符串。ready的sequence／instance／reason为0且owner空，request事件字段非0且owner空，accepted和ack保留原请求字段，另以规范十进制字符串stage_ms分别记录接单及绘制时刻。ack包含32位hex owner。旧格式ack可读，缺少绘制时刻时无法完成新协作。accepted使用短期提示的原子替换路径；请求及ACK保留卷提交。boot为16位hex；重复键、溢出、未来签发、期限超过2000ms、错身份或已过期均拒绝。自有请求仅匹配所有元数据才移除；就绪／接单／ACK文件保留最后快照但过期不使用，不扫描或清理其他文件。UI写失败累计5次后停止该UI实例的自动协作；后台详情写失败累计5次后仅保留通知兜底，原短通知故障预算保持。

## 可靠观察与事件

`sysmodule_reason.c`只接收原Enforce成功观察并完成持久化后的状态；快路径读取失败、效果待确认、恢复／交接、未知官方开关／临时解锁／restricted_now、原因不明、跨日或处理已耗时2秒均不生成可靠事件。不额外建立PCTL会话或读取状态，不消费旧result文件。通知确认频率沿用原调度，不能承诺限制发生瞬间已识别。

可靠快照的主要原因顺序为当前已提交就寝实例、当前护眼break、已提交电视限制、明确耗尽的每日额度；每日在就寝／护眼时被屏蔽。这是单一主要原因，不是四个底层原因完整并发枚举。每日／电视实例绑定本地日，护眼绑定break ID，就寝绑定窗口实例。事件内存同时绑定当前release和后台boot，后台重开不回放历史队列。

首次启用后的新鲜可靠受限快照可以提醒当前实例；相同日／原因／实例去重。原因交接、解除后再受限、同日新break可再次提醒。常规尝试间隔至少10秒，期间合并最新原因；发布时快照须未满2秒，不能为等待限频给旧快照续期。时钟回拨、未知和旧身份保持保守，不发“可以玩”。

去重同时考虑已可靠观察到的原因交接，不能只比较最后一次尝试发布的实例。例如每日A→就寝B→每日A，B在10秒限频内没有发布，也不能把重新确认的A误作重复。等待期间只保留“仍有交接待合并”的内存意图；旧观察老化不能触发发布，也不更新观察时间。等既有策略处理再次提供新鲜可靠快照后，才尝试一次最新原因，不补发中间原因、不额外安排PCTL读取，因而不保证限频结束瞬间就有通知。未知观察、身份／时钟异常会取消待合并意图；进入详情或禁用时即使观察已老化，也会取消意图，离开详情不补播。

有效PlayWise输入owner租约或其读取未知会抑制通知；离开详情不补播已抑制的实例。租约只表示本项目实例的输入所有权，不能证明Ultrahand接收者状态。

后台每次实际检查通知抑制时，直接有界读取 `handover/runtime-ready.json` 并校验 release 与 boot。正常读取省去前置元数据查询。打开报文件不存在时再查询元数据确认缺失，读取错误、类型不符或格式异常仍按未知处理。两个租约槽仍按原路径、绝对期限和可见性核验。NRO 实体输入、Overlay 输入和详情 ACK 独立核验身份。

护眼／就寝仍为同日、同主要原因及同实例，且同轮可靠剩余时间为正时，最近一次尝试满60000ms后可补一次**简要提示**。补充提示只消费新的策略观察revision，快照仍须未满2秒且没有跨本地午夜；相同revision即使仍新鲜也不能启动周期提示。护眼剩余上限3600秒、就寝上限86400秒，未知／归零／越界不补播。每日耗尽和电视原因不周期重复。每次尝试后重新等待完整一分钟，写入失败或接收配置未就绪也不立即补发；既有10秒常规限频、所有权、2秒待消费目标和失败预算不变。

周期提示不读取自动详情 ready、不抢焦点；可见输入 owner、偏好关闭、未知身份／时钟异常会抑制并重置一分钟等待。离开详情后需等待至少一分钟及新的可靠策略观察，不重放被抑制的消息。重复计时只保留内存截止值，不新增 PCTL 会话、status 请求、定时器服务、线程或周期 SD 读取；受策略观察延迟、存储繁忙或接收者不可用影响，实际触发间隔可能大于一分钟或未显示。

## 文件、过期与失败

消费者目录为`sdmc:/config/ultrahand/notifications/`。每次使用唯一`playwise-reason-<16hex backend boot>-<16hex sequence>.notify`，进程中最多一份待消费文件。UTF-8 JSON固定字段：`title`、`text`、`font_size:26`、`duration:10000`、`show_time:"false"`（字符串）、`priority:30`。`pw_owner:"reason-v1"`、`pw_file`、`pw_release`、`pw_day`、`pw_reason`和十进制字符串`pw_instance`仅供本项目所有权与离线核验，旧接收者不会验证这些元数据。

先原子保存 `support/reason-notification-owned.json`（file／payload），再完整写入非 `.notify` 的 `.stage` 文件，最后同目录更名。启动先验证持久记录的受限文件名、owner 和原字节，清理上次自有待消费文件与 stage。禁用、原因变化、未知、解除、正常交接或目标期限到同样清理；字节不匹配或读数未知保留现场并停止新发布。无通用目录清扫，不删除第三方文件；所有权检查与删除之间存在极短的文件系统竞态窗口。

目标待消费窗口2秒，主循环约250ms提供清理机会，通知I/O在原控制锁外同步执行。SD阻塞、控制处理、后台异常退出和真实休眠均可越过目标；清理失败每10秒最多重试，累计5次I/O失败后本boot锁存停止新发布，保留所有权记录。存储恢复后可正常重开后台处理旧记录；未知所有权需先人工检查，不能盲删。

固定接收者约300ms扫描文件，读取后在内存保留内容，通常活动槽结束时才删原文件；通知关闭分支也会删文件。删除不能撤回已经复制的活动通知。duration是入槽后的显示参数，接收者队列、动画、浮窗切换或越界处理还可延长，不是从发布起算的端到端TTL。接收者缺席时只保证发布端尽力清理，不能保证异常窗口中没有旧消息补播。严格过期需另行设计、固定和分发接收端支持，本次不安装或升级第三方。

## 任我玩驻留时的简要提示接收

任我玩已加载并隐藏时，在现有 UI 线程接收自有简要提示。接收器只读取两个自有 journal 指定的已发布文件，核对唯一 JSON 键、受限文件名、所有权及完整载荷原字节。原因提示另核对实际后台 boot 和 release。发布端附带规范十进制字符串 `pw_issued_ms` 与 `pw_expires_ms`，期限为同一设备单调时钟上的两秒。接收器只接受期限内的载荷，缺失、未来、过期或溢出时保持未显示。历史载荷仍由原发布端所有权恢复路径清理。

接收后仅缓存一条文字，使用现有 framebuffer、26 字号、动态测量换行及当前浮窗主题绘制左上卡片，十秒后清屏并释放文字。高度超过可用画布时拒绝绘制。隐藏卡片不调用前台请求或输入 owner 获取，原游戏输入继续传递。短按 MINUS 清除自有缓存，输入仍沿原通道传递。文件与 journal 清理由原发布端负责。

进入详情、敏感页面、关闭自有偏好、HOME／POWER 抑制或单调时间回退时清除缓存。抑制期间及首次恢复允许的采样轮次都不读取两份 journal。后续检查仅接受严格晚于恢复采样时刻签发的原因和测试载荷，包括拒绝同毫秒签发的载荷。发布端先签发再更名，因此恢复后才完成更名的旧载荷也不会补播。后台 boot 变化不取消这一时间边界，原因载荷仍须匹配当前身份。单调时钟回退时至少等待到已观察的最高时间，再按恢复时刻重新建立边界。

隐藏显示期间继续以50ms检查到期和按键，只有提示出现、替换或清屏时才提交帧。实际受限提示与详情协作沿用250ms节奏。隐藏空闲且允许接收时，手动测试提示的所有权记录按500ms检查一次。已有提示或手动按 MINUS 关闭时，仍在允许接收的轮次检查并消费匹配的已发布文件。已消费的文件名跳过重复载荷解析，新消息仍核对身份、期限及原字节。关闭偏好后的稳定隐藏期只检查偏好。HOME／POWER 清屏后继续等待手动快捷键。第三方管理器仍按其自身接收路径处理通知，旧接收者可以忽略期限字段。

原生限制画面可能以全屏遮罩覆盖简要提示。卡片内的位置和文字布局只能改善未被遮罩的画面，实际可读性需核对原生限制与简要提示同屏的真机截图。该接收路径需要新候选的真实显示、游戏输入和生命周期验证。Host 回归覆盖真实发布器载荷、原字节变化、身份失配、过期文件、抑制退出、手动关闭、十秒期限与原清理所有权。

自动详情写入累计五次失败后停止该写入协作，隐藏简要接收继续按只读节奏核对偏好和后台身份。后台 boot 变化清除旧缓存。HOME／POWER 事件唤醒原 UI 事件，仅执行受抑制的隐藏清屏回调，再返回阻塞等待，手动快捷键沿原路径解除抑制。

`support/reason-brief-receiver.json` 版本 1 记录当前驻留接收状态，字段包括 `release_id`、`boot_id`、十进制字符串 `ui_instance` 与 `sampled_mono_ms`、`automatic_enabled`、`runtime_known`、`home_power_blocked`、`detail_io_failures`、`brief_active`、`reason_file`、`test_file`、`update_count` 和固定 false 的 `display_confirmed`。仅在状态或已消费文件变化时覆盖，每秒至多一次、每个浮窗进程最多 32 次成功更新，5 次诊断写入失败后停写；关闭偏好且尚未采样时不写。诊断写入失败不影响接收，画面实际可见性需结合绑定截图确认。

## 诊断与安全边界

`support/reason-notification.json` 版本 1 为有界覆盖诊断，包含 `pending_display_unknown`、`expired_display_unknown`、`suppressed`、`write_failed` 与 `blocked_unknown_ownership`（兼用于 5 次失败锁存）。`display_confirmed:false` 和 `receiver:"unknown"` 保持不变。字段含 `release_id`、`backend_boot_id`、`day_index`、`reason`、十进制字符串 `instance`、`captured_at`、十进制字符串 `expires_mono_ms`、`sequence`、`io_failures` 与上一已完成旁路调用的 `io_max_ms`；`reason` 枚举为 0 无、1 每日、2 就寝、3 护眼、4 电视。诊断写失败不影响控制结果。

通知标题和正文只含主要状态、同轮观察的时间快照和详情入口，不含 PIN、secret、release 或调试字段；通知状态独立于规则、恢复前像、消费、资格、nonce 和业务 ledger，不新增控制请求、线程、句柄或 PCTL 权限。

诊断附带`detail_decision`版本1，记录最近一次详情选择。`available`为false时其余字段保留零值。有效快照绑定同一后台release／boot及该次`decision_ms`、`day_index`、`reason`和`instance`，包含`repeat`、当时累计写失败数`failures`、`ready_read_attempted`、`ready_read_ok`、`ready_release_match`、`ready_boot_match`、`ready_fresh`、`ready_ui_instance`、`ready_issued_ms`、`ready_expires_ms`、`clock_budget_available`与`sequence_available`。所有毫秒、实例和序号使用规范十进制字符串，枚举与失败数使用JSON整数，判断字段使用JSON布尔值。ready读取成功时，元数据保存实际读取的原租期，再按原路径生成有效2000ms的详情提议。读取失败时匹配、新鲜度及ready元数据均为false或零。重复提醒和五次详情写入失败门禁仍在ready读取前执行。

后台结果附带 `detail_accepted_ms` 与 `detail_draw_deadline_ms`，为十进制字符串，没有有效接单时写入零。快照随现有诊断状态写入，新的选择即使状态名相同也更新一次。其它状态变化保留最近选择及其身份，兜底和ACK阶段沿用该快照。诊断文本超过固定容量时放弃该次诊断写入。该记录覆盖后台实际判定输入，画面可见性和详情绘制确认仍须分别核验。

## 面向孩子的状态与时间通知

本节已在源码实现；新候选实际显示与P4仍须分别验收。正文为状态、时间、入口三段，维持26字号与原生命周期。实现、构建与真机状态见[调整记录](../开发/验收记录/2026-11/自动化与交互/自动原因通知状态时间实施记录-20261111.md)；[原交接](../开发/验收记录/2026-11/自动化与交互/自动原因通知文案与状态时间调整交接-20261111.md)保留接手时快照。

目标通知依次展示品牌标题、孩子能理解的当前主要状态、对应时间信息和手动详情入口。文案使用温和、明确的动作，例如“今天的游戏时间用完啦”“该睡觉啦”“让眼睛休息一下吧”“请连接电视继续玩”；避免“额度耗尽”“限制已生效”等管理术语。状态指整个主机的主要限制，不能误称已统计某款游戏。

| 主要状态 | 时间行要求与简体文案方向 |
| --- | --- |
| 每日时间用完 | 同轮可靠观察明确耗尽时显示“今天还可玩：0分钟”；负余额不展示负分钟，也不新增“马上恢复”承诺 |
| 护眼休息 | 同轮可靠break及截止时间可用时显示“休息还剩约N分钟（提醒时）”；自然到零仍须后台确认，不承诺到点一定能玩 |
| 就寝 | 可靠当前就寝实例及结束时间可用时显示“本次就寝还剩约N小时M分钟（提醒时）”；不能把就寝结束等同所有限制解除 |
| 电视模式 | 仅在同轮明确非电视余额耗尽时显示“非电视时间剩余：0分钟”；仅电视等其它触发条件以“连接电视后查看可玩时间”说明，不把电视要求换算成未知倒计时 |
| 时间字段不可用 | 主要原因仍可靠时显示“剩余时间待确认”，保留详情入口；不能从未知、过期结果、上次通知或计划推算补0。主要原因本身不可靠时仍不发布 |

剩余时间为**提醒时的快照**，不在接收端逐秒更新；有时长的行明确带“提醒时”。正剩余秒数向上取整为分钟，低于1分钟显示“不足1分钟”，取整、长时段和跨夜边界均须确定性回归。不同计数不能混用：本次休息／就寝剩余不等于今日可玩时间；不限时不能写成0或1440分钟。时间只从既有成功策略观察携带，不为通知新增PCTL读取、status请求或计时服务。若现有观察缺字段，先扩展该纯数据投影及测试，不能复用陈旧客户端结果。

详情入口保留实际保存的快捷键提示；非法配置保留“打开任我玩查看详情”。简体目标示例（示意数据）：

```text
任我玩
让眼睛休息一下吧
休息还剩约5分钟（提醒时）
L＋↓ 详情
```

提示框应比现有两行正文更大，完整容纳新增信息。先从固定接收者的自动测量、换行、宽高上限及允许字号验证能否通过内容增长；不臆造`width`／`height`字段，不通过缩小至难读字号满足验收，不未经授权升级接收者。正文保持26字号，按字宽与三语长文本验证换行／高度；四行示例不要求固定像素位置。外部管理器决定其主题与外框，本项目不能承诺完全控制尺寸。能力不足时记录准确缺口，保留可回归实现，不能伪称界面验收完成。

新正文及时间行需同步简体、繁体、英文；本项目设置与详情继续遵循双主题、语义色和动态测量规范。验证覆盖四类原因、未知／过期／跨日、多个限制、三语长文本、实际快捷键和通用入口、不裁字、不抢焦点，以及原因变化时旧快照可能仍短暂可见的边界。限频、2秒待消费目标、10000ms显示参数、默认关闭、手动打开及第三方只读边界保持现有契约。

### 时间投影与接收端容量

`PtcReasonObservation`携带同轮`time_kind`与`remaining_seconds`，各轮先重置为未知，不能继承上一条时间。就寝结束日绑定当前窗口起始日及是否跨夜，并扣除本地日内秒；护眼取已提交break截止值。发布时扣除观察至发布的0或1秒；达到截止只显示待确认，不显示解除。每日零仅来自已知耗尽，负数显示零；电视零须同日已知非电视用量达到正数配额且同轮已记录非电视模式，未知／仅电视要求使用连接电视说明。观察跨本地午夜即失效，即使墙钟年龄不足2秒。

固定接收端源码（原批封存的libultrahand commit `856ddbddd796fc4a59ad2e0bf939c5963e6f9dd2`）中`getEffectiveHeight`／`drawSlot`的带标题布局最多4行正文，宽448px、高为`88 + (行数-1) × (字体行高+3)`；图标待决时先保留88px列，实际正文换行宽329px，无图标396px。新增时间段让框自动增高，不新增width／height字段、不缩小字号。快捷键末尾缩短为“详情”／“詳情”／“Info”，保留真实组合与手动入口。

`test-notice-layout`直接调用生产正文格式器，用固定文档Noto字体测量三语、所有原因／时间种类、分钟边界、最长4键组合及通用入口，并覆盖329／396px和1.1倍字宽压力。它是内容容量模型，非接收端渲染器或Switch字体证明；`build/host/reason-notices.html`明确标注HOST PREVIEW / SAMPLE DATA。实际框高、无裁切、焦点和可见性须绑定新候选真机核验；其它通知挤占槽位仍可能使整框暂不绘制。

## 与后台空闲调度的协作

完整策略轮次继续使用到期探测与扫描退避；空闲唤醒不为通知重新加载规则、日历或读取PCTL，也不刷新观察revision与captured_at。通知旁路在控制锁外独立于完整轮次执行；启用通知且已有可靠受限观察时才检查可见输入所有权。主循环只在存在待清理通知、待确认详情或尚未处理完的受限变化时保留250ms轮询，这些状态下仍保留原有的详情ACK检查、过期清理及交接停发机会；空闲时回到普通1000ms上限，交接取消仍立即补一次完整轮次。通知配置无论开关状态都每5秒重读，IPC通知提前刷新，外部管理器配置只在即将发布兜底通知时按2秒缓存读取，不能为追求新鲜观察恢复每次唤醒的完整策略处理。新鲜度不足时等待既有策略产生新观察，不补造时间。
