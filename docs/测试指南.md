# 测试指南

本文档是项目测试入口。所有改动先用 host 自动验证证明协议、队列、结果和安全 package 行为，再进入远程 devkitPro 构建、模拟器辅助验证和真实 Switch 分阶段验证。

## 1. 可自动验证

### 1.1 本地一键自动验证

Windows 10 / PowerShell：

```powershell
python .\tools\verify_auto_tests.py
```

预期输出形态：

```text
[RUN ] existing Python regressions
[PASS] existing Python regressions
[RUN ] host protocol probe
[PASS] host protocol probe
[RUN ] safe package layout
[PASS] safe package layout
[RUN ] boot2 packaging guard
[PASS] boot2 packaging guard
summary: 4/4 automatic verification steps passed
```

该脚本无第三方依赖，不要求真实 Switch、模拟器或 devkitPro。它会使用临时目录完成以下断言：

- 运行 `tests/mvp/test_token_v1.py` 和 `tests/observe/test_observe_queue.py`。
- 运行 `tests/frontend/test_ptc_frontend_server.py`，覆盖 PC 本地 Web 后端的 request 创建、result/布局摘要、`disable.flag` 和 package zip 预检/安装保护。
- 执行 `protocol_probe init -> grant_code -> offline_code/status request -> process-observe`。
- 校验 result 为 `status: ok`、`mode: observe`、`dry_run: true`。
- 校验 request 已从 `inbox/pending/` 归档到 `inbox/done/`。
- 校验 observe 模式不创建 `ledger/used_nonces.jsonl`，即不消费 nonce。
- 生成 safe SDMC package 和 zip，校验目录完整、`control_mode=observe`、zip 顶层为 `switch/`。
- 校验 safe package 不包含 `boot2.flag`。
- 校验 `package_sdmc.py --boot2` 在缺少 `--sysmodule-exefs` 时失败，避免生成空 boot2 包。

失败时脚本会打印失败步骤、命令、stdout 和 stderr。成功时只输出 PASS 汇总。

### 1.2 拆分运行

调试具体失败时可以拆开运行：

```powershell
python .\tests\mvp\test_token_v1.py
python .\tests\observe\test_observe_queue.py
python .\tests\frontend\test_ptc_frontend_server.py
```

预期输出：

```text
MVP token v1 tests passed
Observe queue tests passed
```

常用 host probe 命令如下；一键脚本已经覆盖这些路径，手工运行主要用于排查：

```powershell
python .\tools\protocol_probe.py init `
  --root .\.tmp\sdmc-observe `
  --device kid-switch `
  --secret replace-with-long-random-secret

python .\tools\grant_code.py `
  --minutes 30 `
  --device kid-switch `
  --secret replace-with-long-random-secret `
  --date 2026-07-10 `
  --nonce 4660

python .\tools\protocol_probe.py request `
  --root .\.tmp\sdmc-observe `
  --type offline_code `
  --code <CODE>

python .\tools\protocol_probe.py process-observe `
  --root .\.tmp\sdmc-observe `
  --day-index 2382
```

`2026-07-10` 对应 day index `2382`；`2380` 是 `2026-07-08` 的测试值，不要在真机当天测试中照抄。真实 Switch 测试时优先使用 `--date <东八区日期 YYYY-MM-DD>`，或在 PC 日期也按东八区当天显示时省略日期参数。

Switch 端 token 校验固定以东八区计算 day index，和 Web / CLI 的 `--date` 含义一致。若旧构建在北京时间午夜后、UTC 日期仍是前一天时把当天 token 判为 `wrong_date`，应更新 sysmodule 后重新构建 boot2 package；例如北京时间 `2026-07-12 00:12` 的东八区日期 day index 是 `2384`，不能按 UTC 仍算作 `2383`。

手工为 Companion 测试生成匹配 result 时：

```powershell
python .\tools\make_result.py `
  --root .\.tmp\sdmc-observe `
  --request-id <REQUEST_ID> `
  --status ok `
  --day-index 2381
```

`make_result.py` 只写 `results/<request_id>.json`，不会移动 `inbox/pending/` 里的 request；完整队列处理仍使用 `protocol_probe.py process-observe`。

### 1.3 当前 C Host 覆盖

`tools/verify_auto_tests.py` 不编译或运行 C host 测试；它只覆盖 Python 回归、host protocol probe 和 package 安全规则。C host 覆盖需要远程环境，应使用专门脚本通过 SSH 执行：

```powershell
python .\tools\verify_c_host_tests.py
```

预期输出形态：

```text
[RUN ] remote C host core
[PASS] remote C host core
summary: 1/1 C host verification steps passed
```

该脚本会通过 SSH 访问 `249-nintendo-switch-dev`，进入 `/ws/switch-play-time-control-local`，快进到 `origin/master` 后执行 `make test-host`，并校验输出包含 `C host core tests passed`。远程仓库不会自动同步本地未提交改动；需要验证本地改动时，先提交并推送 `master`。

只有在本机有可用 C 编译器并需要调试脚本时，才使用本地模式：

```powershell
python .\tools\verify_c_host_tests.py --local
```

`tests/c/test_host_core.c` 当前覆盖：

- C token v1 与 Python fixture 一致。
- HMAC 校验、错密钥、错日期、重复 nonce、超上限。
- day index、weekday 和跨天 bedtime。
- 错误 reason 映射。
- observe dry-run 策略。
- observe 离线码 dry-run 在 PCTL 当前报告 unrestricted 时仍返回 ok 且不消费 nonce。
- grant 写入策略、backup gate 和 nonce 消费。
- grant 写入模式在 `allow_unlimited_to_limited=false` 且 PCTL 当前报告 unrestricted 时返回 `unlimited_not_allowed` 且不消费 nonce。
- raw block capability gate。
- `disable.flag` 优先级。
- status request pending -> processing -> done -> result。
- grant request 调用 `pctl_stub` 并写 backup/ledger。
- backup failure 阻止 PCTL 写入且不消费 nonce。
- stuck processing request 恢复。
- C 侧 request schema parser 和 result schema validator。
- `observe` 下规则请求保持 dry-run，不写 rules/state/capabilities，不触碰 PCTL。
- `grant` 下今日规则、周模板、bedtime、limit action、parent unlock、probe capability 的成功/失败路径。
- `probe_play_timer_write` 成功后才允许 grant/enforce 真实写入；探针前不会写入，未触发无限制保护时返回 `pctl_write_not_verified`，无限制保护触发时优先返回 `unlimited_not_allowed`。
- `enforce` tick 只在目标变化时写入，`disable.flag` 下不触碰 PCTL。
- PCTL write failure、result write failure 和 ledger append failure 不提前消费 nonce。
- request queue 文件路径拼接长度检查。

仍需补充：

- PCTL read failure 的更多 result 断言。
- 更细粒度 storage failure 的可恢复路径。
- Switch `fs_storage`、time provider 和 PCTL adapter 的真机行为验证。
- Companion 家长区/PIN 流程的 UI 层测试。

## 2. 远程 devkitPro 自动构建验证

C host、Companion NRO、sysmodule NSP 和 package 生成的权威验证默认走远程 devkitPro 容器。本机缺少 `make`、`gcc` 或 WSL 发行版不是跳过 C host 验证的理由。

远程信息：

```text
SSH alias: 249-nintendo-switch-dev
remote path: /ws/switch-play-time-control-local
branch: master
```

远程不会自动同步本地工作区。涉及 C 代码、Makefile、NRO、sysmodule 或 package 的改动，应先本地运行快速验证、提交并推送 `master`，再让远程仓库快进拉取。

完整远程验证应使用脚本自动运行并检查构建产物：

```powershell
python .\tools\verify_devkitpro_build.py
```

预期输出形态：

```text

[PASS] remote devkitPro build
[RUN ] remote build artifacts
[PASS] remote build artifacts
[RUN ] download remote package zips
[PASS] download remote package zips
summary: 3/3 devkitPro verification steps passed
```

脚本默认通过 SSH 访问 `249-nintendo-switch-dev`，进入 `/ws/switch-play-time-control-local`，快进到 `origin/master` 后运行完整构建目标，并验证：

- C host core 和 Python 回归通过。
- `build/switch/pctc.nro` 存在。
- `build/switch/exefs.nsp` 存在。
- `build/packages/safe` 和 `build/packages/observe` 不包含 `boot2.flag`。
- `build/packages/safe-nro-<YYYYMMDD-HHMMSS>.zip` 包含 Companion NRO 且不包含 `boot2.flag`。

## 3. 需要手动验证

### 3.1 模拟器辅助验证

Ryujinx/Eden 等 Switch 模拟器可在 Windows 10 上降低 Companion NRO 文件协议测试风险，但模拟器结论不能替代真机系统能力验证。

模拟器可验证：

- Companion NRO 是否启动。
- 输入、菜单、隐藏家长区入口、PIN 初始化/校验、软键盘和超时显示。
- request JSON 是否写入模拟器 SD 卡的 `switch/play-time-control/inbox/pending/`。
- 使用 `tools/make_result.py` 或 host `process-observe` 写出 result 后，NRO 是否读取并展示匹配 result。
- 家长区 UI 中今日规则、周模板、bedtime、limit action、parent unlock、probe 和 `disable.flag` 操作是否写出预期 request type 或文件。

模拟器不可声明验证：

- Atmosphere boot2 sysmodule 自动启动。
- Nintendo PCTL IPC。
- play timer 真实读写。
- raw block。
- suspend。
- 真机恢复路径。

推荐模拟器流程：

1. 运行 `python .\tools\verify_devkitpro_build.py --install-safe-nro`，远程构建最新 safe NRO zip 并解压到 Eden 模拟器 SD 根目录。
2. 如需手工排查，也可先远程构建 `safe-nro-<YYYYMMDD-HHMMSS>.zip`，再将 safe NRO package 解压或挂载到模拟器 SD 卡根目录。
3. 另开 PowerShell 启动 PC 本地 Web 辅助界面：

   ```powershell
   python .\tools\ptc_frontend_server.py
   ```

4. 浏览器打开 `http://127.0.0.1:8765`，在 `SDMC root` 填入模拟器 SD 根目录，例如 `C:\Users\YeguoqiangTHPC\AppData\Roaming\eden\sdmc`，点 `Refresh` 确认 `missing` 为空或只剩当前阶段预期缺失项。
5. 启动 Companion NRO。在孩子页用 `A` 提交 `status`，用 `X` 输入离线码；也可以直接在 Web 页选择 `status` / `offline_code` 后点 `Submit request`，让页面写入同一套 `inbox/pending/`。
6. 需要离线码时，在 Web 页 `Offline code` 区填 `device`、`secret`、`minutes`、`date` 和可选 `nonce`，点 `Generate` 后再点 `Submit generated code`。也可用命令行生成：

   ```powershell
   python .\tools\grant_code.py `
     --minutes 30 `
     --device kid-switch `
     --secret replace-with-long-random-secret `
     --date 2026-07-10 `
     --nonce 4660
   ```

7. 先按 `Minus` 直接进入家长区，验证 PIN 初始化/校验和家长区 request 写入；组合键路径仍保留为长按 `L/R` 或 `ZL/ZR` 两侧肩键加 `X` 约 2 秒。Web 页的 `Quick cases` 可补充提交 `Bad code`、`Unknown type`、`Bad JSON`，也可用 `Create disable.flag` / `Remove disable.flag` 验证恢复开关。
8. 用脚本生成匹配 result，或把同一 SDMC 目录交给 `protocol_probe.py process-observe` 处理：

   ```powershell
   python .\tools\make_result.py --root C:\Users\YeguoqiangTHPC\AppData\Roaming\eden\sdmc
   ```

9. 确认 NRO 展示匹配 result；同时在 Web 页点 `Refresh`，检查 recent results、events tail、ledger tail 和 backup tail。没有 result 时 NRO 应显示后端未响应或超时，而不是业务失败。

PC 本地 Web 辅助界面：

```powershell
python .\tools\ptc_frontend_server.py
```

默认只监听 `127.0.0.1:8765`。页面可选择 SDMC root、查看布局健康度、创建 v1 request、读取 result/log/ledger/backup 摘要、创建或删除 `disable.flag`、生成离线码，并预检/安装 package zip。包含 `boot2.flag` 的 package 必须在页面勾选确认后才会解压。页面会遮罩 `grant_secret`，但输入 secret 生成离线码时仍应避免截图或共享浏览器内容。

### 3.2 真实 Switch 分阶段验证

真实 Switch 测试必须从低风险到高风险推进，不要直接进入 `grant` 或 `enforce`。

阶段顺序：

1. Safe SDMC layout：只检查 SD 卡目录和配置，不安装 boot2。
2. NRO-only：只验证 Companion 读写文件协议，不安装 boot2。
3. Disabled boot2：验证 sysmodule 启动、日志和结构化 `disabled` result，不访问 PCTL。
4. Observe boot2：验证真实 sysmodule request 处理和 PCTL 只读路径，result 必须 `dry_run: true`，不消费 nonce。
5. Play timer 写入探针：在 grant 或 enforce 写入模式先提交 `probe_play_timer_write`，确认备份、原样写回和 readback。
6. Grant 最小写入：使用 1 分钟有效码，确认写入前备份、成功后消费 nonce。
7. Enforce：在 grant 稳定后验证开机启用或刷新 play timer。
8. Raw block / suspend probe：只在 grant/enforce 基础能力和恢复路径全部通过后单独验证。

#### 3.2.1 真机内测试模式与自检（无需取回 SD 卡）

Companion NRO 的家长区提供 `Test mode` 和 `Self-check` 页面。开发测试阶段优先使用 `Test mode`：它把常用 request、等待 result、匹配 profile 自检和人工确认提示放在同一页；`Self-check` 仍用于手工输入历史 request id 或选择不在测试模式里的 profile。

推荐流程：

1. 进入并解锁家长区后打开 `Test mode`。
2. 用 `Up/Down` 选择 `Status`、`Offline code`、probe、`disable.flag` 或阶段检查用例。
3. 对 `Status` / `Offline code`，用 `X` 切换当前阶段需要的 profile。
4. 按 `A` 提交 request 或运行当前 request 的检查；有 result 的用例会自动轮询并自动运行匹配 self-check。
5. 必要时按 `Y` 主动轮询当前 request；读到 result 后也会按当前用例 profile 自检。
6. 记录 `SUMMARY` 行；出现 `FAIL` 时停止后续更高风险阶段，保留现场。

自检 profile：

- `disabled_status`：阶段 C 的 disabled result。
- `observe_success`：阶段 D 的 observe 成功 request。
- `observe_rejection`：阶段 E 的 observe 拒绝 request。
- `grant_before_probe_reject`：阶段 F 探针前写入拒绝。
- `play_write_probe`：`probe_play_timer_write` 结果、grant/enforce 写入模式、capability、backup 和事件。
- `grant_success`：grant 最小写入的 result、event、backup 和 nonce 消费事件。
- `grant_rejection`：grant 拒绝用例。
- `enforce_snapshot`：enforce tick 的 `events.jsonl` 与 `state.json` 快照；该 profile 不需要 request id。

真机内自检能判断协议产物、归档状态、日志事件、capability、backup 和 nonce 消费事件是否一致；它不能替代人工确认 Atmosphere 是否成功启动、NRO 屏幕交互是否正常、官方家长控制页面是否按预期变化、实际 raw block / suspend 效果和恢复路径是否可用。Grant/enforce 的 PCTL 用户可见效果仍以官方页面或实际系统行为为准。

真机前置条件：

- 真实 Nintendo Switch。
- Atmosphere CFW。
- 可写 SD 卡。
- Homebrew Menu。
- 已知恢复方式：能移除 `boot2.flag`，或能创建 `sdmc:/switch/play-time-control/flags/disable.flag`。
- 在强控制测试前，已经实测 `disable.flag` 行为。
- 已掌握官方家长控制 PIN 或 Nintendo Parental Controls App 的临时解除流程；Atmosphere 不提供替代官方 PIN 的通用解锁入口。

当前能力边界：

- 当前真实 PCTL adapter 使用 libnx 公开 API 读取 restriction 状态，并通过底层 PCTL IPC 封装 play timer settings 探针和写入。
- play timer 写入必须先通过 `probe_play_timer_write`；raw block 和 suspend probe 在单独真机验证前返回稳定错误或保持 capability gate。
- disabled/observe boot2 package 已可远程构建，但 boot2 自启、真实 SDMC 持久化、PCTL 读状态仍需真机确认。
- Companion NRO 的本地 PIN 只保护本项目家长区；如果官方 `Suspend Software` 已经阻止前台软件运行，NRO 入口可能不可用，应使用官方 PIN/App 或 SD 卡 request 兜底。

### 3.3 Observe Boot2 判定细则

PCTL 是 Switch 家长控制系统服务在本项目中的抽象入口，协议定义见 [docs/协议.md §PCTL Role](协议.md#pctl-role)。Observe 阶段只验证真实 sysmodule request 处理、离线码校验和 PCTL 只读路径；它不验证真实写入能力。

判断“不写入 PCTL”：

- `results/<request_id>.json` 包含 `"mode":"observe"` 和 `"dry_run":true`。
- `logs/events.jsonl` 中同一 `request_id` 不应出现 `"event":"pctl_apply"`、`"event":"pctl_backup"` 或 `"event":"pctl_apply_failed"`。
- 提交离线码前后，Switch 家长控制的今日限制、临时解锁和游玩计时器状态不应因本次请求改变。

判断“不消费 nonce”：

- 检查 `sdmc:/switch/play-time-control/ledger/used_nonces.jsonl` 不存在，或不包含本次 `day_index` 与 `nonce` 组合。
- 例如 `--date 2026-07-10 --nonce 4660` 对应 `day_index` 为 `2382`，ledger 中不应出现 `{"day_index":2382,"nonce":4660}`。
- `logs/events.jsonl` 中同一 `request_id` 不应出现 `"event":"nonce_consumed"`。

判断 PCTL 读取成功：

- `results/<request_id>.json` 的 `state` 包含 `limited_today`、`blocked_today`、`unrestricted_today`、`remaining_available`、`remaining_minutes`、`play_timer_enabled` 和 `restricted_now`。
- 读取成功时，`limited_today`、`blocked_today`、`unrestricted_today`、`play_timer_enabled` 和 `restricted_now` 应为 `0` 或 `1`，不是未知值 `-1`。
- `remaining_minutes` 只有在 `remaining_available: true` 时才代表有效分钟数；否则为 `-1` 是正常的。

判断 PCTL 读取失败仍稳定：

- 应写出完整 `results/<request_id>.json`，而不是 Companion 超时、没有 result、JSON 截断或 sysmodule 崩溃。
- result 应包含 `status: "error"`、`mode: "observe"`、`dry_run: true` 和稳定 `error.reason`，例如 `pctl_init_failed` 或 `pctl_read_failed`。

判断 unrestricted guard：

- 如果 PCTL 当前报告 `unrestricted_today: 1`，有效离线码在 observe 模式仍应返回 `status: "ok"`、`mode: "observe"`、`dry_run: true`。
- Observe 不应返回 `unlimited_not_allowed`；该错误只用于 `grant` / `enforce` 等写入模式，防止把当前无限制状态意外写成有限制。

### 3.4 阶段 E：Observe 拒绝用例

阶段 E 仍运行在 `observe` 模式，用来证明所有拒绝路径都能返回结构化 result，且不会写 PCTL 或消费 nonce。

前置检查：

- `config.json` 中 `"control_mode": "observe"`。
- `sdmc:/switch/play-time-control/flags/disable.flag` 不存在。
- 记录测试前 `ledger/used_nonces.jsonl` 和 `logs/events.jsonl` 的末尾内容。
- 使用东八区日期生成 token；`2026-07-10` 对应 day index `2382`。Web 返回的 `day_index` 应与 Switch result 的 `state.day_index` 一致；不一致时先检查 Switch 系统时间和 sysmodule 构建版本。

推荐用例：

| 用例 | 操作 | 期望 reason |
| --- | --- | --- |
| 错误 secret | `grant_code.py --minutes 30 --secret wrong-secret --date <SWITCH_DATE> --nonce 5101` 后提交 `offline_code` | `bad_signature` |
| 错误日期 | 用真实 secret 但 `--date <YESTERDAY>`、`--nonce 5102` | `wrong_date` |
| 超过上限 | 默认 `max_add_minutes=120` 下生成 `--minutes 121`、`--nonce 5103` | `minutes_exceed_limit` |
| 格式错误 | 提交 `offline_code`，code 为 `NOT-A-CODE` | `bad_code` |
| 未知 type | 手工 pending JSON 写 `type:"stage_e_unknown"` | `unknown_request_type` |
| 坏 JSON | 手工 pending 文件写截断 JSON，但保留 `"request_id":"stage-e-bad-json"` | `bad_request` |

辅助命令：

```powershell
python .\tools\protocol_probe.py request `
  --root <sdmc-root> `
  --type offline_code `
  --code <CODE> `
  --request-id stage-e-bad-secret `
  --created-at <unix_seconds>

python .\tools\protocol_probe.py raw-request `
  --root <sdmc-root> `
  --request-id stage-e-unknown `
  --text '{"version":1,"request_id":"stage-e-unknown","type":"stage_e_unknown","created_at":1783526400,"payload":{}}'

python .\tools\protocol_probe.py raw-request `
  --root <sdmc-root> `
  --request-id stage-e-bad-json `
  --text '{"version":1,"request_id":"stage-e-bad-json","type":"offline_code","created_at":1783526400,"payload":{"code":"NOT-A-CODE"}'
```

每个用例都必须满足：

- `results/<request_id>.json` 为 `status:"error"`、`mode:"observe"`、`dry_run:true`。
- request 已移动到 `inbox/done/`。
- `ledger/used_nonces.jsonl` 不新增本次 nonce。
- 同一 request 的事件中不出现 `pctl_backup`、`pctl_apply`、`pctl_apply_failed`、`nonce_consumed`。

### 3.5 Grant / Enforce 写入探针

阶段 F 当前状态：

- Grant / Enforce 代码已实现并通过 host/远程构建验证，但仍待真机验证。
- `probe_play_timer_write` 是进入真实写入的强制门槛；探针前有效离线码不会写入，未触发无限制保护时返回 `pctl_write_not_verified`，无限制保护触发时优先返回 `unlimited_not_allowed`。
- Raw Block / Suspend 尚未完成真实能力验证，仍保持 capability gate，不应在本阶段默认执行。

进入真实写入前，先在 `grant` 模式提交：

```json
{
  "version": 1,
  "request_id": "probe-play-write-0001",
  "type": "probe_play_timer_write",
  "created_at": 1783526400,
  "payload": {}
}
```

通过标准：

- 写入 `backups/last_pctl_backup.txt`，且包含 play timer settings raw hex。
- result 为 `status:"ok"`、`mode:"grant"`、`dry_run:false`。
- `capabilities.json` 中 `play_timer_write_verified:true`。
- 探针前提交有效离线码不写 PCTL、不消费 nonce；未触发无限制保护时返回 `pctl_write_not_verified`，而 PCTL 报告无限制或临时解锁且 `allow_unlimited_to_limited=false` 时优先返回 `unlimited_not_allowed`。

对应真机内自检：

- 探针前拒绝使用 `grant_before_probe_reject`。
- 写入探针使用 `play_write_probe`。
- 最小 grant 成功使用 `grant_success`。
- grant 拒绝用例使用 `grant_rejection`。
- enforce 使用 `enforce_snapshot`，再人工确认官方页面或实际计时器状态。

详细分阶段清单见 [docs/真机测试指南.md](真机测试指南.md)。
