# 测试指南

本文说明测试为什么分层，以及不同改动应执行哪些步骤。普通改动先跑自动测试；只有自动测试无法证明的 PCTL 运行时行为和真实输入链路才上真机验证。

## 测试原理

### 分层验证

测试分为三层：

1. **本地回归**验证 Python、协议、队列、nonce、setup、恢复事务和 package 安全规则。
2. **容器构建**验证 C、Makefile、Companion NRO、Overlay、sysmodule 和最终 package。
3. **真机验收**验证目标 HOS 上的 PCTL 行为、启动流程和手柄/触摸输入。

本地和容器测试必须可重复，不依赖真实时间或 Switch 服务。真机测试按改动范围触发，不作为普通代码回归的默认步骤。

### 安全与恢复

普通 PCTL 写入必须先保存恢复事务，写后确认运行时目标，再提交 rules、state、result 和 nonce。任何阶段失败都应回滚；无法证明恢复成功时必须创建 `disable.flag`。

启动恢复优先级如下：

1. `restore_install_snapshot.flag`
2. `retry_setup_release.flag`
3. 未完成的 `recovery/active/meta.json`
4. `disable.flag`
5. 普通请求和 Enforce

`raw_block` 和 `suspend` 是独立的高风险能力，只在相关功能开发或发布时专项验证。

## 测试步骤

### 1. 运行本地回归

在仓库根目录执行：

```powershell
python .\tools\test.py
```

看到 `PASS: local tests` 表示通过。该入口覆盖：

- token v1/v2、UTC+8 日期、replay、nonce 提交顺序和 v2 冷却。
- request/result schema、队列原子性、IPC 去重和 stuck processing 恢复。
- setup 状态机、前置解除失败回滚、60 秒激活宽限和恢复 flag 优先级。
- 普通 PCTL 写入事务、运行时确认、result/nonce 失败回滚和启动崩溃恢复。
- Enforce 去重、rules/state、raw block/suspend 门禁。
- PWA、单包布局、更新数据保留和安装脚本安全规则。

普通 play-timer capability 探针矩阵、observe 全路径、旧五包矩阵、一键基础测试 self-check 和重复 UI 卡片数量断言不再属于测试范围。

### 2. 构建并校验 Package

改动涉及 C、Makefile、Companion NRO、Overlay、sysmodule 或 package 时，执行：

```powershell
python .\tools\package_remote.py
```

脚本会在一次 SSH 会话中清理旧产物、运行 C/Python 测试、构建三类二进制，并只生成 `build/packages/playwise-<timestamp>.zip`。容器直接读取当前工作区，未提交改动也会参与构建。

完成后确认：

| 检查项 | 通过条件 |
| --- | --- |
| 单包 | 只存在一个最新的 PlayWise zip |
| 完整布局 | 包含 sysmodule、NRO、Overlay 和 `boot2.flag` |
| 初始配置 | `control_mode=enforce`，`setup.json.phase=pending` |
| 更新保留 | 安装脚本保留 secret、PIN、rules、state、ledger、日志和备份 |
| 旧产物 | 构建前已清理，失败时不留下伪完整产物 |

不要使用手工 SSH、`docker exec` 或复制产物的旁路流程替代该入口。

### 3. 验收图形界面

涉及 Companion 或 Overlay 界面时，逐项确认：

1. 首次启动先显示 setup 页面，并显示 phase、限制解除状态、snapshot 状态和激活时间。
2. 家长安全页包含启用自动控制、重试前置解限、恢复安装前状态、紧急停用、raw block 探针和 suspend 探针。
3. 页面不显示一键基础测试或普通 write/effect capability。
4. 孩子页、PIN、8 位码、分钟、周计划、bedtime、限制方式和确认弹窗无重叠，触摸与手柄均可操作。
5. 传输状态能区分 IPC、SD 队列、IPC accepted 后的 SD result 回读和本地 SD flag。
6. setup/recovery 错误显示稳定 code/reason，且错误结果不清除最近一次有效状态。

### 4. 验收新设备或新的 HOS/PCTL 组合

每个设备/HOS 组合执行一次完整验收：

1. 让主机进入受限状态，安装唯一 package，然后重启。
2. 不使用 Nintendo 官方解锁。打开 Companion，确认 setup snapshot 可用且当前限制已解除。
3. 设置或验证 PIN，在家长区点击“启用自动控制”，等待 60 秒并确认 setup 进入 `active`。
4. 使用一个 15 分钟 v2 码，确认真实额度增加、timer enabled、restricted false，并确认 nonce 只提交一次。
5. 重启，确认 setup、规则、额度和 ledger 均已持久化。
6. 首次验收额外创建 `flags/restore_install_snapshot.flag`，确认原始 raw settings 和 timer 状态恢复、setup 进入 `restored`，并存在 `disable.flag`。

任一步失败都应停止 Enforce 和高风险探针，并按“失败后取证”保留现场。

### 5. 按改动范围追加真机测试

| 改动范围 | 追加场景 |
| --- | --- |
| PCTL layout/status/write/restore | 前置解除或普通写入事务对应单项 |
| setup/boot lifecycle | 受限安装、重试解除、60 秒激活或启动崩溃恢复 |
| Companion/Overlay 输入 | 对应输入链路；Overlay 变更还要测试官方硬限制弹窗 |
| Enforce/rules/bedtime | 去重、规则变化、跨日或 bedtime 对应单项 |
| raw block | 独立 raw block 探针及精确恢复 |
| suspend | 独立 suspend 探针 |

### 6. 验证高风险能力

仅在改动涉及对应能力时执行：

- **raw block**：运行独立探针。只有 raw target 写入、运行时阻止、完整 0x44 snapshot 恢复和 timer 恢复全部成功才算通过。恢复失败时必须清除能力并创建 `disable.flag`。
- **suspend**：运行独立探针，确认 Horizon 暂停请求通道可用，并保存 `pctl-s-suspend-v1` backend。本项目不直接终止进程。

## 失败后取证

无法进入 Companion 时，可直接在 SD 卡创建恢复 flag。若要完全停止 boot2，删除 Atmosphere 内容目录中的 `boot2.flag`。

排查前保留以下文件：

- `setup.json`
- `backups/install_pctl_snapshot.json`
- 未完成时的 `recovery/active/`
- 对应的 `results/*.json`
- 当天的 `logs/`
- `capabilities.json`

sysmodule 崩溃报告位于 `sdmc:/atmosphere/crash_reports/<tick>_4200000000bd2300.log`。结合 `sysmodule/build/pctc-sysmodule.map` 和当天日志定位。
