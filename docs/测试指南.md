# 测试指南

测试是架构的一部分。项目必须先在 host 环境证明行为，再使用真实 Switch 服务。

## 当前可验证状态

本机用于快速验证的内容：

- `python .\tests\mvp\test_token_v1.py`
- `python .\tests\observe\test_observe_queue.py`
- `protocol_probe.py` 的 init -> 生成离线码 -> 提交 `offline_code` / `status` request -> observe 处理 -> result 写出流程。
- `tools/package_sdmc.py` 可生成 safe SDMC 目录和 zip。

远程 devkitPro 容器用于权威构建验证：

- `make`：编译并运行 C host 测试和 Python 回归。
- `make companion-nro`：通过 devkitPro/libnx 构建 Companion NRO。
- `make package-safe package-observe package-safe-nro`：生成当前 package。

不要把“本机缺少 `make`/`gcc`/可用 WSL 发行版”记录为 C host 未能验证的最终结论。C host、NRO 和 package 的默认验证路径是提交并推送 `master` 后，通过 SSH 让远程仓库 `git pull --ff-only origin master` 再执行对应 `make` 命令。

仍需模拟器或真机验证：

- 仓库当前还没有真实 boot2 sysmodule 二进制、sysmodule SDMC adapter 或 PCTL adapter。

重要边界：

- 当前 safe package 只能提供 `sdmc:/switch/play-time-control/` 配置和协议目录骨架；safe NRO package 只额外提供 Companion 前台文件协议客户端。
- 模拟器/真机现阶段只能验证 SD 卡目录布局和后续二进制接入准备；不能声称已验证 PCTL、boot2 自启、play timer、raw block 或 suspend。

## 推荐开发验证流程

常规改动按以下顺序验证：

1. 在本机运行 Python 快速回归。
2. 本地提交并推送 `master`。
3. 通过 SSH 让远程仓库快进到最新 `master`，然后在远端直接执行完整构建、测试和 package 生成。
4. 如果第 3 步失败，报告远程命令和失败原因；不要用本地缺少 `make` 或 WSL 作为替代结论。

本机快速回归：

```powershell
python .\tests\mvp\test_token_v1.py
python .\tests\observe\test_observe_queue.py
```

远端完整验证：

```sh
ssh 249-nintendo-switch-dev 'export DEVKITPRO=/opt/devkitpro; export DEVKITARM=/opt/devkitpro/devkitARM; export DEVKITA64=/opt/devkitpro/devkitA64; export PATH=$DEVKITA64/bin:$PATH; cd /ws/switch-play-time-control-local && git pull --ff-only origin master && make && make companion-nro && make package-safe package-observe package-safe-nro'
```

远端验证覆盖：

- C host core 编译与测试。
- Python token / observe 回归。
- Companion NRO 构建。
- safe、observe 和 safe NRO package 生成。

## 测试层次

单元测试：

- 面向纯 `common` 函数。
- 不使用文件系统。
- 不使用 libnx。
- 不依赖真实时间。

集成测试：

- 使用 `mem_storage`。
- 使用 `pctl_stub`。
- 使用 fake time。
- 端到端覆盖 request queue 和 control policy。

模拟器测试：

- 只验证 companion UI 和文件协议。
- 不声称验证真实 PCTL 行为。

真机测试：

- 验证 boot2、PCTL 读写、raw block、suspend 和 play timer 行为。

## 从零开始的本地测试

### 1. 检查环境和工作区

运行：

```powershell
git status --short
python --version
```

预期：

- Python 可用，建议 Python 3.12 或更新版本。
- 工作区只包含你确认要保留的本地改动。

### 2. 跑 Python host 快速回归

运行：

```powershell
python .\tests\mvp\test_token_v1.py
python .\tests\observe\test_observe_queue.py
```

预期输出：

```text
MVP token v1 tests passed
Observe queue tests passed
```

这两条测试覆盖：

- 离线加时代码的编码、解码、签名校验、错日期、重复 nonce 和超上限拒绝。
- observe 队列的 `offline_code`、`status`、坏签名、dry-run result、request 归档，以及 observe 模式不消费 nonce。

### 3. 跑 host observe 端到端 probe

初始化一个本地 SDMC 风格目录：

```powershell
python .\tools\protocol_probe.py init `
  --root .\.tmp\sdmc-observe `
  --device test-device `
  --secret test-secret
```

生成固定离线码：

```powershell
python .\tools\grant_code.py `
  --minutes 30 `
  --device test-device `
  --secret test-secret `
  --day-index 2380 `
  --nonce 4660
```

提交离线码请求，把 `<CODE>` 替换为上一步输出：

```powershell
python .\tools\protocol_probe.py request `
  --root .\.tmp\sdmc-observe `
  --type offline_code `
  --code <CODE>
```

处理 observe 请求：

```powershell
python .\tools\protocol_probe.py process-observe `
  --root .\.tmp\sdmc-observe `
  --day-index 2380
```

预期：

- 输出 `processed=1`。
- `.tmp\sdmc-observe\switch\play-time-control\results\` 下出现 result JSON。
- result 包含 `"status": "ok"`、`"mode": "observe"`、`"dry_run": true`。
- `.tmp\sdmc-observe\switch\play-time-control\ledger\` 保持为空，表示 observe 没有消费 nonce。

再提交并处理一个 status 请求：

```powershell
python .\tools\protocol_probe.py request `
  --root .\.tmp\sdmc-observe `
  --type status

python .\tools\protocol_probe.py process-observe `
  --root .\.tmp\sdmc-observe `
  --day-index 2380
```

预期 status result 同样包含 `"status": "ok"`、`"mode": "observe"`、`"dry_run": true`。

### 4. 生成可复制到 SD 卡根目录的 safe 包

命令必须按所在环境选择。Windows host / PowerShell 使用反引号 `` ` `` 续行和 `.\` 路径；remote devkitPro / bash 使用反斜杠 `\` 续行、`./` 路径和 `python3`。不要把 PowerShell 命令直接粘到 SSH 的 bash 里执行。

Windows host / PowerShell：

```powershell
python .\tools\package_sdmc.py `
  --mode safe `
  --device-id kid-switch `
  --grant-secret replace-with-long-random-secret `
  --max-add-minutes 120 `
  --out .\build\packages\safe `
  --zip .\build\packages\safe.zip
```

remote devkitPro / bash：

```sh
python3 ./tools/package_sdmc.py \
  --mode safe \
  --device-id kid-switch \
  --grant-secret replace-with-long-random-secret \
  --max-add-minutes 120 \
  --out ./build/packages/safe \
  --zip ./build/packages/safe.zip
```

预期：

- `build\packages\safe.zip` 解压后顶层直接是 `switch\play-time-control\...`。
- 不包含 `atmosphere\contents\...\flags\boot2.flag`。
- `switch\play-time-control\config.json` 中 `control_mode` 为 `observe`。

如果需要验证 Companion NRO 文件协议，先在 devkitPro/libnx 环境构建 NRO，再一起打包。没有真实 `.nro` 文件时不要执行本段，继续使用上面的 safe 包即可。

Windows host / PowerShell：

```powershell
$nro = ".\build\switch\pctc.nro"
if (-not (Test-Path $nro)) { throw "missing NRO: update `$nro to the real companion .nro path" }

python .\tools\package_sdmc.py `
  --mode safe `
  --out .\build\packages\safe-nro `
  --zip .\build\packages\safe-nro.zip `
  --nro $nro
```

remote devkitPro / bash：

```sh
make companion-nro

NRO=./build/switch/pctc.nro
test -f "$NRO" || { echo "missing NRO: update NRO to the real companion .nro path"; exit 1; }

python3 ./tools/package_sdmc.py \
  --mode safe \
  --out ./build/packages/safe-nro \
  --zip ./build/packages/safe-nro.zip \
  --nro "$NRO"
```

也可以直接使用快捷目标：

```sh
make package-safe-nro
```

如果已经有 sysmodule `exefs.nsp`，并且准备测试 boot2，必须同时传入 `--sysmodule-exefs` 和 `--boot2`：

Windows host / PowerShell：

```powershell
python .\tools\package_sdmc.py `
  --mode disabled `
  --out .\build\packages\disabled-boot2 `
  --zip .\build\packages\disabled-boot2.zip `
  --sysmodule-exefs .\path\to\exefs.nsp `
  --toolbox .\path\to\toolbox.json `
  --boot2
```

remote devkitPro / bash：

```sh
python3 ./tools/package_sdmc.py \
  --mode disabled \
  --out ./build/packages/disabled-boot2 \
  --zip ./build/packages/disabled-boot2.zip \
  --sysmodule-exefs ./path/to/exefs.nsp \
  --toolbox ./path/to/toolbox.json \
  --boot2
```

脚本不会在缺少 sysmodule 二进制时生成 `boot2.flag`，避免做出一个看似能自启但实际没有后台程序的包。

## C host 测试入口

C host 的默认验证入口是远程 devkitPro 容器。先提交并推送 `master`，再运行：

```sh
ssh 249-nintendo-switch-dev 'cd /ws/switch-play-time-control-local && git pull --ff-only origin master && make'
```

这条命令会在远程编译并运行 `tests/c/test_host_core.c`，然后运行两个 Python 回归测试。

如果当前机器本身具备 `make` 和 `gcc`，也可以本地补充运行：

```sh
make
```

也可以拆开运行：

```sh
make test-host
make test-python
```

本地 `make` 只是补充便利路径，不是跳过远程验证的理由。涉及 C 代码、Makefile、NRO 或 package 的最终验证应以远程 devkitPro 容器结果为准。

## 当前 C Host 覆盖

`tests/c/test_host_core.c` 当前覆盖：

- C token v1 与 Python fixture 一致。
- HMAC 校验、错密钥、错日期、重复 nonce、超上限。
- day index、weekday 和跨天 bedtime。
- 错误 reason 映射。
- observe dry-run 策略。
- grant 写入策略、backup gate 和 nonce 消费。
- raw block capability gate。
- `disable.flag` 优先级。
- status request pending -> processing -> done -> result。
- grant request 调用 `pctl_stub` 并写 backup/ledger。
- backup failure 阻止 PCTL 写入且不消费 nonce。
- stuck processing request 恢复。
- C 侧 request schema parser：缺 payload、未知 type、坏 schema 返回结构化 result。
- `observe` 下规则请求保持 dry-run，不写 rules/state/capabilities，不触碰 PCTL。
- `grant` 下 `set_today_limit` 持久化 rules、通过 backup gate 调用 PCTL，并写 event log。
- `probe_raw_block` 成功后写入 `capabilities.json` 并在 result capabilities 中返回。
- `parent_unlock_start` 写入 `state.json`，status result 能反映 active/expired。

## 仍需补充的覆盖

- `add_today_minutes`、`disable_today_limit`、`block_today` 和 `restore_today_policy` 的独立成功/失败断言。
- `set_weekly_template`、`set_bedtime`、`set_limit_action` 的成功/失败断言。
- `parent_unlock_end` 的独立断言。
- `probe_suspend` 在 stub 中更新 capability。
- PCTL read/write failure 的更多 result 断言。
- storage failure 的可恢复路径。

## Fixture 要求

Fixture 应生成，不手写。

每个 fixture 应定义：

- case name。
- device id。
- grant secret。
- date 或 day index。
- nonce。
- minutes。
- expected token。
- expected result。

`tools/make_fixtures.py` 必须从与 `tools/grant_code.py` 相同的协议规则生成 deterministic fixture。

## 验收门槛

启用真实 PCTL 写入前：

- 所有 host 单元测试通过。
- 所有 host 集成测试通过。
- `observe` 验证有效码但不消费 nonce。
- 坏码路径从不消费 nonce。
- backup failure 阻止写入。
- capability gates 在 probe 前拒绝 raw block 和 suspend。

启用 `enforce` 前：

- `grant` 阶段已经通过真机最小写入测试。
- 拒绝用例在真实硬件通过。
- backup 文件可读且有恢复价值。
- event log 能记录成功和失败路径。
