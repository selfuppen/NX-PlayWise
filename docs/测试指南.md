# 测试指南

测试分为确定性 host 回归、devkitPro 容器构建和真机资格验证。标准分发构建的自动测试覆盖完整安全与恢复能力，但设备端不运行循环写入/回滚式 self-test。

## 本地回归

```text
python tools/test.py
```

通过标志为 `PASS: local tests`。该入口覆盖：

- token v1/v2、8 位码、日期、签名、replay、nonce 提交顺序和冷却；
- request/result schema、原子队列、IPC 去重、stuck request 恢复；
- setup 预检、snapshot、5 秒宽限、兼容状态和恢复优先级；
- 普通 PCTL 事务、失败注入、rollback、result/ledger 失败；
- Enforce 去重、`applied_pending_confirmation`、30 秒确认/回滚，以及活跃 recovery 与启动遗留事务的区分；
- PIN、规则、安装器数据保留和诊断脱敏；
- 标准安装包/完整交付包/Device Lab 契约隔离和 package helper 失败路径。
- `version.h`/`version.mk` 一致性，以及 PWA 官方链接和外链安全属性。
- 单文件离线版与模块化源码的一致性、内联 CSP、零运行时网络依赖、Web Crypto/内置 HMAC 固定向量和无持久存储降级。

测试必须使用固定时间、固定 fixture 和 host adapter，不依赖真实 Switch 服务。

## 权威容器验证

涉及 C、C++、Makefile、NRO、Overlay、sysmodule 或 package 时必须执行：

```text
python tools/package_remote.py
```

脚本在单次 SSH 会话中清理现有构建产物，运行 C host、UI 和 Python 回归，编译三个标准分发组件并生成标准安装包与完整交付包。

分发门禁断言：

- `build/packages/` 只有 `playwise-0.1.4.zip` 和 `playwise-complete-0.1.4.zip`；
- 标准安装 Zip 只包含标准分发 sysmodule、NRO、Overlay、`boot2.flag` 及运行时目录，不包含安装器、离线网页或校验专用文件；
- 完整交付 Zip 只包含字节一致的 `playwise-0.1.4.zip` 与 `playwise-offline.html`，拒绝缺失、重复、额外、路径穿越或内容不一致的成员；
- Zip 内 `build.json` 与构建阶段外部生成的 release manifest 完全一致，profile 为 `release`；
- 三个二进制都嵌入同一 manifest，NRO/Overlay 显示版本均为 `0.1.4`；NRO 还必须嵌入项目仓库和 PWA 地址；
- 无 LAB handler、标准协议外请求、运行时控制模式、`capabilities.json` 或占位 secret；
- 不 seed `credentials.json`，首次启动必须生成唯一 secret；
- `tools/install_package_to_sd.ps1` 替换程序和 build manifest，但保留 credentials、PIN、rules、state、ledger、logs 和 backups；该脚本不打入运行时 Zip。

禁止用手工 SSH、`docker exec` 或复制回本地代替该入口。

## Device Lab 隔离验证

内部人员在 devkitPro 环境显式运行：

```sh
make device-lab-package
```

检查：

- 输出只在 `build/device-lab/`，不会出现在 `build/packages/`；
- Title ID 为 `4200000000BD23F0`，IPC 为 `pwtl:u`，SD 根目录为 `switch/playwise-device-lab`；
- manifest profile 为 `device-lab`；
- NRO 持续显示 DEVICE LAB 危险水印，操作要求 ZL+ZR+A；
- 包默认不含 `boot2.flag`；
- `make packages` 不会构建或携带任何 LAB 产物。

## UI 实机验收

修改 NRO 或 Overlay 后，至少验证：

1. 使用没有 `config.json` 向导字段的全新配置，确认首次设置按“快捷键 → PIN → 确认接管系统控制 → 选择区域”推进；中途退出后重启会恢复到已保存步骤，未完成前不允许普通写入。
2. 快捷键页固定显示 `Minus -`，并提供 `L + R`、`ZL + ZR` 分别搭配四个方向键、`Plus +`、`Minus -` 在内的 14 项列表及“录制其他组合”。选择/录制只更新草稿，按 `+` 确认后才生效；未确认或明确关闭时仅保留 `Minus -`。分别真机验证 `L+R+下`、包含 `Plus +` 和包含 `Minus -` 的组合可长按约 400ms 触发，单独按下并松开 `Minus -` 仍能进入，重启后状态不变。
3. PIN 覆盖 1 位、6 位、64 位、65 位、非数字、两次输入不一致，以及少于 4 位只提示风险；所有 PIN 入口的错误都使用最上层“重试 / 取消”弹窗，错误后清空当前输入，两次不一致时清空两次输入。冷却弹窗逐秒更新剩余秒数并禁用重试，取消不计失败。“修改任我玩PIN”必须先验证当前 PIN，取消、错误和冷却状态都不得进入新 PIN 覆盖流程。
4. 接管确认前只做只读预检；确认后验证安装 snapshot、解除当前限制、约 5 秒同步宽限，并在宽限结束后进入第 4 步。对已有官方限时日，记录“总 180 分钟、已玩 60 分钟、剩余 120 分钟”向量：完成接管后必须仍剩余约 120 分钟（允许显示值相差 1 分钟），不得套用工作日默认 60 分钟；次日才切回 PlayWise 周计划。无法读取总额度且无法由已玩加剩余计算时必须返回 313、不得写 PCTL。若返回 306，页面必须显示“系统设置 → 家长控制 → 开启家长控制”和“重新检测”。
5. 第 4 步默认选中家长区，孩子区和家长区选项都显示简短切换说明；手柄或触摸选择区域后均不得立即进入，必须再触发独立的“确认进入家长区/孩子区”按钮。分别在同步宽限结束前后的 `released`、`active` 状态验证：从第 4 步返回第 3 步时应显示接管已完成，再次继续只回到第 4 步，不重复接管、不重置宽限且不报 308。首次确认进入家长区不重复验证 PIN，之后从孩子区按 `Minus -` 或自定义组合进入家长区需要 PIN，家长区按 `B` 返回孩子区。
6. 家长区“加时码与安全”页面存在“家长区快捷键管理”下级页，可选择/录制/关闭自定义组合，并显示孩子区提示开关和当前状态。关闭提示后孩子区不得显示固定 `Minus -`，也不得禁用任何已启用入口；右侧“加时码如何生成”不得再混入进入家长区或 PIN 说明。
7. 孩子首页以“自律小达人 · 加时奖励”和“遵守约定、合理安排时间”为标题；顶部的“系统计时器”与“运行状态”同列。加时码输入框默认以大字显示“输入加时码”，并显示护眼提醒；输入后以大字显示 8 位码。游戏时间统计在按游戏数据不可用时必须明确显示“游戏明细暂不可用”和真实的今日累计已玩时间，不得伪造前 3 名游戏排行；最近执行区域保持紧凑且不遮挡页脚操作。
8. 家长区只有今日额度、周计划、加时码与安全、支持与恢复四类页面；周计划直接展示七日编辑器，没有功能卡或二级菜单，也没有探针、能力矩阵、后端或 raw layout 文案。
9. “支持与恢复”的第六张卡为“软件信息”；手柄和触摸均可打开只读弹层，显示 `PlayWise（任我玩）`、当前构建版本、`https://github.com/selfuppen/NX-PlayWise` 和 `https://selfuppen.github.io/NX-PlayWise/`，按 `A`、`B` 或触摸关闭按钮均可返回。不得显示密钥、PIN 或内部 Device Lab 信息。
10. 手柄和触摸均可操作数字键盘、额度和周计划；弹窗输入不穿透。
11. 状态语言一致：绿色“正常运行”、蓝色“正在同步”、黄色“兼容性待确认”、橙色“保护模式”；红色表示需要家长关注且会阻止正常控制的状态。保护模式显示“安全保护已触发”，主动停用显示“紧急停用已开启”，两者可并列。
12. `disable.flag` 下孩子页和全部家长页持续显示红色停用状态；status、诊断导出、解除停用和恢复仍可用，额度、周计划和加时码写入在 UI 与后台均被拒绝。分别以 `restored + disable.flag` 和 `active + disable.flag` 验证支持页显示“解除停用并重新接管”；预检失败保留 phase 与 flag，成功后才删除 flag 并进入 5 秒宽限。
13. “导出诊断包”的进行中、成功和失败状态均留在“支持与恢复”当前页，不得打开结果弹层。成功状态分三行完整显示导出路径、提交 GitHub Issue 时附加文件的说明和 `https://github.com/selfuppen/NX-PlayWise/issues`；离开支持页后清除。支持包中搜索 secret、PIN、已提交 8 位码和完整 nonce 均无匹配。
14. 进入/重新进入孩子页、切换到家长区“今日额度”页以及每个时间调整入口都会主动刷新状态；页面显示 UTC+8 日期、当前已玩、当前剩余、调整后可玩和“上次同步 X 秒/分钟前”。超过 30 秒应能明显看出数据可能过期；若真机已验证 PCTL 1952，则不限时也应显示独立已玩时间并允许后续状态判断；1952 不可用时才显示“暂不可用”，且依赖已玩时间的“临时加时”不可提交。
15. “今日额度”和“临时加时”页面不应有文字互相覆盖；大号分钟数同时显示小时/分钟换算，点击分钟数可进入数字输入，快捷调整提供 ±5/±15，并明确提示只影响今天。恢复周计划确认框使用并列状态卡突出“当前还能玩 / 恢复后还能玩”；不限时改限时使用状态卡突出“今天已玩 / 当前还能玩 / 修改后还能玩”。剩余 1–15 分钟使用黄色、0 分钟使用红色、不限时使用绿色，并始终保留文字标签。操作后为 0 或已玩不可用、无法判断是否立即限制时，触控不得绕过手柄长按 `A`；未知状态只说明无法判断，不得伪造立即限制结论。
16. 周计划显示顺序固定为周一到周日，周六浅橙、周日浅红、今天使用更粗的绿色当前日边框；今天同时被选中时还必须使用深蓝底色和白字明确显示焦点，不能让绿色边框覆盖选中反馈。候选顺序固定为日期卡、`X` 切换模式、`ZL` 放弃修改、`+` 保存计划，方向键移动且按钮首尾不循环，`A` 执行当前候选。日期仍可首尾循环；不限时日期按 `A` 或点按时不得打开分钟输入，必须提示先切换模式，切回限时后恢复此前保留的分钟数。分钟输入标题使用“设置周X的周计划额度”，避免与今天的临时额度混淆。只有今天对应的周计划草稿发生有效变化时，页面和数字输入才显示对比；仅修改其他星期、尚未修改、改回保存值，或保存值与草稿均为不限时但备用分钟不同，都不得显示。没有 today override 时使用“当前还能玩 / 保存后预计还能玩”；存在 today override 时使用“当前有效剩余 / 保存并在之后恢复周计划后预计”，并始终提示“保存周计划不会清除今天的临时设置”。限时/不限时切换和已玩时间未知都不得猜测。无修改时放弃和保存仍可选中，但显示禁用状态并解释原因。`Y` 刷新并显示动态上次刷新时间；有草稿时提供“保存并刷新 / 放弃并刷新 / 继续编辑”，默认选中继续编辑，左右移动、`A` 确认，并保留 `+ / X / B` 直达键。
17. 紧急停用期间周计划保持可查看和可移动焦点，但模式切换、分钟输入、触摸增减、数字确认和保存全部使用禁用样式并在输入层与提交层同时拒绝；页面明确显示“紧急停用中，周计划暂时只读；解除停用后才能修改和保存”。停用前已有草稿不得自动丢失，仍允许放弃；编辑数字期间检测到停用时取消本次未确认输入并保留此前草稿。带草稿离开或刷新时不得提供必然失败的保存选项，改为“保留草稿 / 放弃草稿 / 返回”并默认保留；草稿只在本次 NRO 运行期间保留，退出或重启后不持久化。
18. “加时码与安全”依次显示“立即生成加时码”“手机/电脑生成加时码”“加时码生成管理”“修改任我玩PIN”和“家长区快捷键管理”。前两个入口分别直达本机生成页和手机/电脑生成页，按 `B` 直接返回安全页，不得出现旧聚合中转层或 `Y/X/+ /R/ZR` 隐藏快捷键。“加时码生成管理”使用两列五卡布局，依次提供管理加时码设备名、管理加时码密钥、导出手机/电脑配置、编辑二维码跳转地址和恢复二维码跳转默认地址；每项均可由方向键、`A` 和触摸执行，完成后留在管理页。恢复默认地址先验证 PIN，再显示包含默认地址的 `B 取消 / A 确认`。安全页右侧帮助框不得与最近执行框重叠，动作卡小字不得越界。
19. 扫码配对覆盖成功、缺少 fragment 参数、非法密钥、取消导入、已有配置覆盖，以及 `parent-import.json` 成功/失败路径都有确定性前端测试。
20. “手机/电脑生成加时码”标题与一级入口一致，并使用近全屏双栏：主推栏说明从完整交付包取得 `playwise-offline.html`，从管理页导出 `sdmc:/switch/playwise/parent-import.json`，传到可信家长设备后用系统浏览器打开并依次选择“导入配置文件”和“导入此设备”；同时提示手机不要使用聊天软件或网盘内置预览器。联网扫码栏作为可选便捷方式保留二维码，并完整显示最长 256 字节的合法当前地址，不得省略；二维码和配置文件均明确标为包含加时码密钥。页面只能使用 `B` 或触摸返回，不得按 `A/+` 意外关闭，也不得使用共享中文字体缺失的 emoji。
21. 本机生成器默认 20 分钟，六个时长调整按钮、生成和返回均可由方向键选中并按 `A` 执行；`L/R` 约 ±15、`ZL/ZR` 约 ±30、`+` 生成，并全部吸附到合法且不超过设备上限的档位。进入页面时主动刷新状态，并以状态卡显示“今天已玩 / 当前还能玩 / 兑换后预计还能玩”和更新时间；刷新失败时实时值显示暂不可用但仍允许生成。预计值受每日 1440 分钟上限约束并明确标出截断。未加载日期时拒绝生成，并排除当天 ledger 与本机已签发 nonce。调整时长或再次生成不得暗示已签发代码被撤销：当前代码继续显示其签发时长和生成时预计快照，并提示同日签发的其他代码可能仍可兑换。当天 512 个 nonce 均不可再签发时直接拒绝生成，不得清空签发集合或复用 nonce。
22. 编辑二维码跳转地址提示只使用官方 PWA 或项目静态前端的可信自部署地址，并警告页面可以读取加时码密钥；运行时仍只做 URL 格式校验。覆盖 HTTPS、localhost/回环/私有 IP HTTP、path/query、恢复默认，以及 public HTTP、userinfo、控制字符、超长和已有 fragment 的拒绝路径。使用指南说明把完整 `tools/ptc_frontend` 发布到可信 HTTPS 静态站点即可满足扫码和文件导入能力，且 `python tools/ptc_frontend_server.py` 仅用于本机预览。
23. PWA 离线页面包含配对、码无效、日期、设备无响应、紧急停用和高级诊断排错说明。
    单文件 `playwise-offline.html` 还需直接从 `file://` 打开验证：页面完成算法自检、导入 `parent-import.json`、生成代码且不请求外部 JS/CSS/manifest/Service Worker。至少覆盖桌面 Chrome/Edge；Android 和 iOS 需记录文件管理器是否真正交给浏览器执行，不能把仅显示静态预览视为通过。
24. Overlay 顶部显示“自律约定 / 兑换加时奖励”；提交前顶部唯一显示“当前还剩可玩”和刷新时间，兑换成功后显示“修改后可玩”，折叠栏和普通展开详情不得重复剩余时间或更新时间。正式提交后读取结果期间，“当前还剩可玩”必须切换为橙色“正在刷新…”等待态，刷新按钮显示“确认中 / 提交后等待结果”，不得把旧分钟数继续画成实时值后再突然跳变。8 位输入槽为 40×48、数字字号 30，“已输入位数”字号 14，键盘数字字号 24；输入槽与“已输入位数”之间至少留出一个完整小字号高度。触摸命中区域必须与刷新、键盘、提交栏和动态高度状态栏的可见位置一致，不得存在可见但不可点或不可见却可点的区域，错误/成功展开状态栏不得越过页脚。打开时自动读取状态；空闲时 `Y` 和顶部触摸按钮可刷新。刷新或读取结果期间仍允许数字输入、方向移动、退格、触摸清空、展开/收起状态栏和按 `B` 关闭，只禁用会发起重叠请求的刷新、预览与提交；提交栏显示后台处理中但不得冻结本地输入。刷新期间保留输入和最近一次成功状态，成功后保持页面打开。刷新时间显示“刚刚刷新 / N 秒前”，30 秒后警示数据可能过期；不得用本地倒计时猜测剩余时间。status 成功不能按 `unlock_observed` 判为加时失败；加时码错误清空输入并提示重新输入，不提供会重交已提交代码的“重试”。
25. NRO 与 Overlay 都验证“输入 → 非消费预览 → 确认 → 再校验 → 正式兑换 → 结果”完整流程。预览不得写 PCTL、rules/state 或 ledger；取消确认、无效码、同步提交失败、PCTL/result/ledger 失败都不消费 nonce，并明确提示代码仍可使用。兑换后为 0、未知或从不限时改为限时时，触控确认无效，必须手柄长按。正式提交后分别在 pending、processing、done/result 阶段强制退出并重启：界面只能恢复成功终态或持续显示“结果确认中”，不得重新提交；恢复标记不含完整代码，并且只在终态已展示、用户关闭结果后删除。

## 资格验证

`0.1.4` 的资格验证基线：

- Nintendo Switch OLED；
- HOS 22.5.0；
- 资格测试环境 Atmosphère 1.11.2。

必须使用当前 `build/packages/playwise-0.1.4.zip` 构建执行：

1. 在已启用官方时间限制的主机上安装并重启。
2. 确认首次只读预检完成，未确认前没有 PCTL 写入。
3. 创建一个自选长度的数字 PIN，确认自动生成的 secret 不等于任何公开占位值，确认一周规则。
4. 家长确认接管后，验证安装 snapshot、解除当前限制、5 秒同步和 Active 状态。
5. 分别测试 status、设置今日总额度、增加分钟、今日不限时、恢复周计划和周计划保存。
6. 使用一个由当前候选环境生成的 15 分钟 v2 加时码，确认 timer、剩余时间和 nonce 仅提交一次。
7. 制造一次状态传播延迟，确认显示“正在同步”；30 秒内确认成功或按契约回滚。
8. 重启验证 setup、rules、state、ledger 和未完成事务恢复。
9. 创建 `disable.flag`，确认只熔断写入；再验证诊断和安装快照恢复。
10. 恢复安装前 snapshot，确认原始 raw/timer 状态可被精确证明，并进入 `restored`。
11. 确认 `restored` 下首次设置第 3 步显示“解除停用并重新接管”；确认后必须先重新经过预检，成功时才解除 `disable.flag` 并在 5 秒宽限后进入 `active`，失败时必须保留停用标记和 `restored`，且安装 snapshot 不得被覆盖。
12. 制造一次 Enforce 状态传播延迟，确认 30 秒窗口内同一进程的 scheduler 不会把活跃 recovery 误判为启动遗留事务；随后在窗口内真实重启，确认遗留事务被恢复、创建 `disable.flag`，并可从 `active` 状态通过“解除停用并重新接管”安全恢复。

`0.1.4` 已于 2026-08-10 在上述环境完成资格验证；manifest 的 `verified_environment.result` 为 `verified`。

## 失败取证

优先从标准分发构建的支持页导出脱敏诊断。若 NRO 无法启动，保留：

- `build.json`、`setup.json`、`compatibility.json`、`environment.json`；
- `backups/install_pctl_snapshot.json`；
- `recovery/active/`；
- `results/`、`logs/` 和相关 crash report。

不要对外发送 `credentials.json`、`auth.json`、完整 ledger 或原始离线码。要停止自动启动，可移除 `atmosphere/contents/4200000000BD2300/flags/boot2.flag`。
