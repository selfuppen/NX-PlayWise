# 真机测试指南

真机测试必须分阶段进行，不要直接跳到 `enforce`。

## 前置条件

- 真实 Nintendo Switch 硬件。
- Atmosphere CFW。
- 可写 SD 卡。
- 用于启动 companion NRO 的 Homebrew Menu。
- sysmodule 行为异常时有已知恢复路径。
- 在强控制测试前，已经验证 `disable.flag` 行为。

## 阶段 1：Host 测试

目标：

- 证明 common 逻辑、request queue、policy 和 test doubles 可用。

通过标准：

- 单元测试通过。
- 集成测试通过。
- Fixtures 是确定性的。

## 阶段 2：Companion 模拟器

目标：

- 在不接触 PCTL 的情况下验证 UI 和文件协议。

通过标准：

- Companion 可以启动。
- 离线码输入会写出 request。
- 家长区 PIN 流程可用。
- 家长操作会写出预期 request type。
- 手工放入的 result 文件能正确显示。

## 阶段 3：仅 NRO 安全包

目标：

- 在没有 boot2 sysmodule 的硬件环境中验证 SD 卡路径和 companion。

通过标准：

- Companion 可以读写 `sdmc:/switch/play-time-control/`。
- 未安装 sysmodule 自动启动项。

## 阶段 4：Disabled Boot2 冒烟测试

目标：

- 在不触碰 PCTL 的情况下验证 sysmodule 启动和日志。

必需配置：

```json
{
  "control_mode": "disabled"
}
```

通过标准：

- boot2 sysmodule 可以启动。
- `sysmodule.log` 被写出。
- Requests 返回 disabled 错误。
- 不尝试读取或写入 PCTL。

## 阶段 5：Observe PCTL 读取

目标：

- 验证 PCTL 读取路径和 dry-run result。

通过标准：

- 有效离线码返回 `dry_run: true`。
- 当前状态被报告。
- 不写入 PCTL。
- 不消费 nonce。

## 阶段 6：Grant 最小写入

目标：

- 验证最小安全 PCTL 写入。

方法：

- 使用 1 分钟的有效加时代码。
- 保持 backup 启用。

通过标准：

- 写入前创建 backup 文件。
- 今日限制按预期变化。
- Result 为成功。
- 成功后消费 nonce。
- Event log 记录本次写入。

## 阶段 7：Grant 拒绝用例

目标：

- 证明失败路径不会修改 PCTL。

用例：

- 重复代码。
- 错误日期。
- 错误 secret。
- 加时时长超过上限。
- Unlimited guard。
- Backup failure，如果可测试。

通过标准：

- 写出稳定 error result。
- PCTL 目标保持不变。
- 除非原始成功 grant 已消费 nonce，否则不消费 nonce。

## 阶段 8：Weekly、Bedtime、Parent Unlock

目标：

- 在强控制前验证完整本地管理行为。

通过标准：

- Weekly template 会应用预期的今日目标。
- Bedtime state 在预期时间变化。
- Parent unlock 可以开始、结束和过期。
- Event log 记录状态转换。

## 阶段 9：Enforce

目标：

- 验证 play timer 刷新和强控制模式。

通过标准：

- Enforce 按设计启动或刷新 play timer。
- 写入仍然要求 backup。
- Results 保持结构化。
- `disable.flag` 仍会强制 fail-open。

## 阶段 10：Raw Block 与 Suspend Probe

目标：

- 单独验证高风险能力。

规则：

- 仅在前面阶段全部通过后运行。
- 每次只运行一种能力。
- 保持恢复路径可用。
- 记录人工观察结果。

通过标准：

- Probe result 被记录到日志。
- 只有成功验证后，capability 才能标记为 true。
- Probe 前普通 raw block/suspend 请求会被拒绝，probe 后才允许。
