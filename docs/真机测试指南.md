# 真机测试指南

真机测试必须分阶段进行，不要直接跳到 `grant`、`enforce`、raw block 或 suspend。自动验证、远程构建命令和模拟器辅助流程见 `docs/测试指南.md`。

## 前置条件

- 真实 Nintendo Switch 硬件。
- Atmosphere CFW。
- 可写 SD 卡。
- 用于启动 Companion NRO 的 Homebrew Menu。
- 远程 devkitPro 已生成对应 package。
- sysmodule 行为异常时有已知恢复路径。
- 在强控制测试前，已经验证 `disable.flag` 行为。
- 掌握官方家长控制 PIN 或 Nintendo Parental Controls App 的临时解除流程；这是系统级硬限制下最可靠的人工恢复入口，不由 Atmosphere 提供。

恢复路径至少满足一个：

- 能从 SD 卡移除 `sdmc:/atmosphere/contents/4200000000BD2300/flags/boot2.flag`。
- 能创建 `sdmc:/switch/play-time-control/flags/disable.flag` 并重启。

`disable.flag` 只保证本项目 fail-open，不保证撤销官方 PCTL 已经写入或正在生效的 play-time 限制。如果官方 `Suspend Software` 已经阻止前台软件运行，Companion NRO 可能无法启动；此时应先用官方 PIN/App 临时解除限制，或直接在 SD 卡写入 request 文件交给后台 sysmodule 处理。

## 当前边界

当前仓库已有最小 Companion NRO、boot2 sysmodule skeleton、Switch SDMC adapter、Switch time provider 和保守 PCTL adapter。远程 devkitPro 已可构建：

- `build/switch/pctc.nro`
- `build/switch/exefs.nsp`
- safe / observe / safe-nro package
- disabled / observe / grant / enforce boot2 package（包含 sysmodule、`boot2.flag` 和 Companion NRO）

这些 package 只是进入分阶段真机验证的输入，不能直接声明完整功能已验证。当前真实 PCTL adapter 使用显式的多会话 `pctl`/`pctl:s` 服务读取和操作 play timer；每次操作完成后立即释放会话，绝不打开单会话的 `pctl:a`。`grant`/`enforce` 在 `probe_play_timer_write` 通过前不会写入；未触发更早策略保护时返回 `pctl_write_not_verified`，而无限制保护触发时优先返回 `unlimited_not_allowed`。raw block 和 suspend 仍保持 capability gate。

以下能力还不能通过 host 或模拟器验证：

- boot2 sysmodule 是否真实启动。
- PCTL 读状态是否符合真机实际。
- play timer 真实写入。
- raw block。
- suspend。
- 真机恢复路径。

## 阶段 A：Safe SDMC 目录布局

目标：

- 只验证 SD 卡根目录解压后的文件布局正确。
- 不安装 boot2，不触碰 PCTL。

手动操作：

1. 按 `docs/测试指南.md` 生成或取得 safe package。
2. 将 safe zip 解压到 SD 卡根目录。
3. 确认 `sdmc:/switch/play-time-control/config.json` 存在。
4. 确认 `inbox/pending/`、`inbox/processing/`、`inbox/done/`、`results/`、`logs/`、`ledger/`、`backups/`、`flags/` 存在。
5. 确认没有 `sdmc:/atmosphere/contents/4200000000BD2300/flags/boot2.flag`。
6. 打开 `config.json`，确认 `control_mode` 为 `observe`。

通过标准：

- 目录结构完整。
- safe package 没有 Atmosphere boot2 自动启动项。
- `config.json` 中的 `device_id`、`grant_secret`、`max_add_minutes` 与生成命令一致。

## 阶段 B：Companion NRO 文件协议

目标：

- 在有 Companion NRO 后验证 UI 能读写同一套 SDMC 文件协议。
- 仍然不安装 boot2，不验证 PCTL。

推荐先用 Ryujinx/Eden 在 Windows 10 上辅助验证 Companion NRO 的 UI 和文件协议；模拟器通过后再到真机做 NRO-only。模拟器不能替代本阶段的真机 SD 卡访问确认。

手动操作：

1. 按 `docs/测试指南.md` 生成或取得 `safe-nro-<YYYYMMDD-HHMMSS>.zip`。
2. 将该 zip 解压到 SD 卡根目录。
3. 从 Homebrew Menu 启动 `switch/play-time-control/` 下的 NRO。
4. 在孩子页按 `A` 提交 `status` 请求；按 `X` 可输入 16 位离线码并提交 `offline_code` 请求。
5. 按 `Minus` 直接进入家长区；组合键路径仍保留为长按 `L/R` 或 `ZL/ZR` 两侧肩键加 `X` 约 2 秒。首次进入时设置本项目 Companion PIN；之后用该 PIN 校验进入。该 PIN 只保护本项目家长区，不是 Nintendo 系统 PIN。
6. 在家长区验证可提交今日规则、周模板、bedtime、limit action、parent unlock 和 probe request。高风险 probe 与 `disable.flag` 操作在“Verification / recovery”页，需要输入 `YES` 二次确认。
7. 确认 `sdmc:/switch/play-time-control/inbox/pending/` 出现 request JSON，或 `flags/disable.flag` 按 UI 操作创建/删除。
8. 使用 `tools/make_result.py` 快速生成匹配 result，或把 SD 卡目录复制回 PC 后用 host `process-observe` 处理，再放回 SD 卡。
9. 确认 Companion 能显示匹配 result；没有 result 时应显示后端未响应或超时，而不是业务失败。

本阶段建议同时使用 PC 本地 Web 辅助界面，替代手工创建 request JSON 和检查 result/log/ledger/backup：

```powershell
python .\tools\ptc_frontend_server.py
```

浏览器打开 `http://127.0.0.1:8765` 后选择 SDMC root。页面只监听 `127.0.0.1`，可提交同一批 v1 request、创建/删除 `disable.flag`、生成离线码，并预检/安装 package zip。包含 `boot2.flag` 的 package 必须显式勾选确认后才会解压。每次提交后点 `Refresh`，用 recent results、events tail、ledger tail 和 backup tail 复核状态。

request / result 对照：

- Companion 写 request 到 `sdmc:/switch/play-time-control/inbox/pending/<request_id>.json`。
- `request_id` 必须同时出现在文件名和 JSON 字段里。
- Companion 只读取 `sdmc:/switch/play-time-control/results/<request_id>.json`。
- result 里的 `"request_id"` 必须与当前等待的 request 完全一致，否则会显示 result mismatch。
- 手工写 result 时使用 UTF-8 JSON 文本；当前 Companion 会校验 `version`、`request_id`、`type`、`status`、`mode`、`dry_run`、`state`、`capabilities` 和 `completed_at`。

Companion 结果展示：

- 真机屏幕会把 result JSON 格式化为多行 ASCII summary，优先查看 `status`、`mode`、`dry_run`、`error reason/code`、`day_index`、PCTL 状态和 capabilities。
- JSON 中的中文 `error.message` 仍保留在 `results/<request_id>.json` 中作为协议字段；Switch 控制台字体可能无法稳定显示中文，屏幕判断以 `reason` 和 `code` 为准。

通过标准：

- Companion 可以启动。
- Companion 可以写入 `status` request；如输入离线码，也可以写入 `offline_code` request。
- Companion 可以读取匹配 result。
- 未安装 boot2 sysmodule。

## 阶段 C：Disabled Boot2

目标：

- 在不访问 PCTL 的情况下验证 sysmodule 启动、日志和结构化拒绝。

必须先满足：

- 已有真实 sysmodule `exefs.nsp` 和 Companion NRO；`disabled-boot2` package 会同时包含二者。
- 已完成阶段 A；如果涉及 UI，也已经完成阶段 B。
- 已有可用恢复方式。

手动操作：

1. 按 `docs/测试指南.md` 生成或取得 `disabled-boot2-<YYYYMMDD-HHMMSS>.zip`。
2. 删除旧测试目录 `sdmc:/atmosphere/contents/4200000000BD2300/`，再解压该 zip 到 SD 卡根目录。
3. 启动或重启进入 Atmosphere。
4. 检查 `sdmc:/switch/play-time-control/logs/` 下是否有 sysmodule 日志。
5. 从 Homebrew Menu 启动 `switch/play-time-control/pctc.nro`，按 `A` 提交一个 `status` request。也可以运行 `python .\tools\ptc_frontend_server.py`，在 Web 页选择 SDMC root 后用 `Quick cases` 提交 `Disabled/Observe status`，或手工在 `sdmc:/switch/play-time-control/inbox/pending/` 写入 request JSON。
6. 确认 result reason 为 `disabled`。

手工 request 示例：

```json
{
  "version": 1,
  "request_id": "manual-disabled-0001",
  "type": "status",
  "created_at": 1783526400,
  "payload": {}
}
```

文件名应为 `sdmc:/switch/play-time-control/inbox/pending/manual-disabled-0001.json`，`request_id` 必须与 JSON 内字段一致。

如果启动或进入 Atmosphere 失败，先移除 `sdmc:/atmosphere/contents/4200000000BD2300/flags/boot2.flag` 恢复启动，再从 SD 卡复制这些排障文件：

- `sdmc:/atmosphere/fatal_errors/`
- `sdmc:/atmosphere/crash_reports/`
- `sdmc:/switch/play-time-control/logs/sysmodule.log`
- `sdmc:/switch/play-time-control/logs/events.jsonl`

如果项目自己的 `logs/` 为空，说明进程可能在 SDMC 日志初始化前已经崩溃，优先查看 Atmosphere 的 fatal/crash report。

通过标准：

- sysmodule 能启动并写日志。
- request 能得到结构化 disabled result。
- 不读取、不写入 PCTL。
- 恢复路径实测可用。

## 阶段 D：Observe Boot2

目标：

- 验证真实 sysmodule request 处理和 PCTL 只读路径。

必须先满足：

- 阶段 C 已通过。
- `control_mode` 为 `observe`。
- `flags/disable.flag` 不存在，除非正在故意测试 fail-open。

手动操作：

1. 按 `docs/测试指南.md` 生成或取得 `observe-boot2-<YYYYMMDD-HHMMSS>.zip`。
2. 解压该 zip 到 SD 卡根目录。
3. 启动或重启进入 Atmosphere。
4. 生成当天有效离线码。优先使用 Switch 本地日期，例如：

   ```powershell
   python .\tools\grant_code.py `
     --minutes 30 `
     --device kid-switch `
     --secret replace-with-long-random-secret `
     --date 2026-07-10 `
     --nonce 4660
   ```

   `2026-07-09` 对应 day index `2381`，`2026-07-10` 对应 day index `2382`。`2380` 是 `2026-07-08` 的测试值；如果在 2026-07-09 或 2026-07-10 照抄 `--day-index 2380`，结果会是 `wrong_date`。只有在 PC 与 Switch 本地日期一致时，才建议省略 `--date`。
5. 从 Homebrew Menu 启动 `switch/play-time-control/pctc.nro`，按 `X` 打开系统键盘，输入形如 `241W-2AE0-04HM-YKC7` 的 16 位离线码并提交。也可以运行 `python .\tools\ptc_frontend_server.py`，在 Web 页选择 SDMC root，在 `Offline code` 区生成当天有效码后点 `Submit generated code`，或手工写入 request 文件。如果主机已被官方 `Suspend Software` 阻止前台软件运行，先用官方 PIN/App 临时解除限制，或跳过 NRO 直接用 PC Web / SD 卡 request 文件交给后台 sysmodule 处理。
6. 检查 `results/<request_id>.json`。
7. 检查 `logs/events.jsonl`。
8. 检查 `ledger/` 没有消费本次 nonce。具体判定方法见 [docs/测试指南.md §3.3](测试指南.md#33-observe-boot2-判定细则)。

手工 `offline_code` request 示例：

```json
{
  "version": 1,
  "request_id": "manual-observe-0001",
  "type": "offline_code",
  "created_at": 1783526400,
  "payload": {
    "code": "241W-2AE0-04HM-YKC7"
  }
}
```

文件名应为 `sdmc:/switch/play-time-control/inbox/pending/manual-observe-0001.json`。

通过标准：

- result 包含 `status: "ok"`。
- result 包含 `mode: "observe"`。
- result 包含 `dry_run: true`。
- 不写入 PCTL。
- 不消费 nonce。
- PCTL 读取成功、读取失败和 `unrestricted_today: 1` 的细化判断见 [docs/测试指南.md §3.3](测试指南.md#33-observe-boot2-判定细则)。

## 阶段 E：Observe 拒绝用例

在 observe 模式下运行：

前置检查：

1. 确认 `config.json` 中 `"control_mode":"observe"`。
2. 确认 `sdmc:/switch/play-time-control/flags/disable.flag` 不存在。
3. 记录测试前 `ledger/used_nonces.jsonl` 和 `logs/events.jsonl` 的末尾内容。
4. 使用 Switch 本地日期生成 token。`2026-07-10` 对应 day index `2382`。

逐个提交以下 request，每个用例使用独立 request id 和 nonce：

| 用例 | 操作 | 期望 reason |
| --- | --- | --- |
| 错误 secret | `grant_code.py --minutes 30 --secret wrong-secret --date <SWITCH_DATE> --nonce 5101` 后提交 `offline_code` | `bad_signature` |
| 错误日期 | 用真实 secret 但 `--date <YESTERDAY>`、`--nonce 5102` | `wrong_date` |
| 加时时长超过上限 | 默认 `max_add_minutes=120` 下生成 `--minutes 121`、`--nonce 5103` | `minutes_exceed_limit` |
| 格式错误 token | 提交 `offline_code`，code 为 `NOT-A-CODE` | `bad_code` |
| 未知 request type | 手工 pending JSON 写 `type:"stage_e_unknown"` | `unknown_request_type` |
| 坏 JSON | 手工 pending 文件写截断 JSON，但保留 `"request_id":"stage-e-bad-json"` | `bad_request` |

辅助命令：

```powershell
python .\tools\protocol_probe.py request `
  --root <sdmc-root> `
  --type offline_code `
  --code <CODE> `
  --request-id stage-e-bad-secret `
  --created-at <unix_seconds>

python .\tools\protocol_probe.py raw-request `
  --root <sdmc-root> `
  --request-id stage-e-unknown `
  --text '{"version":1,"request_id":"stage-e-unknown","type":"stage_e_unknown","created_at":1783526400,"payload":{}}'

python .\tools\protocol_probe.py raw-request `
  --root <sdmc-root> `
  --request-id stage-e-bad-json `
  --text '{"version":1,"request_id":"stage-e-bad-json","type":"offline_code","created_at":1783526400,"payload":{"code":"NOT-A-CODE"}'
```

这些拒绝用例也可以通过 PC 本地 Web 的 Quick cases 提交：`Bad code`、`Unknown type` 和 `Bad JSON` 会生成对应 pending 文件；错误 secret、错误日期和超过上限可先在页面生成离线码，再提交 `offline_code`。

通过标准：

- Result 为 `status: "error"`。
- Reason 稳定。
- 不消费 nonce。
- 不尝试写入 PCTL。
- sysmodule 已处理 request 时，Companion 不显示后端超时。

## 阶段 F：Grant / Enforce / Raw Block / Suspend

目标：

- 在真实 PCTL 写入 adapter、备份文件和失败路径全部通过后，再开放写入和强控制能力。
- 本阶段先验证 `probe_play_timer_write`，通过后才做 grant/enforce；raw block 和 suspend 仍放在最后单独验证。

当前完成状态：

- 写入能力必须同时满足 `play_timer_write_verified:true` 和 `play_timer_write_backend:"pctl-s-v1"`；缺少后端标识的旧 capability 会自动失效，探针失败时不得回退到 `pctl:a`。

- Grant / Enforce：代码已实现，并已通过 host 自动测试、远程 C host 测试和远程 devkitPro 构建验证；仍需真机验证后才能声明阶段完成。
- Play timer 写入：已实现保守探针 `probe_play_timer_write`。探针前，grant/enforce 写入不会写 PCTL 或消费 nonce；未触发更早策略保护时返回 `pctl_write_not_verified`，无限制保护触发时优先返回 `unlimited_not_allowed`。
- Raw Block / Suspend：尚未开发完成，仍保持 capability gate；不要在本轮测试中声明通过。

进入本阶段前必须满足：

- `python .\tools\verify_auto_tests.py` 通过。
- 远程 C host tests 全部通过。
- disabled boot2 和 observe boot2 已在真机通过。
- `disable.flag` 恢复路径已实测。
- 写入前 backup 可读且有恢复价值。
- PCTL 写失败、backup 失败、坏 token、重复 token 都不会消费 nonce。

### 阶段 F 具体操作流程

1. 构建 grant / enforce boot2 package。

   ```powershell
   python .\tools\verify_grant_enforce_packages.py
   ```

   脚本会远程构建并验证 `grant-boot2` / `enforce-boot2` package，先清空 `D:\switch\play-time-controll\download`，再下载最新 zip 到该目录，并解压到同名目录。安装前从这些解压目录或对应 zip 取用，不要跳过脚本的 `control_mode`、`boot2.flag`、`exefs.nsp` 和 Companion NRO 校验。

   建议在正式上机前同时运行：

   ```powershell
   python .\tools\verify_auto_tests.py
   python .\tools\verify_c_host_tests.py
   python .\tools\verify_devkitpro_build.py
   ```

2. 安装 grant boot2 package。

   - 备份 SD 卡关键目录。
   - 删除旧目录 `sdmc:/atmosphere/contents/4200000000BD2300/`。
   - 将 `grant-boot2-<timestamp>.zip` 解压到 SD 卡根目录。
   - 确认存在 `sdmc:/atmosphere/contents/4200000000BD2300/exefs.nsp` 和 `flags/boot2.flag`。
   - 确认 `sdmc:/switch/play-time-control/config.json` 中 `"control_mode":"grant"`。
   - 确认 `sdmc:/switch/play-time-control/flags/disable.flag` 不存在。

   在提交任何写入相关 request 前，先将 SD 卡接到 PC，记录以下基线；每个 request 都要使用新的 request id 和 nonce：

   - `backups/last_pctl_backup.txt` 的修改时间和完整内容。
   - `ledger/used_nonces.jsonl` 的现有内容或文件不存在的状态。
   - `logs/events.jsonl` 的末尾内容。
   - Switch 官方家长控制页面中当天限制、临时解锁和计时器的当前状态。截图或人工记录均可。

   后续检查应在同一份 SD 卡副本上进行。不要把 `config.json` 中的 `grant_secret` 复制到测试记录、日志或截图中。

   以下命令中的 `<SD卡盘符>` 改为实际盘符。每次检查前，将 SD 卡接回 PC 并安全读取；不要在 Switch 运行时直接改写这些文件：

   ```powershell
   $appRoot = '<SD卡盘符>:\switch\play-time-control'
   ```

   手工写入 pending request 后，安全弹出 SD 卡并插回已运行 Atmosphere 的 Switch。sysmodule 启动后会先等待约 15 秒，随后每约 0.5 秒轮询一次；等待启动延迟和至少一个轮询周期后，再关机取卡检查。不要在 Switch 运行时拔出 SD 卡。

   对有 request id 的步骤，先确认 `inbox/pending/` 和 `inbox/processing/` 中没有同名文件、`inbox/done/` 中已有同名文件，再读取 `results/<request_id>.json`。如果仍有 pending/processing 文件或没有 result，先保留现场，检查 `logs/sysmodule.log`、`logs/events.jsonl` 和 Atmosphere fatal/crash report；不要重提同一 request。

3. 先验证探针前拒绝。

   生成当天 1 分钟有效码：

   ```powershell
   python .\tools\grant_code.py `
     --minutes 1 `
     --device kid-switch `
     --secret replace-with-long-random-secret `
     --date <Switch本地日期> `
     --nonce 6101
   ```

   通过 Companion NRO 输入，用 PC 本地 Web 提交，或手工写入 `sdmc:/switch/play-time-control/inbox/pending/grant-before-probe.json`：

   ```json
   {
     "version": 1,
     "request_id": "grant-before-probe",
     "type": "offline_code",
     "created_at": 1783526400,
     "payload": {
       "code": "<CODE>"
     }
   }
   ```

   预期 result 为 `status:"error"`。当 PCTL 报告无限制或临时解锁且 `allow_unlimited_to_limited=false` 时，预期 `reason:"unlimited_not_allowed"`；否则预期 `reason:"pctl_write_not_verified"`。两种拒绝都不生成 `ledger/used_nonces.jsonl`，也不出现成功的 `pctl_apply`。

   `unlimited_not_allowed` 只验证无限制保护，不等同于验证写入探针 gate；要验收 `pctl_write_not_verified`，测试时必须不触发无限制保护。

   取出 SD 卡后，检查 `results/grant-before-probe.json` 为 `status:"error"`、`mode:"grant"`、`dry_run:false`，且 reason 符合上面的分支。搜索同一 request id 的事件，不得有成功的 `pctl_apply` 或 `nonce_consumed`；ledger 中不得出现 nonce `6101`。PCTL 当前状态和 backup 文件修改时间也应保持基线不变。

4. 执行 play timer 写入探针。

   在 Companion NRO 家长区的“Verification / recovery”页提交 `probe_play_timer_write`，或用 PC 本地 Web 提交；也可以手工写入 `sdmc:/switch/play-time-control/inbox/pending/probe-play-write-0001.json`：

   ```json
   {
     "version": 1,
     "request_id": "probe-play-write-0001",
     "type": "probe_play_timer_write",
     "created_at": 1783526400,
     "payload": {}
   }
   ```

   将 SD 卡接回 PC 后，按以下顺序检查：

   ```powershell
   $requestId = 'probe-play-write-0001'
   Get-ChildItem "$appRoot\inbox\pending\$requestId.json", "$appRoot\inbox\processing\$requestId.json" -ErrorAction SilentlyContinue
   Get-Item "$appRoot\inbox\done\$requestId.json"
   $result = Get-Content "$appRoot\results\$requestId.json" -Raw -Encoding utf8 | ConvertFrom-Json
   $result | Format-List version, request_id, type, status, mode, dry_run, completed_at, error, state, capabilities
   Select-String -LiteralPath "$appRoot\logs\events.jsonl" -Pattern ('"request_id":"' + $requestId + '"')
   Get-Content "$appRoot\capabilities.json" -Raw -Encoding utf8 | ConvertFrom-Json | Format-List
   Select-String -LiteralPath "$appRoot\backups\last_pctl_backup.txt" -Pattern 'play_timer_settings_hex='
   ```

   全部满足才可继续：

   - result 是 `request_id:"probe-play-write-0001"`、`type:"probe_play_timer_write"`、`status:"ok"`、`mode:"grant"`、`dry_run:false`，且 `capabilities.play_timer_write_verified` 为 `true`。
   - `capabilities.json` 也已持久化为 `"play_timer_write_verified":true`；只在 result 中看到该字段而文件未更新，不能继续。
   - `backups/last_pctl_backup.txt` 已在本次请求后更新，且 `play_timer_settings_hex=` 后有值。保留此文件副本，但不要手工修改 raw hex。
   - 同一 request 的事件至少有 `request_received`、`pctl_backup`、`probe_ok`、`result_ok`，全部 `error:"ok"`；不得有 `probe_failed`、`pctl_backup_failed`、`result_error` 或 `nonce_consumed`。
   - 对照基线，Switch 官方家长控制的当天限制、临时解锁和计时器状态没有变化；探针仅做原样写回和 readback。

   任一条件不符合即停止阶段 F，不要继续 grant/enforce。

5. 执行 grant 最小写入。

   生成新的 1 分钟有效码：

   ```powershell
   python .\tools\grant_code.py `
     --minutes 1 `
     --device kid-switch `
     --secret replace-with-long-random-secret `
     --date <Switch本地日期> `
     --nonce 6102
   ```

   通过 Companion NRO 输入，或手工写入 `offline_code` request。取出 SD 卡后确认 result 为 `status:"ok"`、`type:"offline_code"`、`mode:"grant"`、`dry_run:false`，且 result 的 request id 与文件名一致。用该 request id 搜索 `events.jsonl`，应依次至少看到 `request_received`、`pctl_backup`、`pctl_apply`、`result_ok`、`nonce_consumed`；不得出现 `pctl_apply_failed`、`result_write_failed` 或 `nonce_failed`。

   `used_nonces.jsonl` 必须新增且仅新增一次 `{"day_index":<当天 day index>,"nonce":6102}`。例如 `--date 2026-07-10` 对应 day index `2382`。backup 文件必须已更新；随后重新打开 Switch 官方家长控制页面，确认当天限制仅按本次 1 分钟授权的预期变化。以官方页面或实际计时器状态为准，不以 backup 的 raw hex 推断用户可见结果。

   ```powershell
   Select-String -LiteralPath "$appRoot\ledger\used_nonces.jsonl" -Pattern '"day_index":<当天 day index>,"nonce":6102'
   Select-String -LiteralPath "$appRoot\logs\events.jsonl" -Pattern '"request_id":"<grant request id>"'
   ```

6. 执行 grant 拒绝用例。

   至少验证重复代码、错误日期、错误 secret、超过上限、unlimited guard。每个用例使用新的 request id；提交前记录 backup 修改时间、对应 nonce 的 ledger 匹配行和官方页面状态。提交后检查 result 为 `status:"error"` 且 reason 与预期一致，PCTL 目标和 backup 保持不变；除已成功使用过的重复码外，新 nonce 不得出现在 ledger，同一 request 不得有成功的 `pctl_apply` 或 `nonce_consumed`。

   `unlimited_not_allowed` 用例还必须是 `mode:"grant"`、`dry_run:false`，并保留 PCTL 当前无限制或临时解锁的人工记录。它验证的是防止写入的保护，不是探针 gate 已通过的证据。

7. 执行 enforce 验证。

   - 安装 `enforce-boot2-<timestamp>.zip`。
   - 确认 `config.json` 中 `"control_mode":"enforce"`。
   - 保留 `capabilities.json` 中 `"play_timer_write_verified":true`。
   - 记录 `events.jsonl` 的当前末尾和 backup 修改时间，再重启进入 Atmosphere。

   enforce tick 是后台循环，不会产生对应 request/result。取出 SD 卡后检查 `logs/events.jsonl` 中 `request_id:"unknown"`、`type:"unknown"` 的新事件，以及 `state.json`：

   ```powershell
   Get-Content "$appRoot\state.json" -Raw -Encoding utf8 | ConvertFrom-Json | Format-List
   Get-Content "$appRoot\logs\events.jsonl" -Tail 40
   ```

   首次目标变化时，事件应按写入流程出现 `pctl_backup`、`pctl_apply`、`pctl_start_timer`、`state_persisted`，且全部 `error:"ok"`。`state.json` 的 `last_enforced_day_index` 应为当天 day index，`last_enforced_mode` 和 `last_enforced_minutes` 应与 `rules.json` 对当天生效的规则一致；官方家长控制页面也应反映该目标。

   记录 event log 行数或末尾时间后等待至少一个轮询周期。规则、日期和 capability 未改变时，不应再新增 `pctl_backup`、`pctl_apply` 或 `pctl_start_timer`。然后创建 `flags/disable.flag`，再等待一个轮询周期；不得再新增这些 PCTL 写入事件，官方页面也不得再被本项目改变。任一检查失败时停止测试，保留日志和 backup，并按“恢复与回滚”处理。

8. Raw Block / Suspend 暂不执行正式验证。

   当前 `raw_block` 和 `suspend` 仍未完成真实能力验证。仅在 grant/enforce 真机稳定、恢复路径可靠后，再为这两项制定单独探针和回滚方案。

   阶段 F 完成后，保留 `config.json` 以外的 result、event log、ledger、capabilities、state 和 backup 副本，以及每一步的官方页面观察记录。任何检查不符合预期时，立即创建 `disable.flag`，停止继续测试，并按“恢复与回滚”保留现场；不要继续 raw block 或 suspend。

Play timer 写入探针通过标准：

- 在 `grant` 模式提交 `probe_play_timer_write` request。
- `backups/last_pctl_backup.txt` 存在，且包含 `play_timer_settings_hex=`。
- result 为 `status:"ok"`、`mode:"grant"`、`dry_run:false`。
- `capabilities.json` 中 `play_timer_write_verified:true`。
- 探针前提交有效离线码不写 PCTL、不消费 nonce；未触发无限制保护时返回 `pctl_write_not_verified`，而 PCTL 报告无限制或临时解锁且 `allow_unlimited_to_limited=false` 时优先返回 `unlimited_not_allowed`。

Grant 最小写入通过标准：

- 使用 1 分钟的有效加时代码。
- 必须已经有 `play_timer_write_verified:true`。
- 写入前创建 backup 文件。
- 今日限制按预期变化。
- Result 为成功。
- 成功后消费 nonce。
- Event log 记录本次写入。

Grant 拒绝用例：

- 重复代码。
- 错误日期。
- 错误 secret。
- 加时时长超过上限。
- Unlimited guard：在 `grant`/`enforce` 写入模式下，如果 Switch PCTL 当前报告无限制或临时解锁，且 `allow_unlimited_to_limited=false`，应返回 `unlimited_not_allowed`。
- Backup failure，如果可测试。

拒绝用例通过标准：

- 写出稳定 error result。
- PCTL 目标保持不变。
- 除非原始成功 grant 已消费 nonce，否则不消费 nonce。

Enforce 通过标准：

- Enforce 按设计启动或刷新 play timer。
- 写入仍然要求 backup。
- 对应后台事件和 `state.json` 保持可解析、可追踪；enforce tick 本身不生成 request result。
- `disable.flag` 仍会强制 fail-open。

Raw Block 与 Suspend Probe 规则：

- 仅在 grant/enforce 基础能力全部通过后运行。
- 每次只运行一种能力。
- 保持恢复路径可用。
- 记录人工观察结果。
- Probe result 被记录到日志。
- 只有成功验证后，capability 才能标记为 true。
- Probe 前普通 raw block/suspend 请求会被拒绝，probe 后才允许。

## 恢复与回滚

禁用 sysmodule 行为：

1. 创建 `sdmc:/switch/play-time-control/flags/disable.flag`。
2. 必要时重启。
3. 如果需要完全停止 boot 行为，移除 `boot2.flag`。

系统级限制恢复：

- Atmosphere 不提供替代官方家长控制 PIN 的通用解锁入口。
- 本项目 Companion PIN 只保护家长区，不能作为系统级恢复手段。
- 如果官方 play-time 限制或 `Suspend Software` 已经生效，优先用官方 PIN 或 Nintendo Parental Controls App 临时解除；前台 NRO 不可用时，通过 SD 卡手工写入 pending request 或创建 `disable.flag`。

清理 request 状态：

- 将卡在 `inbox/processing/` 的文件移回 `inbox/pending/`，或归档它们。
- 保留 `results/` 和 `logs/events.jsonl` 以便调试。

在后续 grant/enforce 阶段复核 PCTL 写入行为前，不要删除备份。
