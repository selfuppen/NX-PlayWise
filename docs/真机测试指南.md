# 真机测试指南

真机测试必须分阶段进行，不要直接跳到 `grant`、`enforce`、raw block 或 suspend。自动验证、远程构建命令和模拟器辅助流程见 `docs/测试指南.md`。

## 前置条件

- 真实 Nintendo Switch 硬件。
- Atmosphere CFW。
- 可写 SD 卡。
- 用于启动 Companion NRO 的 Homebrew Menu。
- 远程 devkitPro 已生成对应 package。
- sysmodule 行为异常时有已知恢复路径。
- 在强控制测试前，已经验证 `disable.flag` 行为。

恢复路径至少满足一个：

- 能从 SD 卡移除 `sdmc:/atmosphere/contents/4200000000BD2300/flags/boot2.flag`。
- 能创建 `sdmc:/switch/play-time-control/flags/disable.flag` 并重启。

## 当前边界

当前仓库已有最小 Companion NRO、boot2 sysmodule skeleton、Switch SDMC adapter、Switch time provider 和保守 PCTL adapter。远程 devkitPro 已可构建：

- `build/switch/pctc.nro`
- `build/switch/exefs.nsp`
- safe / observe / safe-nro package
- disabled / observe boot2 package

这些 package 只是进入分阶段真机验证的输入，不能直接声明完整功能已验证。当前真实 PCTL adapter 只使用 libnx 公开 API 读取 restriction 状态并生成备份文本；play timer 写入、raw block 和 suspend probe 在 raw layout 真机验证前会返回稳定错误。

以下能力还不能通过 host 或模拟器验证：

- boot2 sysmodule 是否真实启动。
- PCTL 读状态是否符合真机实际。
- play timer 真实写入。
- raw block。
- suspend。
- 真机恢复路径。

## 阶段 A：Safe SDMC 目录布局

目标：

- 只验证 SD 卡根目录解压后的文件布局正确。
- 不安装 boot2，不触碰 PCTL。

手动操作：

1. 按 `docs/测试指南.md` 生成或取得 safe package。
2. 将 safe zip 解压到 SD 卡根目录。
3. 确认 `sdmc:/switch/play-time-control/config.json` 存在。
4. 确认 `inbox/pending/`、`inbox/processing/`、`inbox/done/`、`results/`、`logs/`、`ledger/`、`backups/`、`flags/` 存在。
5. 确认没有 `sdmc:/atmosphere/contents/4200000000BD2300/flags/boot2.flag`。
6. 打开 `config.json`，确认 `control_mode` 为 `observe`。

通过标准：

- 目录结构完整。
- safe package 没有 Atmosphere boot2 自动启动项。
- `config.json` 中的 `device_id`、`grant_secret`、`max_add_minutes` 与生成命令一致。

## 阶段 B：Companion NRO 文件协议

目标：

- 在有 Companion NRO 后验证 UI 能读写同一套 SDMC 文件协议。
- 仍然不安装 boot2，不验证 PCTL。

推荐先用 Ryujinx/Eden 在 Windows 10 上辅助验证 Companion NRO 的 UI 和文件协议；模拟器通过后再到真机做 NRO-only。模拟器不能替代本阶段的真机 SD 卡访问确认。

手动操作：

1. 按 `docs/测试指南.md` 生成或取得 `safe-nro-<YYYYMMDD-HHMMSS>.zip`。
2. 将该 zip 解压到 SD 卡根目录。
3. 从 Homebrew Menu 启动 `switch/play-time-control/` 下的 NRO。
4. 在 UI 中提交 `status` 请求。
5. 确认 `sdmc:/switch/play-time-control/inbox/pending/` 出现 request JSON。
6. 使用 `tools/make_result.py` 快速生成匹配 result，或把 SD 卡目录复制回 PC 后用 host `process-observe` 处理，再放回 SD 卡。
7. 确认 Companion 能显示匹配 result；没有 result 时应显示后端未响应或超时，而不是业务失败。

request / result 对照：

- Companion 写 request 到 `sdmc:/switch/play-time-control/inbox/pending/<request_id>.json`。
- `request_id` 必须同时出现在文件名和 JSON 字段里。
- Companion 只读取 `sdmc:/switch/play-time-control/results/<request_id>.json`。
- result 里的 `"request_id"` 必须与当前等待的 request 完全一致，否则会显示 result mismatch。
- 手工写 result 时使用 UTF-8 JSON 文本；当前 Companion 会校验 `version`、`request_id`、`type`、`status`、`mode`、`dry_run`、`state`、`capabilities` 和 `completed_at`。

通过标准：

- Companion 可以启动。
- Companion 可以写入 request。
- Companion 可以读取匹配 result。
- 未安装 boot2 sysmodule。

## 阶段 C：Disabled Boot2

目标：

- 在不访问 PCTL 的情况下验证 sysmodule 启动、日志和结构化拒绝。

必须先满足：

- 已有真实 sysmodule `exefs.nsp`。
- 已完成阶段 A；如果涉及 UI，也已经完成阶段 B。
- 已有可用恢复方式。

手动操作：

1. 按 `docs/测试指南.md` 生成或取得 `disabled-boot2-<YYYYMMDD-HHMMSS>.zip`。
2. 删除旧测试目录 `sdmc:/atmosphere/contents/010000000000BD23/`，再解压该 zip 到 SD 卡根目录。
3. 启动或重启进入 Atmosphere。
4. 检查 `sdmc:/switch/play-time-control/logs/` 下是否有 sysmodule 日志。
5. 提交一个 request。
6. 确认 result reason 为 `disabled`。

如果启动或进入 Atmosphere 失败，先移除 `sdmc:/atmosphere/contents/4200000000BD2300/flags/boot2.flag` 恢复启动，再从 SD 卡复制这些排障文件：

- `sdmc:/atmosphere/fatal_errors/`
- `sdmc:/atmosphere/crash_reports/`
- `sdmc:/switch/play-time-control/logs/sysmodule.log`
- `sdmc:/switch/play-time-control/logs/events.jsonl`

如果项目自己的 `logs/` 为空，说明进程可能在 SDMC 日志初始化前已经崩溃，优先查看 Atmosphere 的 fatal/crash report。

通过标准：

- sysmodule 能启动并写日志。
- request 能得到结构化 disabled result。
- 不读取、不写入 PCTL。
- 恢复路径实测可用。

## 阶段 D：Observe Boot2

目标：

- 验证真实 sysmodule request 处理和 PCTL 只读路径。

必须先满足：

- 阶段 C 已通过。
- `control_mode` 为 `observe`。
- `flags/disable.flag` 不存在，除非正在故意测试 fail-open。

手动操作：

1. 按 `docs/测试指南.md` 生成或取得 `observe-boot2-<YYYYMMDD-HHMMSS>.zip`。
2. 解压该 zip 到 SD 卡根目录。
3. 启动或重启进入 Atmosphere。
4. 生成当天有效离线码。
5. 通过 Companion 或 request 文件提交 `offline_code`。
6. 检查 `results/<request_id>.json`。
7. 检查 `logs/events.jsonl`。
8. 检查 `ledger/` 没有消费本次 nonce。

通过标准：

- result 包含 `status: "ok"`。
- result 包含 `mode: "observe"`。
- result 包含 `dry_run: true`。
- 不写入 PCTL。
- 不消费 nonce。
- 如果 PCTL 读取成功，result state 应包含可用的 restriction 状态字段。
- 如果 PCTL 读取失败，result 仍是结构化且稳定的。

## 阶段 E：Observe 拒绝用例

在 observe 模式下运行：

- 错误 secret。
- 错误日期。
- 加时时长超过上限。
- 格式错误的 token。
- 未知 request type。
- 坏 JSON。

通过标准：

- Result 为 `status: "error"`。
- Reason 稳定。
- 不消费 nonce。
- 不尝试写入 PCTL。
- sysmodule 已处理 request 时，Companion 不显示后端超时。

## 阶段 F：Grant / Enforce / Raw Block / Suspend

目标：

- 在真实 PCTL 写入 adapter、备份文件和失败路径全部通过后，再开放写入和强控制能力。

进入本阶段前必须满足：

- `python .\tools\verify_auto_tests.py` 通过。
- 远程 C host tests 全部通过。
- disabled boot2 和 observe boot2 已在真机通过。
- `disable.flag` 恢复路径已实测。
- 写入前 backup 可读且有恢复价值。
- PCTL 写失败、backup 失败、坏 token、重复 token 都不会消费 nonce。

Grant 最小写入通过标准：

- 使用 1 分钟的有效加时代码。
- 写入前创建 backup 文件。
- 今日限制按预期变化。
- Result 为成功。
- 成功后消费 nonce。
- Event log 记录本次写入。

Grant 拒绝用例：

- 重复代码。
- 错误日期。
- 错误 secret。
- 加时时长超过上限。
- Unlimited guard。
- Backup failure，如果可测试。

拒绝用例通过标准：

- 写出稳定 error result。
- PCTL 目标保持不变。
- 除非原始成功 grant 已消费 nonce，否则不消费 nonce。

Enforce 通过标准：

- Enforce 按设计启动或刷新 play timer。
- 写入仍然要求 backup。
- Results 保持结构化。
- `disable.flag` 仍会强制 fail-open。

Raw Block 与 Suspend Probe 规则：

- 仅在 grant/enforce 基础能力全部通过后运行。
- 每次只运行一种能力。
- 保持恢复路径可用。
- 记录人工观察结果。
- Probe result 被记录到日志。
- 只有成功验证后，capability 才能标记为 true。
- Probe 前普通 raw block/suspend 请求会被拒绝，probe 后才允许。

## 恢复与回滚

禁用 sysmodule 行为：

1. 创建 `sdmc:/switch/play-time-control/flags/disable.flag`。
2. 必要时重启。
3. 如果需要完全停止 boot 行为，移除 `boot2.flag`。

清理 request 状态：

- 将卡在 `inbox/processing/` 的文件移回 `inbox/pending/`，或归档它们。
- 保留 `results/` 和 `logs/events.jsonl` 以便调试。

在后续 grant/enforce 阶段复核 PCTL 写入行为前，不要删除备份。
