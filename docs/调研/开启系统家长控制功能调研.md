# 开启系统家长控制功能调研

调研日期：2026-10-06。本文是可行性与接入设计记录，不新增标准协议请求或运行时功能，也不代表已经通过真机验证。

## 结论

可以探索在 PlayWise 首次设置中提供“设置系统家长控制”入口：由 Companion NRO 调用 libnx 的 `pctlauthRegisterPasscode()`，让家长在 Nintendo 原生界面设置官方 PIN，返回后由后台重新读取开启状态。这条路径有公开 libnx 封装，也有本机 NX-Pctl-Manager 的使用实例，适合先做隔离真机实验。

目前不能承诺“一键开启并完成 PlayWise 接管”。公开接口的确定职责是注册 PIN；它是否等价于系统设置的完整首次配置流程、返回后 `1031` 是否变为 true、是否产生可接管的计时配置，以及取消时有无局部变化，都缺少本项目绑定环境的真机证据。即使 `1031=true`，也只能表示当前协议中的官方家长控制已开启，不能证明计时、到时限制或 PlayWise 接管成功。

另有一个明确的接入阻点：**若注册后计时配置仍为全零，当前 PlayWise 不会把它解释为今日不限时，首次接管会因当天规则未知返回 `313 handover_state_unavailable`。** 因而仅添加一个原生 PIN 按钮不一定能完成首次设置。

建议先验证“原生 PIN 注册 + 状态回读 + 当前接管前置条件”，证据通过后再实现正式入口；如遇全零配置，另行设计首次计时初始化事务，保留现有接管对未知额度的拒绝行为。

## 现有行为与概念边界

| 项目 | 当前来源与行为 | 不能据此推出 |
| --- | --- | --- |
| 官方家长控制已开启 | 后台通过 `1031 IsRestrictionEnabled` 读取；UI 保留开启、未开启、未知三态 | 计时正在运行或到时确实限制 |
| 官方临时解除 | `1006 IsRestrictionTemporaryUnlocked`，与开启状态分开 | 已删除官方设置或需要重新注册 PIN |

## 可选技术路径

| 路径 | 源码可以确认的内容 | 评估 |
| --- | --- | --- |
| `pctlauthRegisterPasscode()` | 启动 Nintendo 家长控制 PIN 注册 LibraryApplet，返回系统 Result | 首选实验候选；无需由 PlayWise 收集官方 PIN |
| `pctlauthShowForConfiguration()` | 检查已有 PIN；头文件要求 PIN 已注册 | 已有设置的认证用途，不能当作首次开启接口 |
| `pctlauthChangePasscode()` | 修改已有官方 PIN | 超出本次首次开启范围 |
| `pctlauthShow(false)` | 临时解除官方家长控制 | 与开启目标方向不同，不能用于初始化 |
| 跳到系统家长控制设置页 | 本地 libnx 有 HOME、系统更新等跳转封装，未找到家长控制设置页的公开跳转封装 | 保留现有手动步骤；不能猜 general-channel 参数 |
| 直接调用私有 `SetPinCode` 或类似“启用全部功能”命令 | 当前 libnx 没有此类公开封装；参考项目注释报告现代固件拒绝直接设 PIN | 不作为首版方案；第三方注释不是本项目的真机证明 |

`pctlauthRegisterPasscode()` 的调用链位于本地 libnx：

```text
pctlauthRegisterPasscode()
  -> PctlAuthType_RegisterPasscode
  -> AppletId_LibraryAppletAuth (0x0A)
  -> libappletLaunch(..., LibAppletMode_AllForeground)
  -> 等待 applet 退出，读取一个 Result
```

封装在 HOS 4.0.0 及以上使用 applet 参数版本 2，较早版本使用 1；这个源码分支不代表 PlayWise 支持所有这些固件。它不返回 PIN 给调用者，也不返回完整配置或开启状态。启动成功、正常退出和系统返回成功不能替代后台回读；失败也不能证明没有局部变化。libnx 的通用封装把部分取消、异常退出归为 `LibAppletBadExit`，界面不应把所有失败都解释为用户取消。

本机 NX-Pctl-Manager 在 `pctl_set_pin()` 中先 `pctlExit()`，再调用原生注册界面，最后 `pctlInitialize()`。其注释说明部分固件在调用者仍持有 PCTL 会话时会失败；界面代码也记录原生界面返回与失焦事件之间的时序问题。这提供了会话交接和焦点恢复的实验线索，不能证明 PlayWise 的独立后台同时运行时同样安全。

该参考项目是 GPL-3.0-or-later，PlayWise 是 Apache-2.0。这里仅参考接口用法和调查线索，不复制参考项目的实现，也不增加构建依赖。

## PlayWise 接入需要解决的边界

### 1. 前台原生界面与后台 PCTL 访问

原生 PIN 界面应由具备 AM/applet 上下文的 NRO 启动。当前 sysmodule 使用 `AppletType_None`，Tesla 浮窗也不是可直接复用的原生 LibraryApplet 调用环境；首版入口应放在未受限时的 NRO 首次设置中。相册 applet 模式与游戏接管的 application 模式需分别验机，不能因现有系统键盘可用就假定 auth applet 可用。

现有 NRO 不持有 PCTL 会话，因此在 NRO 中调用 `pctlExit()` 无法关闭另一个进程内的后台会话。后台虽然逐次关闭会话，但状态轮询、队列请求、启动预检和 Enforce 仍可能与原生界面重叠。

隔离实验应先通过现有安全停止/切换流程确保标准和 Lab 控制后台都没有并发 PCTL 访问，再调用原生界面。正式接入如保留后台，必须设计由后台确认的互斥窗口：先完成已接受操作和恢复事务，暂停新的 PCTL 读写，确认没有在用会话后才允许 NRO 启动；窗口内客户端不能经 SD 队列绕过限制。原生界面退出并完成重新检查后才恢复访问，调用者中断或无法确认退出时不得盲目恢复控制写入。

现有 `disable.flag` 只阻止新的控制写，仍允许状态读取和恢复，不能独立满足上述互斥要求。现有 handover 的 quiesce 用于后台退出交接，也不是已经实现的原生设置互斥协议。具体请求、持久化方式和错误码需在后续实现中定义，本文不预留请求 ID。

### 2. 新注册官方 PIN 无法由现有快照撤销

`PtcPctlSettingsSnapshot` 只保存 `0x44` 计时设置和 timer 布尔状态，不包含官方 PIN、年龄/通信限制或手机配对信息。恢复安装快照不能宣称恢复了“系统家长控制原本未开启”的状态。

因此操作应明确告知：家长将在 Nintendo 界面创建独立的官方 PIN；此设置由系统保存，后续 PlayWise 接管失败或恢复计时设置时也可能保留。失败后重新读取实际状态，不自动调用删除全部设置、解绑、读取 PIN 明文或重置 PIN 的命令。

PlayWise 的安装快照应继续表示接管前的计时状态。对尚无安装快照的新设备，应在官方设置完成并刷新后、PlayWise 第一次计时写入前保存；已有安装快照永不覆盖。若要保存原生设置前的观察数据，它只能作为独立脱敏证据，不能伪装成可恢复全部家长控制的备份。

### 3. 全零计时配置与首次接管

当前代码链可以确认：全零 `0x44` 通过日槽位的结构合法性检查，但 `ptc_play_timer_settings_get_mode` 无法将其分类；状态没有 `limited_today`、`blocked_today` 或 `unrestricted_today`，`capture_handover_today` 因而返回 313。**这是对“如果注册后仍全零”的代码推导，不是对原生注册行为的真机结论。**

真机实验必须同时采集注册前后 `1031` 与计时配置，区分“官方设置已完成”和“PlayWise 可以接管”。若原生界面留下可可靠读取的当天配置，继续使用现有接管流程；若留下全零或未知配置，保持未接管并说明原因。

后续首次计时初始化若确有需要，必须单独证明设备没有需要保留的有效计时计划，并设计家长明确选择、原始计时快照、写入回读、文件提交失败回滚与中断恢复。不能把“今天已用时间未知”当作 0，也不能为通过 setup 把全零一律映射为不限时、自动改为今日不限时或调用 `1451` 激活 timer。已有计划仍走保留当天额度的接管，不进入初始化分支。

## 建议的首版交互范围

只考虑尚未完成 PlayWise 接管、明确未配置官方家长控制的新设备；已有官方 PIN、配对、开启状态未知、活动恢复事务或已受限的设备继续使用系统设置与现有支持流程。仅凭 `1031=false` 不足以证明这是从未配置的设备。

建议流程：

1. 首次设置保留“开启家长控制说明”，另设“设置系统家长控制”操作入口。实验阶段明确标为待验证。
2. 后台重新检查环境和官方状态；已开启时直接显示已开启，未知时要求刷新或进入支持，不能启动注册来试错。新设备判定所需的非敏感证据也必须先确定。
3. 展示官方 PIN 与任我玩密码分别保存，以及现有计时恢复不会删除官方 PIN 的说明，由家长确认进入原生界面。
4. 建立 PCTL 互斥窗口后，NRO 调用 `pctlauthRegisterPasscode()`；禁止重复启动，处理失焦与返回后的输入残留。
5. 返回后让后台取得新观察结果，丢弃原生界面前的状态缓存；显示“官方家长控制已开启 / 仍未开启 / 状态待确认”。不能把旧的 120 秒内缓存用作本次操作的验证。
6. 重新采集接管前置条件，再由家长确认接管。原生界面 Result、`1031` 状态和 `complete_setup` 结果分别展示；官方设置成功但接管失败时应准确说明两者。

若家长取消或 NRO 中断，再次进入时先观察当前系统状态，不自动重放 PIN 注册，也不宣称系统保持原状。原生界面语言可能由系统决定，返回后的 PlayWise 页面继续遵循应用语言；三语提示需要覆盖这些状态。

## 最小验证计划

先用独立实验 NRO 或 Device Lab NRO 的隔离入口验证；初次实验不同时增加私有 PIN 写入或自动计时初始化。原生界面会持久化官方设置，使用操作者愿意配置的测试设备，PIN 仅在 Nintendo 界面输入。

| 场景 | 必须采集或确认 |
| --- | --- |
| 从未配置官方家长控制，完成注册 | 界面能打开和返回；Result；注册前后 `1031/1006`、可用计时字段与 `0x44`；系统设置中的实际状态 |
| 注册过程中取消 | 返回、焦点和按键恢复；系统实际状态；可再次正常设置；不猜测取消 Result 的含义 |
| 原生界面启动失败或异常退出 | 保留原始 Result/module/description；随后状态读取独立成功或失败；不伪造完成 |
| 官方设置已存在或手机已配对 | PlayWise 前置门禁拒绝首次注册；已有 PIN、限制与配对保持；如需研究原生界面本身对这些状态的行为，另列实验 |
| 注册后计时配置全零或未知 | 显示官方开启与接管失败的差别；现有接管继续返回 313，不写默认计划 |
| 注册后计时配置可接管 | 新观察结果支持现有接管；安装快照时点正确；再以非关键游戏检查实际扣时与到时限制 |
| 相册与 application 两种启动方式 | applet 权限、内存、焦点、触摸、返回与主循环恢复分别验机 |
| 后台并存、NRO 退出、睡眠/唤醒 | 互斥期间无并发 PCTL 会话或队列旁路；无法证明退出时停止新写入；恢复必须重新检查 |

报告绑定 NRO/候选包哈希、源码身份、机型、HOS、固件摘要、Atmosphère、入口模式和观察时间。只保存非敏感 Result 与状态；官方 PIN、截图中的 PIN、任我玩密码和密钥均不进入报告或诊断。

后续实现的 host 测试需覆盖成功回读、取消、启动失败、返回成功但仍未开启、状态读取失败、旧缓存、重复输入、中断后重新观察、后台互斥和全零接管拒绝。不能用 stub 的“注册成功即 enabled=true”证明真实系统行为。

一旦修改 C/C++、NRO、sysmodule、权限或打包，最终执行 `python tools/package_remote.py`，默认构建并校验 Eden 应用；修改 UI 时再按需执行 `--with-previews`。Host/Eden 能验证上述状态机和交互，不能证明 auth applet、官方设置持久化、PCTL 计时或限制效果。正式开放前还需对应真机记录，资格仍按既有流程管理。
