# 应用内在线更新方案调研

[调研分类](../README.md) · [文档索引](../../README.md) · [现有手动热更新](../../使用/使用指南.md#手动热更新操作步骤)

调查日期：2026-10-28（Asia/Shanghai）。本地源码基线 `727c1bf98eb824267d58cc9eb301e7b925435cac`，版本 `3.1.2-alpha`，工作区有未提交的 Overlay、配色及其测试修改。本次仅增加调研及索引，不改变产品、更新源、版本号或设备状态。下文“建议／需要”均为待实现方案，不是已发布能力。

## 结论与范围

建议在家长区“支持与恢复 → 软件信息”内增加“检查更新”和“下载并更新”，把已有的完整覆盖安装、安全交接、配置导出串起来。打开应用时可异步检查版本；安装仍由家长确认，失败不能影响离线发码、兑换或现有控制逻辑。

两个给定地址能够提供商店版本信息和程序文件，但当前还不足以支撑可靠的一键安装。必须补齐发布签名、严格版本比较、商店封装适配、逐文件安装日志、中断恢复、NRO 自更新后的重新进入、升级兼容与回退限制。已有热加载只解决“完整文件已经到位后如何切换后台”，没有提供下载和整包安装事务。

配置应通过安装路径隔离保留；更新前再自动创建一份独立配置备份和旧程序前像。程序回退、配置选择恢复、运行账本保护是三个不同问题，不能用覆盖整个旧目录代替恢复。

## 用户流程建议

1. 首次提供“打开应用时检查更新”设置，由家长选择；启用后每次打开异步检查，短期内复用带时间和来源的缓存，并保留手动检查。请求只发往更新源，不上传 PIN、设备 ID、规则、密钥或活动。只获取版本不会改变现有策略；无网／失败不会阻塞应用，也不会强制弹出联网或 Nintendo 登录流程。
2. 家长区软件信息同时显示“当前应用版本”“已安装版本”“后台运行版本”和更新源版本。孩子区最多显示“有更新，请家长处理”，不开放下载、备份或安装权限。
3. 详情显示版本、稳定／测试通道、更新日志、下载大小、来源、兼容性及备份说明。主操作为“下载并更新”，另有“稍后”；下载前按现有敏感操作策略验证 PIN，最终安装确认包含预计影响和备份位置。
4. 下载与验包允许取消；此时只处理本事务暂存文件。验包完成后执行安装预检、独立备份、写入和全量回读。安装阶段暂不允许普通取消，改为完成事务或执行可证明的恢复，画面持续显示阶段。
5. 文件安装完成后显示“重新打开应用以加载新版”。首版采用退出并由用户正常重开 NRO，再由新 NRO 发起既有后台热加载；不能用仍在内存中的旧 NRO 判断“新版后台已经加载”。一键重新进入需在 hbmenu/applet/title override 等实际运行方式下独立验证后再增加。
6. 复用现有后台交接，必要时经家长正常确认环境重新检测。新后台和新 NRO 身份均匹配、同 ID/type 状态回执成功、无本事务残留才显示“更新完成”。Overlay 文件已替换和正在运行的旧 Overlay 必须区分；其退出重开／缓存行为需要真机确认。

“已下载”“文件已安装”“应用待重开”“后台待加载”“需要重新检测”“更新完成”必须分别显示。热加载失败、安装中断和下载失败也要分别提示，不能用一个“失败，请重启”覆盖所有状态。仅在既有有界恢复路径已核实不适用时提示正常整机重启。

新页面遵循现有三语、浅暗主题、动态文本测量和手柄／触摸共同布局；版本号、来源与长日志允许受控换行或滚动。远端说明作为限长纯文本处理，过滤不支持字形，不执行 HTML、脚本或富文本链接。下载状态使用正常信息／待处理语义色，不覆盖现有健康与限制告警。

## 版本、通道和发布源

- 采用严格 SemVer 解析和比较，测试 `beta.2 < beta.10 < 正式版`、`3.1.10 > 3.1.9`、`3.1.2-alpha > 3.1.1-beta.1`；不得字符串排序或浮点比较。构建元数据不决定版本高低，非法标识和数字前导零应拒绝；现有宽松版本正则不能直接承担这项校验。
- 默认订阅稳定通道，测试版需要家长显式选择；当前源只有 beta 时，稳定通道应显示“暂无可用稳定更新”。本地开发版高于在线版时说明差异，不自动降级。显式回退必须单独经过兼容检查与确认。
- 相同版本不同 `release_id` 是重建候选：只有可信发布记录明确声明替代关系时才提示替换，不能通过猜测构建 ID 大小排序。相同身份不重复安装，不伪造 ID 触发后台交接。
- `repo.json` 作为商店发现入口，固定 ZIP 地址作为兼容下载入口；增加 PlayWise 专属、版本化且带签名的发布描述及不可变下载地址。新端点目前未提供，不能假定已经存在。
- 发布描述至少绑定 `schema_version`、应用标识、通道、严格版本、`release_id`、目标 profile／Title ID、ZIP 精确字节数与 SHA-256、全部安装资产的路径／大小／SHA-256、更新器和协议／配置兼容范围、更新日志、发布序号、签名 key ID。通过被签名的 payload 原始字节验证，避免双方对 JSON 序列化规则理解不同。
- 建议内置发行者公钥验证签名（算法与库在实现时固定并审查，例如 Ed25519），私钥只存在发布端；计划密钥轮换与撤销。HTTPS 证书／主机名必须正常校验，不提供跳过开关。单独增加同源 SHA-256 只能发现损坏，不能抵御元信息和 ZIP 被同时替换。
- 固定 URL 可能在下载途中换版：签名描述先冻结目标哈希；下载不符则废弃本事务并重新检查，不能临时接受新响应。发布时先上传完整不可变包，最后更新索引；使用 ETag／Last-Modified 减少重复流量，ETag 不承担真实性验证。
- 记录每通道已接受的可信发布序号防止无提示回放；显式回退走独立策略。设备时钟不可信时不以 `updated` 或本地日期猜版本／签名有效性，也不能关闭 TLS 校验；无法建立可信连接时保留离线功能并明确检查未完成。

商店保持现有格式时，可以提供新的发行签名旁文件来绑定原始商店 ZIP 和安装清单。旧 `md5` 继续供商店兼容使用。缺少可信签名时，第一阶段可上线只读检查与更新说明；正式“一键安装”先等待发布端补齐签名。

## 下载、验包与安装事务

### 网络与解包边界

下载仅在 NRO 中进行，保持后台和 Overlay 不初始化网络。HTTP/TLS 通过有界工作任务或可轮询状态机运行，不阻塞输入／绘制；设置连接、无进展、整次操作期限、重试次数与最大响应大小，退出时释放 socket、线程和服务。项目新增网络权限及内存开销必须经过生产构建与真机生命周期验证。

JSON 按 UTF-8 和严格类型解析，拒绝重复关键字段／应用条目、过深嵌套、过大正文和不合法版本。重定向只能到明确允许的 HTTPS 主机，拒绝降级到 HTTP。按实际接收字节限额并核对签名中的长度，不信任 `Content-Length`、商店 KiB 字段或压缩格式声明；支持 chunked 时也执行相同上限。

ZIP 只解到本事务新建的暂存目录，禁止直接 `extractall` 到 SD 根目录。拒绝绝对路径、盘符、反斜杠歧义、`..`、重复及 FAT 大小写冲突、符号链接、加密包、不支持压缩方式、异常数量／膨胀比／累计解压量；检查 central/local header 的一致性、解压后实际长度、CRC 和 SHA-256。FAT 单文件限制和可用容量也必须预检。

首版严格允许既有 13 个运行文件，目录成员仅允许相应祖先；商店额外的两份描述只在适配器中限长解析及核对，不执行 `U:` 或其他指令、不写到 SD 根目录。未知文件拒绝，新增资产需通过可审查的更新器版本／包格式演进支持。优先让发布端另供与仓库标准包一致的直装 ZIP，商店封装继续只服务商店客户端。

### 持久化事务

建议新增 `sdmc:/switch/playwise/updates/<transaction-id>/` 保存冻结的目标描述、下载包、staging、旧程序前像、配置归档和安装 journal；名称及 schema 需在实现时正式写入协议。目录归属、空间占用与清理规则均由事务记录，未知目录或记录损坏时停止，不覆盖或递归清理。

```text
发现更新 -> 下载 -> 验证签名及资产 -> 安装预检 -> 配置与旧程序备份
    -> prepared -> installing -> files_installed -> awaiting_reopen
    -> 新 NRO 校验 -> 既有后台交接 -> 身份与回执核验 -> completed
```

1. 预检当前安装完整性、源进程身份、空 boot flag、IPC／恢复能力、无活跃请求、无未知 handover／reload／更新事务、无待保存编辑和不兼容数据。容量按“新 ZIP + 新资产暂存 + 旧资产前像 + 配置归档 + journal／余量”动态计算，不写死当前包大小。下载期间后台照常计时，不能为了更新自动加时、解除限制或重置规则；当更新入口被系统限制阻断时保留手动更新和正常授权解限说明。
2. 获取唯一更新 owner，排除另一个 NRO／FTP／商店客户端并发安装的冲突。下载时不长期静默后台；实际发布时仍须防止业务写入与交接竞争，并在写前重新核验身份及文件。现有 quiesce 同时关联旧进程退出，不能不经修改就当成通用安装锁；安装锁与请求接纳规则是新契约和测试点。
3. 所有旧程序资产及其“原来不存在”的状态逐项保存、读回并哈希绑定；配置备份完成且读回有效后才进入首个正式路径写入。正式路径的 rename／remove 前先持久化意图，写后记录已完成，检查 flush／close／SD commit 原生 Result。
4. 每文件以同卷临时文件写入、读回、保留旧前像、重命名发布；未知 `.tmp/.previous` 不覆盖。两份新 manifest 在依赖资产到位后发布，`build.json` 最后发布；最终全量复核后才写 `files_installed`。同目录重命名只提供逐文件更新手段，FAT 上整包不具备跨文件原子性，也不能声称任意断电均无损。
5. `boot2.flag` 正常更新保持原标准空文件，不作为普通文件反复删除重建；异常非空／缺失状态按既有安全门禁处理，不擅自启用后台。需要的暂存／恢复仍由现有热加载 journal 单独负责，在线安装 journal 与其明确关联，不由两个控制器竞争拥有启动标志。
6. NRO 自身最后一段覆盖安排、字体与内置／外部资源的代际一致性需实测。当前运行 NRO 仍是旧版本；覆盖完成不调用旧控制器去验证一个与自身编译身份不同的目标。首版交付完整文件、退出重开，再由新 NRO 处理后台。
7. 下次启动优先处理安装恢复，再做 defaults 初始化、普通更新检查和正常后台交接，防止半安装触发业务。根据 journal、前像和实际哈希定位最后一次发布；不确定时保留材料并显示明确的恢复选项。新 NRO 自身无法加载时还需可独立进入的已验证恢复 NRO／手动整包恢复路径，不能仅依赖新程序自己修复自己。
8. 首次新后台 ready 之后继续核对真实运行身份、配置解析、原请求回执和现有重新检测门禁。版本改变可能触发 `runtime_fingerprint_changed`；不能默认为已授权接管或偷偷删除 `disable.flag`。失败保留旧／新文件身份及 PID／boot 状态，不因目标不存在就无界重试。

### 失败策略

| 中断位置 | 处理原则 |
| --- | --- |
| 下载／验包／备份失败 | 不写正式程序；标记失败，可清理本事务部分下载；备份失败不允许继续安装 |
| 某文件写入或回读失败 | 停止发布和交接；用已验证前像恢复本事务程序文件或补齐同一冻结目标，不能把版本提示改成成功 |
| 断电／关闭导致半安装 | 下次恢复依据已落盘 journal 与实际字节完成或回退；需要验证重启时 boot2 可能先于 NRO 加载的混合代际窗口 |
| 已完成文件安装，旧后台仍运行 | 明示“待重开／待加载”；可以继续正常恢复流程，不宣称后台已升级 |
| 旧后台已退出，新后台不健康 | 保留原交接记录、恢复空 flag；在连续证明无人运行且数据兼容时才尝试经确认的整套程序回退，不强杀未知进程 |
| 新程序已经迁移了数据或发生正常业务 | 不自动回写旧目录；只允许兼容的程序回退，或进入独立且有前像的迁移恢复事务 |
| fatal、未知写入、恢复不明 | 停止依赖操作、留存证据并进入支持流程；不自动整机重启或删除日志／账本 |

断电后的无人值守后台启动保护是关键缺口：应用内 journal 在 NRO 没打开时不会自动运行。需要专门设计并验证后台对安装状态与所需资产代际的只读门禁、兼容旧版后台的范围及启动失败恢复；不能把“下次重开 NRO 会检查”写成整机启动安全保证。为所有历史版本实现完整断电回滚未必可行，首版应声明最低可在线升级版本和受支持的恢复范围。

## 配置保留、备份和恢复

| 数据 | 普通更新 | 更新失败／用户恢复 |
| --- | --- | --- |
| PIN、配对密钥、设备配置、规则、主题／语言／快捷键、用户日历 | 不在安装覆盖路径；不因模板变化重置 | 配置恢复使用现有十一组导入预览与事务；只改用户选择的组 |
| `state.json`、已玩／非电视累计、缓冲领取、nonce／ledger、活动 | 继续正常增长，不能“冻结”为更新开始时状态 | 绝不用升级前旧副本覆盖成功业务痕迹；失败事务继续走原协议回滚 |
| 安装前 PCTL snapshot、当前恢复材料、环境确认、外部 hbmenu 配置 | 原样保留；不从 ZIP 初始化／替换 | 配置归档不承担这些数据的全机恢复，也不把旧环境授权带回新环境 |
| 旧 NRO／Overlay／NSP、字体、模板、两份程序清单 | 独立保存本次程序前像 | 兼容性通过后整套恢复；验证 SD 文件与实际运行版本分别恢复到什么状态 |

自动配置归档建议复用请求 49 的后台串行 stage 和现有归档器，另存本事务专属路径，不能覆盖用户手工保存的 `backups/config-backup.json`。同一 request ID/type 等待回执，超时保留未知，不换 ID 重提。落盘后重新载入验证摘要、文件集和引用关系；归档与索引一并读回，重复离线核验结果一致后才标记可恢复。

现有 UI 只有固定归档路径，需要增加“更新前备份”列表／选择器、来源版本、创建时间、完整性状态、十一组选项及恢复预览；后台重新验证实际归档，不能只信 UI 缓存。保留原手工备份入口。备份含 PIN 哈希和加时密钥，存储在本机，禁止上传到更新源、普通诊断或公开日志；说明同一 SD 卡损坏仍会丢失备份，可由家长另行导出。

恢复 PIN 要验证归档 PIN；恢复配对资料按现有协议生成新密钥，手机需要重新配对。“恢复原配置”不等于把原配对 secret 原样重新启用，也不等于退还已消费额度。未选择配对组时当前密钥继续保留。

至少保留最近一次有效旧程序和独立配置归档；成功确认后可再按数量／总容量轮换历史，失败或未知事务先登记保留原因和复查条件。只删除本事务或已核实归属的路径，不清理用户备份、未知 recovery 或共享日历。清理失败单列提示，不改写更新或恢复结果。

## 必须补齐的功能与实施顺序

| 优先级 | 工作项 | 交付边界 |
| --- | --- | --- |
| P0 | 发布端可信描述、签名、不可变目标与完整资产哈希 | 现有 ZIP 和 MD5 可兼容保留，缺少可信描述时不开放正式一键安装 |
| P0 | SemVer、通道、同版本重建及显式降级政策 | 先实现纯 C／Host 确定性模块；当前较新的开发版不会被误降级 |
| P0 | 有界网络、ZIP 安全解析、商店封装适配 | 先只读检查与下载暂存；不把商店路径脚本变成可执行安装指令 |
| P0 | 配置多代备份、旧程序前像、全包安装 journal 和安装锁 | 备份验证完成才发布首个文件；任一错误阻止后续依赖操作 |
| P0 | 自更新重开、中断启动保护、独立恢复入口 | 首版明确最低支持版本；真机验证 applet／应用模式及 boot2 先启动窗口 |
| P0 | 数据 schema／IPC／恢复版本兼容与迁移事务 | 版本号高低不能代表可升级／可回退；未经定义的新 schema 拒绝写入 |
| P1 | 三语更新页、开机检查设置、缓存／忽略某版、进度和错误重试 | 自动检查不等于自动安装，儿童与只读支持模式不能安装 |
| P1 | 备份列表、选择恢复、存储管理、脱敏更新历史 | 可独立核验目标／源哈希、各阶段和恢复状态，不保存秘密 |
| P2 | 经验证的自动重开、可靠断点续传、镜像故障切换 | 续传需冻结 ETag／目标哈希，不匹配重下；首版可采用有界整包重下 |

实施分三批：

1. **只读检查**：版本／通道模块、列表解析、网络有界性、软件信息 UI、发布端契约。没有签名也只能提示商店版本与说明，不宣称已经安全验包。
2. **安全安装**：签名与全部资产验证、自动独立备份、安装锁／journal、异常恢复和重开引导；复用现有后台加载，先证明同数据格式升级。
3. **完整恢复与体验**：备份选择 UI、声明式迁移和降级兼容、经验证的自动重开／续传／镜像。涉及迁移的版本，在所需恢复能力未具备时不进入在线可安装列表。

发布脚本将 clean 构建、统一门禁、冻结 ZIP／精确哈希、签名和索引更新按依赖顺序串联。商店版本、`info.json`、包 manifest 及内嵌身份有任一不一致就不发布。人工主要功能验证和完整资格仍分别记录，签名或下载成功不会把 `pending` 自动变成 qualified。

## 验收与本次实际验证

实现后的 Host 测试需覆盖成功升级、相同版本／本地较新／通道不符，非法与重复元信息，断网／重定向／TLS 失败／响应超限，旧签名回放／无效签名／清单错版，路径穿越／大小写重复／ZIP 炸弹／截断包，空间不足／备份失败，以及每个写入、重命名、commit 和 journal 阶段的故障注入及重开恢复。每个错误都断言正式文件、配置、nonce 和原恢复材料的状态，不能只断言显示了错误。

迁移测试要求升级后新版本可读、业务不退还、失败事务恢复；降级到不支持当前 schema 的版本必须明确拒绝。自动备份读回与两次离线核验、未知前像拒绝覆盖、手工备份不被更新任务覆盖也必须有测试。
