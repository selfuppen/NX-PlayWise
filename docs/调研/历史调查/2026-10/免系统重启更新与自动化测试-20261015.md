# 免系统重启更新与自动化测试（2026-10-15）

后续实现与操作说明见[无人值守更新与测试指南](../../../开发/无人值守更新与测试指南.md)。新增内容身份、静默隔离、journal 有界重试、持久事件和主机协调器；下文真机记录仍只证明当时的冻结产物，不覆盖这些新增实现，也不改写原始封存证据。

## 结论与范围

源码层面已有可复用的免重启路线：在线覆盖完整标准包，旧后台协作退出，再由独立启动方通过 `pm:shell` 启动 SD 上的新版后台。同日后续真机探索已证明：现有后台管理浮窗可以启动已停止的新版后台，标准 NRO 也完成了一次免重启回切；第一轮标准切换则在 journal 更新阶段中断。分项结果与恢复证据见下文，不能把这些结果合并成稳定无人值守部署通过。

建议先修复并验证现有标准热加载的 journal 失败处理和 IPC 重连边界，复用现有 NRO 与管理器恢复能力，再决定是否实现内部专用的有界部署协调器。用户已授权本批使用 PIN 或临时跳过；实际沿用正常 PIN 验证，没有绕过或修改认证。只有需要后台、游戏和前端共同无人值守迭代且现有进程无法承载时，才评估独立常驻协调器。不能为省掉重启直接启用旧 BD23F1、自启动输入探针或强杀后台。

免系统重启仍需重启被替换的进程或重新加载前端文件。当前 `runtime-ready.json` 的 `boot_id` 是后台每次启动随机生成的**进程实例标识**，不是系统启动标识；它变化不能证明系统重启，它不变也不能证明磁盘上的新代码已运行。

不要用标准后台自己调用“退出后再启动自己”：退出后已无执行者。后台启动线程也不能解决自身进程结束的问题。需要仍存活、拥有实际权限的独立启动方。

### 现有热加载时序

`hot_reload.c` 与 `sysmodule/source/main.c` 的实现为：

1. 新 NRO 验证完整安装与源 PID，写 journal 和带事务 ID 的 `handover/intent.json`。
2. 后台停止接受新 IPC 提交，在串行调度后、没有活跃 recovery 时写 `ready.json`。
3. NRO 关闭自己的旧 IPC 会话，以专用 backup 暂存原空 `boot2.flag`。
4. 后台看到 flag 缺失后自行退出，释放 IPC 和 PCTL；NRO 连续三次确认目标 Title ID 不存在。
5. 恢复原空 flag、清理本次交接文件，然后通过 `pmshellLaunchProgram`、`NcmStorageId_None` 启动同 Title ID。
6. 核对新 PID、目标 release、profile、新进程 boot ID；NRO 再重连 IPC 并提交正常状态请求。

交接、退出和 ready 期限分别为 10、10、30 秒；后台启动本身有 15 秒延迟，因此不能用几秒内未 ready 判定失败。现有启动策略仅在确认目标不存在时允许总计两次启动尝试。完整判定还包括控制器之外的 IPC 重连和业务状态检查。

`boot2.flag` 的暂存是 PlayWise 交接实现的退出触发条件；不是“删 flag 就会由 Atmosphère 自动停止进程”。恢复 flag 也不等于已启动新版，实际启动由 PM 调用完成。

### 不能忽略的五个问题

**构建身份碰撞。** `tools/generate_release_manifest.py` 的 `release_id` 只由版本与 commit 前 12 位组成，`source_dirty` 只是布尔标记。同一个 commit 上修改代码反复构建，可能得到相同 release ID、不同二进制。`ptc_hot_reload_inspect` 在 release ID 相等时先判 `CURRENT`，不会进入不同 ID 分支的组件验证和切换。未来协调器必须绑定候选 Zip 与三组件 SHA-256，并为已加载实例提供可信的构建身份；不能只比较磁盘清单，也不能手改 build.json 冒充嵌入身份。是否扩展生产构建身份需另行设计、测试与兼容评审，本次不改协议。

**启动成功不等于恢复控制。** `sysmodule/sysmodule_setup.c::validate_runtime_fingerprint` 将安装清单 release ID 与 `compatibility.json` 中已接受的 ID 比较。新 ID 在既有 active/released 安装上会触发 protection 和 `runtime_fingerprint_changed`，需要正常重新检测与接管。自动化必须把这一步列为显式测试状态，通过现有合法授权流程处理，不能直接改 compatibility、复制旧接受记录或移除保护标记来伪造通过。没有授权输入时，仅完成更新与只读诊断，后续控制测试记为前提不满足。

**静默不等于文件队列停止。** 当前 `accepting=false` 拒绝的是 IPC 提交；主循环仍会调用 scheduler，scheduler 仍扫描 SD 队列。因此部署窗口还需要停止所有测试请求生产者，关闭旧客户端，核对 pending/processing 及原请求回执。不能拿 ready 文件推断所有外部写入已停止，不能对超时未知请求换 ID 重发。

**安装清单发布与旧进程存在竞争。** 旧后台的 scheduler 会再次执行 bootstrap 检查，而检查读取 SD 上的 build.json。在线替换为新 release ID 后、旧后台退出前，旧进程就可能发现新清单与旧 compatibility 不匹配而进入保护。因此 staged 上传之外还需设计安装提交、静默交接和保护态处理的明确顺序；不能假设传文件阶段对运行状态完全无影响，也不能把这种保护当作更新后已恢复正常的证据。

**前端和后台的控制权。** NRO/Overlay 一次重新打开的流程仍依赖设备入口。此前[浮窗输入隔离补测](../../../开发/验收记录/2026-10/自动化与交互/浮窗远程输入隔离补测-20261015.md)中的底层 HOME 变化属于代理未证明的推断，[人工复核更正](../../../开发/验收记录/2026-10/自动化与交互/人工画面复核与快捷键更正-20261015.md)已撤回该推断，用户在本轮聊天再次确认输入隔离没有问题，应按该授权继续。本批正常输入 PIN，并执行经过页面检查的确认与恢复。未来通用协调器仍需明确前台身份和目标，不能将某个未知页面上的按键序列当作通用升级接口。

## 分阶段路线

| 阶段 | 交付与通过条件 | 能自动化的范围 |
| --- | --- | --- |
| A：现有路径验真 | 用两份身份明确的完整标准候选，按[标准热加载验收](../../../开发/测试指南.md#标准版在线覆盖与热加载)完成 A→B→A；保留单 owner、IPC、状态与恢复证据 | 先证明正常热加载，启动与 PIN 仍由人集中完成 |
| B：固定协调器原型 | 内部独立 NRO 一次打开，持有有界运行租期，通过 SD mailbox 接收已准备候选的切换任务；复用交接与 journal 逻辑 | NRO 保持运行期间，后台候选循环、队列回归与取证；不宣称游戏/前端全自动 |
| C：完整测试台 | 若 B 无法满足前台测试，再单独验证无 PCTL、无 HID/AM/BPC/PDM 初始化的常驻协调器，限定 Title ID、目录、租期、次数和恢复策略 | 部署协调器可在目标 NRO、Overlay、游戏切换时继续存活；仍取决于权限、资源和前端重进验证 |

B 是新设计，不是已有命令。协调器不得从待替换 NRO 的编译期 release ID 推断目标；它读取并验证任务绑定的候选身份。只能操作预先指定的 PlayWise Title ID 和本批文件，不提供任意进程管理或远程 shell，不进入标准安装包。测试机的一次批次授权与生产版家长入口分别维护，不删除标准 PIN/确认契约。

B 的初次启动也先核验所需服务和退出生命周期，沿用已证明的未受限入口，不把旧 hbmenu/Controllers X+A 或额外输入初始化带回批次。保持 NRO 运行的可行性只覆盖该运行窗口；用户切走、系统限制或进程退出后，不宣称协调器仍可调度。

C 是条件性后续，不是默认增加 sysmodule。若进入此阶段，先独立证明 PM/SM/FS 权限、会话关闭、线程退出、内存和反复启动资源稳定性，再允许它切换 PCTL owner。NRO 能调用某服务并不能证明新的 NPDM 或 Overlay 宿主也有同样权限；不能沿用已知不稳定的旧 PM 电源路线。

协调器自身保持固定版本，不在它负责的同一批更新中替换自身。需要升级协调器时另做交接，避免同时失去测试控制与恢复执行者。

## 自动化闭环的最小契约

以下是待实现要求，不能作为现成部署脚本执行：

1. **准备**：统一入口 `python tools/package_remote.py` 构建、测试和校验，默认包含 Eden；冻结候选 Zip 与三组件哈希。归档当前 SD 映像、安装清单、运行身份、启动标记、公共规则、完整 0x44/timer 和恢复材料；PIN/密钥留在受保护的原数据中，不写公开报告。
2. **停发与暂存**：请求生产者停止，原 UUID/type 逐项对账，关闭目标前端。FTP 先上传本批 staging 目录、回读校验，不边传边启动；安装提交需有自己的 journal。禁止使用 clean 安装清除测试历史来掩盖状态迁移。
3. **切换**：沿用旧后台协作退出、连续证明进程不存在、恢复 boot flag、再启动目标的顺序。切换和安装 journal 都须绑定同一批次及各自文件所有权，并规定中断恢复顺序；不复用另一个事务的 backup。
4. **证明加载**：核对目标 PID、profile、IPC v2、新进程实例及可区分的实际构建身份。磁盘哈希只能证明安装内容；若缺乏已加载映像身份，则记录工具缺口，不能把同 release ID 的不同二进制判为切换成功。
5. **恢复测试前提**：通过合法接管流程核对 setup/compatibility/protection。保持原 PIN、密钥、nonce、规则、历史与恢复材料；普通状态成功不自动代表 Enforce 已正常工作。
6. **执行与取证**：只发一次已记录的标准请求，保存同 ID/type 回执；raw、Result、完整 0x44、时间与身份只追加保留。截图只用 pixelPeek，集中生成人工复核材料。真休眠、底座、到点提示和真实游戏效果仍按各自验收口径执行。
7. **收尾**：成功时清理本批 staging 与标记，核对后台、IPC、规则和启动状态。退出前失败恢复旧接单状态；退出后失败保持 boot flag 和 journal 可恢复，仅在证明目标不存在时按既有上限尝试。fatal、未知写入、身份冲突或恢复无法证明时停止依赖操作，不强杀、不无限启动、不自动重启掩盖故障。

为了证明“系统没有重启”，报告需保存独立协调器在整个窗口持续存活的身份和连续单调时间记录，并保留后台实例变化。不要把后台进程 `boot_id` 当作系统重启计数；原始采集仍按各自 boot 分段，不跨后台 boot 相减 tick 计算业务用量。

阶段 A 至少覆盖正常 A→B→A、源拒绝退出、目标失败、stale ready、安装中断和交接各 journal 阶段中断。阶段 B 再做有界多轮压力与资源检查；验证 `QUIESCING` 不回退重发、文件队列无遗留未知请求，以及没有第二个 PCTL owner。Host 源码断言和 Eden 无法代替这些真机证据。

热加载回归不能代替冷启动、正常系统重启、真实休眠/唤醒、跨日和物理底座资格测试。自动化收益主要在反复构建、部署、状态/规则回归、采集与报告，物理场景集中为少量批次。
